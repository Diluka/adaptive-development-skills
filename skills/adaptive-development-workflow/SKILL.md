# Adaptive Development Workflow：自适应开发工作流

<SUBAGENT-STOP>
如果你是为边界明确的工作单元派发的子代理，跳过任务级路由，只执行派发给你的单元和主要方法。任务级节点转换、工作单元拆分、范围、授权与交付由根代理编排；不得擅自改变这些边界或发起、转派相关流程。只有委派说明明确授予局部编排权时，才可在原单元边界内继续派发更小的执行单元，并向协调者回报结果。
</SUBAGENT-STOP>

## 1. 入口职责

本技能只承担宏观决策：判断任务侧重点和整体交付意图，拆分与分级工作单元，编排讨论 / 调查 / 设计 / 作业 / 验证 / 评审节点，处理节点转换、范围、授权和交付边界。节点进入与转换的详细判据见 `resources/node-routing.md`，术语与中英对照见 `resources/terminology.md`。

当前节点确定后，具体如何做、选择什么方法或机制、需要什么证据，统一交给 [execution](../execution/SKILL.md)。标准方法被用户直接指定时，由该方法自行核验前提；方法偏好不改变本技能的任务边界和节点路由。

## 2. 识别任务侧重点与交付意图

任务类型是模糊的大分类而非互斥标签，可看作任务的**侧重点**：讨论 / 调查 / 作业 / 验证。一个任务通常以一类为主，也可能叠加其他类型；侧重点决定主工作流。

先判断整体交付意图：

- **开发任务**：最终需要项目保留、集成或交付代码、配置、依赖、测试、脚本、技能、工作流或版本控制文档，可先包含调查单元。
- **非开发任务**：只交付解释、评审意见、事实、根因、可行性证据或决策输入，不自动产生分支、提交、推送或 MR/PR。

调查中使用的可丢弃脚本、原型、测试或插桩不改变这一判断。决定保留临时产物或落实调查结论时，结束调查单元，把正式产物作为开发单元重新路由。

## 3. 拆分工作单元

按可独立描述的目标、权威判据、交付物和证据边界拆分，不按文件、对象、技术层或「属于同一请求」打包。一个单元只承担一个主要问题；多个方法条件同时成立时，先检查是否存在可独立反证的目标，可分开就建立有依赖的单元。

先分类每个单元：

- **调查单元**：消除对当前系统、根因、契约、可行性、设计取舍或未知行为的不确定性，只交付可追溯事实、证据或决策输入。
- **开发单元**：交付项目需要保留、集成或发布的变更，以明确需求、真实调用方、已核验契约或已接受的调查结论为依据。

调查达到足以决策的证据后立即结束。若结论要求正式修复、长期测试、契约产物、规格或实现，把新目标带回本入口重新分级和编排，不让调查单元顺手实施。

## 4. 按当前增量分级

只按当前请求造成的实际增量分级，不继承父任务、现有分支或整个 PR/MR 的复杂度。文件数和行数只是信号；运行行为、公共契约、影响范围、不确定性、可逆性、外部副作用和直接证据更重要。

| 级别 | 可观察条件 | 最低充分节点 |
|---|---|---|
| 微小 | 目标明确、局部可逆；不改变运行行为或公共契约，不涉及依赖、生成规则、权限或产物自身的外部副作用；可直接检查 | 作业后做必要直接核对；不落盘计划，不安排最终独立评审 |
| 常规 | 有边界明确的行为或配置变化，或需要若干相关步骤；没有重大未知或高风险 | 按协调与恢复收益决定设计节点；保留覆盖受影响路径的验证；独立视角能补真实风险时再评审 |
| 复杂或高风险 | 涉及跨模块或公共契约、架构与依赖迁移、安全、身份、资金、数据、并发、破坏性或难回退操作、正式环境、显著未知，或多代理共享状态 | 保留落盘计划、风险相称验证和独立评审节点，并安排回退或恢复边界 |

从最低充分级别开始，真实影响面变化时升降级。每个保留节点都要能说明它能发现哪种合理错误；已有证据覆盖同一风险或节点没有实际收益时可跳过，但复杂或高风险级别规定的最低节点不得用同一参与者的自查冒充。

## 5. 编排与转换

工作流在六个节点间动态编排：讨论 / 调查 / 设计 / 作业 / 验证 / 评审。节点并非固定流水线：

- **动态编排**：目的不明确时从讨论开始，随边界清晰派生其他节点；明确指令或已有方案可直接进入相应节点；小问题可直接回答或操作。
- **返工循环**：验证失败或评审发现范围内问题时，返回受影响节点，再走必要的后续节点。
- **插入子流程**：作业中出现契约、根因或可行性未知时插入调查；出现会改变方案且无法自行解决的歧义时插入讨论；完成后返回原流程。
- **任务分裂**：新事实产生独立目标时拆成新单元，各自重新分级和编排。

节点进入、退出和完成转换的详细判据见 [resources/node-routing.md](resources/node-routing.md)。进入任一节点后，用 [execution](../execution/SKILL.md) 选择并落实该节点的具体方法、验证手段和执行机制。

## 6. 重新编排边界

执行结果只改变当前动作、方法、证据组合或计划细节，且目标、工作单元、级别、节点、范围、授权和交付结果不变时，由 `execution` 在原节点内反馈修正后继续。

出现以下任一变化时回到本技能重新编排：

- 任务侧重点、开发 / 非开发性质或工作单元目标变化；
- 新事实要求拆分或合并单元、增减节点或调整级别；
- 需求、公共契约、范围、授权、交付结果或外部副作用变化；
- 调查结论需要形成长期项目产物；
- 当前节点无法继续，必须插入讨论、调查或返回上游节点。

证据冲突时按以下优先级判断：明确需求与不变量 > 真实调用方和运行行为 > 依赖、协议与框架契约 > 实现与测试 > 计划、清单与方法偏好。测试是证据，不得发明业务行为；计划是可修正的工作依据。

## 7. 授权与交付边界

开发任务和准备正式纳入版本控制的项目变更，默认完成普通 Git 交付：根据仓库实际远端和约定创建或使用分支、提交、推送，并在 GitLab 创建 MR 或在 GitHub 创建 PR。用户明确要求仅修改本地、只提供差异、不提交、不推送或不创建 MR/PR 时，按限制逐项收窄。

默认普通 Git 交付停在 MR/PR。合并、发布、部署、正式环境写入、权限修改、外部消息、流量调整和其他高影响外部操作，只有在用户明确要求且安全边界成立时才执行。选择任何方法或交付机制都不扩大授权。

## 8. 安全边界

- 调查、开发和验证期间不得写入正式环境数据源；只读证据不授权数据修复。
- 不为测试制造真实调用方不需要的生产分支、开关、包装层、回退或公共接口。
- 保留用户和其他任务的改动；不通过暂存、提交、重置、清理或移动来占用其状态。
- 微小任务不为形式增加规格、计划、测试、代理或评审；标准方法一旦选中则忠实执行其核心循环。
