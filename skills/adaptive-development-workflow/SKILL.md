# Adaptive Development Workflow：自适应开发工作流

<SUBAGENT-STOP>
如果你是为边界明确的工作单元派发的子代理，跳过本技能，只执行派发给你的单元和主要方法。任务级拆分、范围、授权、节点转换与交付由根代理负责；仅在委派说明明确授权时，才在原单元内继续拆分，并向协调者回报结果。
</SUBAGENT-STOP>

工作节点都是可选的，不预设任何节点"必须"或"不能"进入——由你根据任务实际情况临场编排。选中某个节点，就要按该节点的规矩办事。

## 工作节点

| 节点 | 是什么 | 规矩 |
|---|---|---|
| **讨论** | 与用户一起澄清需求边界、关键歧义与成功标准 | 先发散再收敛，只澄清会实质改变方案的关键歧义；可参考头脑风暴（Brainstorming）：发散探索可能性 → 收敛明确界限 → 达成一致 |
| **调查** | 取证回答未知：读代码、文档、日志、跑实验 | 只交付可追溯事实、证据与决策输入，不把结论直接变成项目差异；证据足以回答原问题即停止 |
| **设计** | 把选定方向展开为落盘方案 | 计划只承载已完成选择的内容，不替代行为、契约与架构方向的选择 |
| **作业** | 产出交付物：代码、正文、配置、调研 | 以真实调用方、契约和项目约定为边界，不擅自扩大范围 |
| **验证** | 核对产物是否符合预期 | 用真实消费或激活路径的直接证据；证据足以支撑声明即停止追加；手段不限于自动化测试 |
| **评审** | 整体审视交付是否值得 | 必须独立于实现者（不能自审）；只给意见与结论，不改动 |

## 完整例子：串起全部节点的复杂工作流

一个复杂任务可以按需取用节点，形态例如：

1. **讨论**：需求边界模糊 → 与用户发散收敛，明确目标、范围与成功标准。
2. **调查**：存在会改变方案的未知（契约、可行性、根因）→ 先取证回答。
3. **设计**：选定方向复杂或高风险 → 落盘计划，展开实现步骤与验收边界。
4. **作业**：按计划实现，产出交付物。
5. **验证**：用真实路径证据核对产物符合预期。
6. **评审**：复杂或高风险任务由独立视角整体审视。
7. **交付**：按仓库约定完成分支、提交、推送与 MR/PR，回报链接并等待 CI 终态。

节点不是固定流水线：返工（验证失败回到作业）、插入子流程（作业中插入调查或讨论）、任务分裂（新事实产生独立目标）都是正常形态。每个保留节点都要能说明它能发现哪种合理错误。

## 授权与红线

- 开发任务默认按仓库约定完成分支、提交、推送与 MR/PR；用户明确收窄时按其限制执行。
- 合并、发布、部署、正式环境写入、权限修改、外部消息、流量调整和其他高影响外部操作需要明确授权；选择任何方法或交付机制都不扩大授权。
- 调查、开发和验证期间不得写入正式环境数据源；只读证据不授权数据修复。
- 保留用户和其他任务的改动；不通过暂存、提交、重置、清理或移动来占用其状态。
- 节点内的具体做法、方法与机制选择交给 [execution](../execution/SKILL.md)。
