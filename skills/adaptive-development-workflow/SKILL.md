# Adaptive Development Workflow：自适应开发工作流

## 核心原则

把需求具体化为可验证的工作单元，再根据每个单元的主要不确定性、风险、真实调用方和证据来源，选择当前最合适的主要开发方法。整个需求可以组合多种方法，但不能强迫所有工作单元使用同一种流程。

一个需求可能同时包含契约集成、确定的业务规则、删除、调查和发布。每个工作单元都应有明确的预期结果与主要方法；辅助技能只补充必要证据。

每个开发任务在正式实现前必须通过 [writing-plans](../writing-plans/SKILL.md) 写一份计划文档，一份文档可以覆盖全部工作单元。简单、清晰、低风险的机械修改使用简短计划并直接执行，不增加复杂模板或用户审批仪式。最终版本完成前，必须通过 [requesting-code-review](../requesting-code-review/SKILL.md) 进行至少一轮独立子代理评审；风险只决定评审深度，不决定是否评审。

## 先判断任务类型

如果任务的预期交付结果包含需要被项目保留、集成、提交或交付的产物变更，它就是开发任务。正式代码、配置、依赖声明、锁文件、构建或 CI 脚本、准备保留的测试、数据模型、迁移、生成规则、技能、插件、代理规则、项目工作流，以及准备版本控制的正式项目文档都属于项目产物。

以下任务本身不是开发任务：

- 纯解释、咨询、翻译或回答问题；
- 只读代码、日志、数据库、Git 或运行状态调查；
- 只运行测试、构建、类型检查或静态分析而不保留项目差异；
- 只评审并报告问题，或只交付已经完成开发的提交、推送、PR/MR 或部署；
- 以结论和证据为交付结果的调查或技术探索，即使它编写了最小示例、探测脚本、临时原型、复现代码、实验测试或临时诊断插桩。

是否写代码、修改文件或执行写操作都不是判据。调查中的临时产物必须放在项目规定的实验位置、临时目录、沙箱、实验分支或可丢弃工作树，不得混入最终项目差异；结束时检查工作区，证明临时依赖、配置、锁文件和生成产物没有遗留。外部写入、破坏性操作、正式环境和权限扩大仍受授权与安全边界约束。

当调查中的原型、脚本、测试、配置或其他实现被决定保留时，任务从这一刻转换为开发任务：停止扩展临时代码，创建或更新计划，明确哪些内容保留、重写或删除，为正式实现选择主要方法，再按用户确认边界完成实现、验证和独立评审。如果请求一开始就要求“调查并完成实现”，整体从一开始就是开发任务，调查只是其中的工作单元。

## 先确定事实

证据冲突时按以下顺序判断：

1. 明确需求与不变量
2. 真实生产调用方与运行行为
3. 依赖、协议与框架契约
4. 实现与测试
5. 计划、检查清单与偏好的开发方法

测试是证据，不是最高权威。计划是对工作的假设，不能用来覆盖当前系统事实。

## 为每个工作单元选择方法

当调用方、证据来源、风险或改动类型不同时拆分工作单元。先记录每个单元的预期结果与真实使用方，再选择最窄且足够的方法。

| 可观察条件 | 主要方法 |
|---|---|
| 第三方 API、SDK、框架、协议或 CLI 边界 | [contract-verification](../contract-verification/SKILL.md) |
| 需要选择测试层级或接缝、处理测试与实现冲突，或判断失败测试是否代表真实回归 | [evidence-based-testing](../evidence-based-testing/SKILL.md) |
| 需要新增或改变明确行为，且存在稳定、符合真实调用方式的测试接缝 | [test-driven-development](../test-driven-development/SKILL.md) |
| 需求、调用方式和依赖契约已明确，不需要专门调查、探索或测试驱动 | 直接实现，并按风险验证 |
| 删除适配器、依赖、导出项或无效路径 | [caller-driven-cleanup](../caller-driven-cleanup/SKILL.md)；不要为了 TDD 制造新行为 |
| 根因未知或行为间歇出现 | [systematic-debugging](../systematic-debugging/SKILL.md) |
| 技术可行性未知 | [technical-spike](../technical-spike/SKILL.md) |
| 依赖或工具链版本变化 | [dependency-upgrade](../dependency-upgrade/SKILL.md) |

同一工作单元可能需要辅助技能，但必须指出决定其开发方式的主要问题，并选择一个主要方法。整个需求通过不同工作单元的方法组合完成，不为整个请求选一个“唯一赢家”。

## 按需组合生命周期支持

以下技能负责把各工作单元组织成完整需求生命周期，不替代工作单元的主要开发方法：

| 生命周期条件 | 支持技能 |
|---|---|
| 用户意图、成功标准或关键约束仍会改变方案 | [brainstorming](../brainstorming/SKILL.md) |
| 用户或项目规范要求长期保留需求、设计、接口或其他项目文档 | [project-documentation](../project-documentation/SKILL.md) |
| 任何开发任务即将开始正式实现，或调查产物决定转为正式交付 | [writing-plans](../writing-plans/SKILL.md) |
| 计划文档已经具备执行条件 | [executing-plans](../executing-plans/SKILL.md) |
| 边界清晰的工作单元可显著节约根代理上下文 | [subagent-driven-development](../subagent-driven-development/SKILL.md) |
| 至少两个单元不共享可变状态或文件 | [dispatching-parallel-agents](../dispatching-parallel-agents/SKILL.md) |
| 开发任务的正式实现和相关验证已经完成 | [requesting-code-review](../requesting-code-review/SKILL.md) |
| 复杂非开发调研存在明显偏航或证据遗漏风险 | 按准确性收益选择 [requesting-code-review](../requesting-code-review/SKILL.md)，不设统一门禁 |
| 即将声明结果完成 | [verification-before-completion](../verification-before-completion/SKILL.md) |
| 实现完成，需要分支集成或交接 | [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md) |

## 贯穿需求生命周期

1. 根据预期交付是否包含要保留的项目产物，判断请求是否为开发任务；混合请求按工作单元区分调查与正式实现。
2. 只澄清会实质改变方案的模糊需求，把用户意图转成可观察结果、成功标准和约束。
3. 按结果、调用方、依赖关系、风险和证据来源拆分工作单元，并为每个单元选择当前最合适的主要方法。
4. 开发任务在正式实现前写入一份覆盖整个任务的计划文档，告知用户路径，并按风险判断是直接执行还是等待确认。
5. 根据上下文收益决定是否委派实现；边界清晰且能显著减少根代理局部上下文时优先使用子代理，否则由根代理实现。
6. 按依赖顺序完成必要调查和正式实现并同步计划；若新证据推翻假设，更新计划并重新选择方法。
7. 分别验证每个工作单元，再验证组合后的完整需求和真实运行链路。
8. 开发任务由未参与实现的独立子代理评审最终完整差异；根代理核验意见，实质修复后重新验证并复审最终版本。
9. 根据授权完成 PR/MR、集成与交接，保留未完成事项和剩余风险。

计划文档和最终独立评审是所有开发任务共有的生命周期责任，但计划不是统一的用户审批门禁，独立评审也不替代运行时验证。简单需求可以使用很短的计划和很窄的评审；TDD、实现子代理、工作树、PR/MR 和提交仍按工作单元、上下文收益、风险与授权选择。

非开发任务不强制计划或独立评审。复杂功能调研如果范围广、证据链长或容易偏离原目标，可以选择独立评审代理检查目标覆盖、反证和结论准确性；简单调查直接以证据完成。除明确规定为必需的步骤外，只在某个方法或代理角色能实质提高任务完整性或准确性时使用它。

## 设置风险边界

修改状态前确认：

- 操作是否可逆或具有破坏性；
- 本地、测试、预发布与正式环境边界；
- 有未提交改动的工作树或并发编辑；
- 外部写入、推送、消息、部署与数据变更的授权；
- 支撑每个最终声明的最小验证。

没有业务行为变化、需求明确、低风险、安全且处于现有授权范围内的工作，告知计划路径后直接执行。涉及业务语义变化、关键歧义、高风险、破坏性操作、正式环境、外部写入、权限扩大或新增副作用时，实施前必须确认计划。

调查和验证期间不得写正式环境数据源。只读证据可以指导代码改动，但不授权数据修复。

## 示例

一个同时包含外部契约调整、旧适配器删除和确定性规则修复的请求应拆成三个单元：先验证真实契约；再追踪调用方并删除适配器，不为清理使用 TDD；最后确认规则不变量，通过真实测试接缝修复行为。结束时验证组合后的运行链路，同时保留各单元的不同方法。

## 常见错误

- 对删除使用 TDD，结果重建了本应移除的路径。
- 把通过的模拟测试当成 SDK 或 HTTP 契约证明。
- 当前调用方已否定计划，仍机械执行旧步骤。
- 没有落盘计划就实现，或把简单计划错误扩张成复杂流程。
- 把必须写计划误解为每项工作都必须等待用户批准。
- 因调查写了临时代码，就把它误判为要交付的开发实现。
- 将临时原型直接提升为正式实现，不先转换任务类型并更新计划。
- 按风险省略开发任务的独立评审，或用主代理自查替代独立子代理。
- 把独立评审必需误解为所有正式实现都必须由子代理完成。
- 并行修改相同文件、锁文件或共享状态。
- 跑了全量测试，却无法说明它支撑哪个声明。
