# Adaptive Development Workflow：从请求选择工作路径

<SUBAGENT-STOP>
已收到边界和主要方法明确的委派单元时，只执行该方法并回报事实、产物和验证；不要为实施加载根入口。若仅方法仍有真实选择缺口，可按需读 [方法分流](resources/method-selection.md) 并将范围变化报告协调者。任务级范围、授权与交付由协调者持有，局部编排须明确授权。
</SUBAGENT-STOP>

用户的一句话通常给出目标，不会附带正式规格。先从仓库现状、真实调用方、已确认规则和当前授权还原**想得到的结果**；不要从“修复、加上、调查”等动词直接推导固定流程，也不要为了使用某方法先生产它的前置文档。

## 选择当前最短路径

| 会使下一步走错的缺口 | 当前行动 | 何时继续或停下 |
|---|---|---|
| 缺少只能由用户决定、会改变行为或验收的业务取舍 | 只澄清该决定，保留已经明确的部分 | 决定已有权威来源时直接沿用，不反复询问 |
| 缺少真实调用方、根因、外部契约或可行性事实 | 取能改变下一步选择的最小证据；相邻方法难区分时再读 [方法分流](resources/method-selection.md) | 事实足以回答或实施时结束调查 |
| 目标、约束、接缝和授权已足够 | 直接实施、检查或回答 | 在真实使用路径核对结果；不为直接行动补规格或仪式 |
| 选定路线跨单元、风险高或难以回退 | 记录必要的选择、依赖、风险和验证安排 | 新增高风险或难回退动作先确认，计划不替用户授权 |
| 最终结论还缺覆盖或独立视角 | 补当前风险的直接证据；评审只交独立于实现的人或代理 | 声明与证据相符时停止追加 |

同一措辞可有不同路径：“加订单号筛选”若现有接口和语义已知就直接实现；若订单号含义或服务契约未知，先确认会改变行为的那一项。“修复上传取消后提示成功”已有症状，先沿真实取消路径定位错误；不能用某个猜测性延迟取代根因证据。

## 转换与边界

讨论、调查、设计、作业、验证和评审是可选的工作视角，不是必须依次走完的阶段。调查与实施属于同一个已授权请求时，事实确认后可直接继续实现；新事实改变用户可见行为、公共契约、架构边界、风险、范围、授权或副作用时，暂停受影响路径，关键取舍或高风险/难回退新动作先交用户确认。用户纠正目标时，复查从原始请求以来的实现、测试与文档，撤回依赖旧假设的内容。

- 调查输出可追溯事实及未决边界；不能把建议伪装成已授权修复。具体方法或证据仍有选择缺口时按需读取 [方法分流](resources/method-selection.md)，已有事实充分时直接行动。
- 验证从真实消费路径取证，测试期望独立来自需求、调用方或契约；不从待写实现镜像断言，也不为测试增加不必要的生产接口或开关。替身只隔离真实外部边界，已由类型证明的约束不再镜像测试。
- 工作路径不扩大授权。合并、发布、部署、正式环境改动、权限变更、外部消息、流量调整、破坏性清理及其他高影响操作需要明确授权；正式环境数据源禁止写入。保留用户和其他任务的改动。
- 开发成果通过验证和适用评审后，用户未收窄时默认按仓库约定创建或使用分支、提交、推送并发起 MR/PR；由 [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md) 核对实际远端、交付状态和最终提交的 CI。用户明确限制本地/提交/推送/PR 时逐项遵守；只读调查结论不自动触发 Git 交付。完成声明由 [verification-before-completion](../verification-before-completion/SKILL.md) 核对实际证据。
