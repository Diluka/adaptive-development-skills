# 作业（实现）节点决策规则

Use when 完成具体工作（写代码、写正文、调配置、做调研等），判断需求边界、直接干
vs 先设计、选择开发方式。

## 判据一：需求边界的清晰度

- **边界明确**（常受既有设施隐性限制）→ 直接动手。
- **边界模糊**（如「做一个淘宝」）→ 先讨论，明确功能界限 / 开发界限。

## 判据二：直接干 vs 先设计（复杂度）

- **新业务开发** → 先设计：较大、后续需验证 / 评审，没有文档就没有评判标准。
- **简单变更** → 直接干：简单验证即可保证效果，写设计是形式主义。

## 开发方式选择（看任务、不互斥）

| 方法     | 适用场景                                           | 说明                                                                                                                                          |
| -------- | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **BDD**  | 需求没有明确具体设计                               | 写实现 + 写测试，最好全链路 e2e，以可执行行为表达用户需求，见 [behavior-driven-development](../../../behavior-driven-development/SKILL.md)    |
| **SDD**  | 有 / 会产生规格文档（明确触发信号）                | 规格详细利于单元测试；因规格是高标准正式文档，SDD 在自主决策时不常见，见 [spec-driven-development](../../../spec-driven-development/SKILL.md) |
| **TDD**  | 行为单一的小功能（bug 修复、函数开发 / 重构）      | 用例即设计 + 验证，节约设计与验证；大功能会边界重叠、冗余分支，见 [test-driven-development](../../../test-driven-development/SKILL.md)        |
| **维护** | 删除死代码、适配器、导出、依赖或升级依赖等维护变更 | 见 [maintenance-operations](../../../maintenance-operations/SKILL.md)                                                                         |

执行形态见 [execution](../../../execution/SKILL.md)。

## 类型驱动设计方式叠加

- 稳定领域状态、公共
  API、协议阶段、权限或单位能由类型系统显著排除非法组合，且类型建模本身构成独立目标和证据边界时，叠加
  [type-driven-design](../../../type-driven-design/SKILL.md)。
- 类型驱动设计与开发方式正交；外部
  JSON、HTTP、数据库或用户输入解析前仍不可信，保留运行时解析与边界验证。

## 写文档类 / 操作类作业

- **写文档类**：记录 / 总结（内容已存在）→ 直接写 + 事实准确性核对；说明 /
  指南（说明已有系统）→ 先调查后写 + 对照验证；规划 / 设计（内容不存在）→
  属设计节点本身。
- **操作类**：核心风险是副作用与可逆性。影响小、可逆 → 直接操作 +
  验证；影响大、难回退 → 先设计 → 干跑预览（dry-run / plan）→ 执行 →
  验证，必要时评审；操作不确定 → 先调查。
