# 评审节点决策规则

Use when 判断是否需要评审（整体审视某件事是否做得对），以及评审与验证的边界。

## 何时需要评审（判据 = 复杂度 / 风险）

- **新业务 / 复杂任务**：需要评审。
- **简单变更**：不需要，验证即可保证效果。
- 已有证据覆盖同一风险或独立视角无实际收益时跳过。
- 复杂 / 高风险任务要求独立评审。

## 评审触发

- **独立功能**：评审兼容性——是否引入破坏性导致副作用。
- **高危操作**：难以 / 无法撤销，需非常谨慎的验证，必要时用户二次审核。
- **改动较大**（范围或行数）：相对需求出现较大改动可能跑偏——需审，可能需纠正或从头审视。

## 评审与验证区分

- **验证** = 有既定对照的核对（实现是否符合设计）。
- **评审** = 无固定对照的整体审视（是否值得交付、是否是用户想要的）。
- 评审靠「看」，产出结论 +
  是否返回纠正的反馈回路；验证靠「做」（运行、执行、编译、测量）。

## 独立性（硬约束）

- 实现代理不能自己审自己，评审必须分离（可都是子代理，可一主一子，不能是同一个）。
- 评审花了时间 / token 就要有意义，没有真正独立视角时不如省略。
- 可对已存在的东西直接给意见（如 code review 他人分支），只给意见不改动。
