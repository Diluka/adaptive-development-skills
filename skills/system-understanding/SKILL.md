# System Understanding：理解与审查现有系统

## 核心原则

从具体问题出发建立可追溯的系统模型，不按目录罗列文件，也不用惯例、偏好或抽象程度代替具体事实。先还原真实系统，再提出或评价目标设计；结论必须能追溯到当前源码、装配、版本、真实调用方与运行证据。本技能只交付事实模型与决策输入，不把结论实现为项目差异。

## 建立事实基线

1. 明确待回答的问题或待决定事项、受影响边界、已知约束和不可改变的行为。
2. 确认研究所针对的仓库、分支或提交和适用配置；从公共入口与真实调用方沿控制流和数据流追踪。
3. 核对真实运行行为、已实施契约、当前配置与既有设计决定；文档、类型和注释与运行证据冲突时，显式记录差异。
4. 分开已确认事实、证据支持的综合、待验证假设和真正未知；不把理想目标倒推为当前现状。

外部 SDK、框架、协议或服务契约不确定，或者技术可行性或性能仍未知时，把未知事项返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md)，分别拆成 [contract-verification](../contract-verification/SKILL.md) 或 [unknown-exploration](../unknown-exploration/SKILL.md) 调查单元，再把所得证据用于理解与审查。

## 选择研究模式

| 模式 | 适用问题 | 主要结果 |
|---|---|---|
| 地图 | 仓库由什么组成、主要入口和边界在哪里 | 子系统职责、公共入口、装配关系、关键运行流、存储与外部边界 |
| 专题研究 | 某个功能、概念或机制到底如何工作 | 从入口到副作用的纵向切片、必要机制、状态与所有权 |
| 演进 | 现在为何如此、何时改变、旧行为与当前行为有何差异 | 当前基线、关键变更、版本差异及有证据支持的原因 |
| 架构审查 | 职责、所有权、生命周期、状态边界或不变量存在待决取舍 | 备选方案比较与可追溯的决策依据 |

## 追踪当前系统

1. 从公共导出、HTTP 或消息入口、CLI、启动流程、计划任务和后台消费者中定位真实入口；优先使用仓库已有语义索引或调用图，再用源码搜索补足动态路径。
2. 检查入口如何被装配：模块注册、依赖注入、路由、插件、生成代码、配置与功能开关可能决定哪个实现实际可达。
3. 沿编排进入领域规则，记录关键输入、状态转换、不变量、错误与返回路径，以及职责由哪个模块或进程拥有。
4. 继续追到持久化、事务、缓存、事件发布与消费、后台任务、重试和最终副作用；只展开与问题相关的分支。
5. 标出外部服务、SDK、框架和协议边界及项目实际使用的版本。真实契约仍不确定时，把该未知返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md)，拆成独立的 [contract-verification](../contract-verification/SKILL.md) 调查单元。
6. 从可观察副作用、反向调用方、代表性测试或运行时产物交叉核对主路径，主动寻找能推翻当前模型的分支。

动态分派、反射、代码生成、约定式加载和部署配置可能让静态调用图不完整。找不到直接调用者时先检查这些机制，不把静态不可见等同于不可达。

## 建模架构

只对影响当前决定的部分建模：

| 维度 | 需要回答的问题 |
|---|---|
| 稳定概念 | 哪些业务或系统概念会长期存在，哪些只是当前实现细节？ |
| 职责与所有权 | 谁创建、修改、持久化和销毁对象或状态，谁是唯一事实来源？ |
| 生命周期 | 初始化、激活、转换、停止、释放和恢复在哪个边界发生？ |
| 状态边界 | 哪些状态属于内存、持久层、派生结果或外部系统，如何保持一致？ |
| 不变量 | 哪些条件始终必须成立，由哪个边界强制？ |
| 数据流 | 数据如何从入口经过编排、变换和持久化到达副作用与可观察输出？ |

用这些模型比较备选方案，检查是否减少重复状态、隐式时序、双重所有权和穿透抽象，而不是追求层数、模式或统一命名。

## 检查适用风险

先从真实调用、部署和状态模型判断风险是否存在，再检查对应设计，不无条件套用分布式系统清单：

- 操作可失败或部分成功时，检查错误语义、重试边界、幂等性和补偿或恢复路径。
- 存在多进程、多实例或异步并发时，检查协调、顺序、重复处理与一致性假设。
- 存在持久化或长生命数据时，检查模式演进、中断后恢复、迁移和旧数据兼容。
- 公开 API、框架扩展点或跨版本使用方受影响时，检查向后兼容、升级路径和失败的可诊断性。
- 运行故障需要被发现或定位时，检查关键状态转换、错误与关联标识是否可观察。

## 研究历史演进

以当前可达实现为基线，使用 `git log`、`git log -S` 或 `-G`、`git blame`、`git show`、标签、发布说明和迁移记录定位关键变化；遇到移动或重命名时跟随文件历史。围绕行为、契约、所有权或数据模型的差异选择提交，不输出无关的提交年表。

提交内容可以证明“改了什么”，提交信息、关联决策或问题记录才可能解释“为什么”。原因没有直接证据时标为综合或未知；不要从作者、时间接近或最终代码反推意图。

## 形成结论

交付能直接支持决策的结论：

1. 推荐方案及其对应的事实、约束和关键不变量；
2. 当前范围内的主要取舍，包括获得的性质与承担的成本；
3. 被否决的真实备选方案及其不适用原因，不凑虚假选项；
4. 对调用方、公开契约、数据、部署、运维和后续实现的实际影响；
5. 仍未确认的假设、决策点和获得下一份证据的最小动作。

专题需要教学式展开时，提出源码正在回答的问题、给出能解释主路径的最简单模型、找出会破坏模型的真实约束、说明代码为这些约束引入的必要机制，并用一次具体运行流串起入口、状态变化和副作用；只解释当前问题实际涉及的层次，不虚构抽象、意图或设计理由。

按证据强度区分结论：已确认事实、证据支持的综合、假设、门控行为和缺失实现，各自给出精确来源、推导关系、缺口或排查范围；源码注释、测试和文档都是线索但可能过时，运行时证据可以纠正静态推断。

## 边界与衔接

- 关键业务选择、成功标准或互斥设计方向未定时，使用 [brainstorming](../brainstorming/SKILL.md) 只澄清会改变方案的决策。
- 不强制特定命名、设计模式、新抽象或通用化；当前设计不需要它们时保持简单。
- 默认只交付研究或审查结论，不自动创建设计文档或实施代码；需要长期保留时使用 [project-documentation](../project-documentation/SKILL.md)。
- 任务包含正式实施时，形成足以支撑决定的结论后停止，把结论返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 重新分级并选择开发方式；本技能不继续实施，也不代替最终差异适用的 [requesting-code-review](../requesting-code-review/SKILL.md)。
