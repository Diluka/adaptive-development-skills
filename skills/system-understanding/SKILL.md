# 理解与审查现有系统

## 核心原则

从具体问题出发，建立能追溯到当前源码、装配、版本、真实调用方与运行证据的系统模型。先还原系统实际如何运作，再提出或评价目标设计；目录、惯例、偏好和抽象程度都不能代替事实。

本技能只交付事实模型和决策输入，不直接把结论变成项目差异。

## 建立事实基线

研究时先厘清以下事实：

- 待回答的问题或待决定事项，以及受影响边界、已知约束和不可改变的行为。
- 所研究的仓库、分支或提交和适用配置；从公共入口与真实调用方沿控制流和数据流追踪。
- 真实运行行为、已实施契约、当前配置与既有设计决定；文档、类型或注释与运行证据冲突时，显式记录差异。
- 已确认事实、证据支持的综合、待验证假设和真正未知；不要把理想目标倒推为当前现状。

外部 SDK、框架、协议、服务契约、技术可行性或性能成为独立未知时，把问题及证据缺口返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 拆成调查单元，再由 [execution](../execution/SKILL.md) 选法。取得证据后，再用于理解和审查。

## 选择研究模式

| 模式 | 适用问题 | 主要结果 |
|---|---|---|
| 地图 | 仓库由什么组成、主要入口和边界在哪里 | 子系统职责、公共入口、模块与依赖关系、装配关系、关键运行流、存储与外部边界 |
| 专题研究 | 某个功能、概念或机制到底如何工作 | 从入口到副作用的纵向切片、必要机制、状态与所有权 |
| 演进 | 现在为何如此、何时改变、旧行为与当前行为有何差异 | 当前基线、关键变更、版本差异及有证据支持的原因 |
| 架构审查 | 职责、所有权、生命周期、状态边界或不变量存在待决取舍 | 备选方案比较与可追溯的决策依据 |

## 追踪当前系统

1. 从公共导出、HTTP 或消息入口、CLI、启动流程、计划任务和后台消费者中找到真实入口。优先使用仓库已有语义索引或调用图，再用源码搜索补足动态路径。
2. 查看入口如何装配。模块注册、依赖注入、路由、插件、生成代码、配置和功能开关都可能决定哪个实现实际可达。
3. 沿编排进入领域规则，记录关键输入、状态转换、不变量、错误和返回路径，以及由哪个模块或进程拥有职责。
4. 继续追到持久化、事务、缓存、事件发布与消费、后台任务、重试和最终副作用；只展开与问题有关的分支。
5. 标出外部服务、SDK、框架和协议边界及项目实际使用的版本。真实契约仍不确定且已形成独立证据边界时，把该未知返回 Workflow 拆成调查单元，再由 Execution 选法。
6. 用可观察副作用、反向调用方、代表性测试或运行时产物交叉核对主路径，并主动寻找能推翻当前模型的分支。需要运行时证据时，优先用最小、可逆的只读观测来源交叉核验主路径：只读日志、APM 跟踪、指标、只读数据库快照、已部署镜像和下游响应；观测不写入、修改或迁移正式环境数据源。

测试断言是理解当前契约与意图的入口：它们说明现有调用方如何使用系统、系统承诺什么行为。遗留行为难以从静态代码判读时，可用特征测试基线记录当前实际行为作为对照。

动态分派、反射、代码生成、约定式加载和部署配置都可能让静态调用图不完整。找不到直接调用者时，先检查这些机制；静态不可见不等于不可达。

## 建模架构

只为影响当前决定的部分建模：

| 维度 | 需要回答的问题 |
|---|---|
| 稳定概念 | 哪些业务或系统概念会长期存在，哪些只是当前实现细节？ |
| 职责与所有权 | 谁创建、修改、持久化和销毁对象或状态，谁是唯一事实来源？ |
| 生命周期 | 初始化、激活、转换、停止和释放在哪个边界发生；失败是否终止当前生命周期，若可恢复由谁在何处恢复？ |
| 状态边界 | 哪些状态属于内存、持久层、派生结果或外部系统，如何保持一致？ |
| 不变量 | 哪些条件始终必须成立，由哪个边界强制？ |
| 数据流 | 数据如何从入口经过编排、变换和持久化到达副作用与可观察输出？ |

用模型比较备选方案，检查是否减少重复状态、隐式时序、双重所有权和穿透抽象；不要为层数、模式或统一命名而建模。

## 检查适用风险

先从真实调用、部署和状态模型判断风险是否存在，再检查对应设计。技术上可能失败本身不构成新增机制的需求；不要无条件套用分布式系统清单。

设计重试、补偿、恢复或中间恢复状态前，先确认异常后仍存活并持有相关状态的主体、实际触发恢复的主体或事件，以及表示恢复完成的可观察结果。任一项未被需求、真实调用方或已核验运行边界确认时，只描述已确认的失败传播或生命周期终止边界，不增加恢复机制、状态或验收项。

- 操作可失败或部分成功时，先确认错误语义和生命周期终点；重试、补偿或恢复只在上述闭环成立时检查，幂等性只在真实重复调用或部分提交风险存在时检查。
- 存在多进程、多实例或异步并发时，检查协调、顺序、重复处理与一致性假设。
- 存在持久化或长生命数据时，检查模式演进、迁移和旧数据兼容；仅在当前范围确有中断后恢复生命周期时检查恢复。
- 公开 API、框架扩展点或跨版本使用方受影响时，检查向后兼容、升级路径和失败的可诊断性。
- 运行故障需要被发现或定位时，检查关键状态转换、错误与关联标识是否可观察。

## 研究历史演进

以当前可达实现为基线，用 `git log`、`git log -S` 或 `-G`、`git blame`、`git show`、标签、发布说明和迁移记录定位关键变化。遇到移动或重命名时跟随文件历史，只选择能说明行为、契约、所有权或数据模型变化的提交，不输出无关年表。

提交内容可以证明“改了什么”；只有提交信息、关联决策或问题记录才可能解释“为什么”。原因没有直接证据时标为综合或未知，不要从作者、时间接近或最终代码反推意图。

## 形成结论

交付能直接支持决策的结论：

1. 推荐方案及其对应的事实、约束和关键不变量；
2. 当前范围内的主要取舍，包括获得的性质与承担的成本；
3. 被否决的真实备选方案及其不适用原因，不凑虚假选项；
4. 对调用方、公开契约、数据、部署、运维和后续实现的实际影响；
5. 仍未确认的假设、决策点和获得下一份证据的最小动作。

专题需要教学式展开时，先提出源码正在回答的问题，再给出解释主路径的最简单模型。找出会破坏模型的真实约束，说明代码为这些约束引入的必要机制，并用一次具体运行流串起入口、状态变化和副作用。只解释当前问题涉及的层次，不虚构抽象、意图或设计理由。

按证据强度标记结论：已确认事实、证据支持的综合、假设、门控行为和缺失实现。分别给出精确来源、推导关系、缺口或排查范围；源码注释、测试和文档都是可能过时的线索，运行时证据可以纠正静态推断。

## 边界与衔接

- 关键业务选择、成功标准或互斥设计方向未定时，把会改变方案的未决项返回 Workflow 插入讨论节点。
- 不强制特定命名、设计模式、新抽象或通用化；当前设计不需要它们时保持简单。
- 默认只交付研究或审查结论，不自动创建设计文档或实施代码；需要长期保留时返回 Workflow 建立开发单元，再由 Execution 选择文档或实施方法。
- 本技能以理解与决策输入为目的；删除、升级等正式维护变更只复用本技能交付的调用方证据，具体开发方法由 Execution 选择。
- 任务包含正式实施时，形成足以支撑决定的结论后停止，把结论返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 建立并分级开发单元，再由 [execution](../execution/SKILL.md) 选择开发方式；本技能不继续实施，也不代替最终差异适用的 [requesting-code-review](../requesting-code-review/SKILL.md)。
