# Delivery：集成、交付与受控发布

## 核心原则

交付由三段能力构成，通常按顺序衔接：主干开发把工作拆成可独立集成的小批次并频繁合入，持续交付让各种变更在整个生命周期保持可发布，渐进式交付对已验证候选版本受控暴露并以真实观测决定扩大或回退。三段能力各自闭环，可以独立建立，但都不能替代功能、契约或质量证据。

## 主干集成（Trunk-Based Development）

围绕一个权威主干组织开发，把工作拆成可独立集成的小批次，直接提交到主干或通过短生命周期变更分支频繁合入。短分支通常以小时计并至少每日合入一次；活跃分支数量、合入频率和代码冻结时间用于发现集成风险，不为满足指标制造无价值提交。

适用前提：已确认权威主干、分支保护、评审规则和必要集成权限；CI 能在足够短的反馈周期内发现当前批次的真实回归；团队能在主干失败时立即修复或回退；目标变化能拆成保持主干可工作、可验证的小批次。不满足前提时，先缩小批次、改善反馈或设计兼容迁移；不把不可安全集成的半成品仅为缩短分支寿命而合入主干。

集成流程：

1. 确认主干、当前分叉、目标 `git remote`、仓库策略和必要门禁。
2. 按可独立观察的行为与兼容边界切分工作；每个批次都应能单独进入主干并保持系统可工作。
3. 按仓库策略选择直接提交主干，或使用由单人或结对拥有的短生命周期变更分支。创建或检出项目改动分支时，隔离位置交给 [using-git-worktrees](../using-git-worktrees/SKILL.md)。
4. 让评审和 CI 紧跟当前小批次，不在等待期间继续把无关工作堆入同一分支。
5. 在最终集成结果上检查 CI；失败时优先修复或回退，恢复主干健康后再继续。
6. 具体分支、提交、推送和 MR/PR 交给 [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md)，按开发任务的普通 Git 交付默认值或用户限制执行；合并与工作树清理分别按其边界处理。

较大变化需要跨批次时，优先采用向前兼容的接口演进、抽象替换或其他安全切片。只有真实发布或隔离需求存在时才增加功能开关，并为所有者、默认行为和清理条件负责；开关不能替代实现证据。

## 持续交付（Continuous Delivery）

让各种变更都能按需、快速、安全且可持续地发布，并在整个生命周期保持软件可部署。Continuous Delivery 不等于 Continuous Deployment：前者建立随时可发布的能力，后者才尝试把每个合格变化自动部署到正式环境。

适用前提：应用、配置、基础设施定义、数据库变更和交付脚本等生产产物有可追溯版本；构建、测试、安全检查和部署步骤能提供与当前风险匹配的快速反馈；候选制品具有稳定身份，环境提升不会重新构建出内容不同的制品；团队能理解运行健康、恢复失败交付并明确各环境授权边界；功能本身已取得适用的实现、契约和安全证据。CI、自动化工具和部署流水线只是必要能力的一部分；单纯提高旧流程的执行频率，或在没有流程、架构与反馈改进时增加工具，不构成持续交付。

建立交付能力：

1. 从一次变化出发，映射版本控制、构建、检查、制品、环境提升、发布和恢复的真实价值流，标出等待、手工交接与权限边界。
2. 让每次集成都产生可追溯的规范构建或制品，并运行能拒绝当前合理错误的检查；不要为填满流水线复制字面量测试。
3. 把不可发布状态作为优先故障处理。失败后先恢复主干和交付链路，再继续堆叠变化。
4. 在环境之间提升同一制品，把环境配置和批准状态与制品身份一并记录，避免环境漂移掩盖真实差异。
5. 在已授权环境验证部署步骤、健康信号和恢复路径；没有部署授权时停在“可发布”，不要把计划或流水线能力描述为已发布。
6. 根据交付时间、失败率、恢复时间、发布频率和部署痛苦持续消除瓶颈，不用单次绿灯证明整体能力成熟。

## 渐进式交付（Progressive Delivery）

在候选版本已经具备开发期证据并达到可发布状态后，通过金丝雀、功能开关、流量分割、地域或用户群分批等机制控制暴露范围，根据真实观测逐步扩大、保持、暂停或回退。观测与决策闭环是本方法核心；只有分批动作而没有判断标准，不构成渐进式交付。

适用前提：候选制品身份明确，已通过与功能风险相称的开发期验证并达到可发布状态；存在能够精确控制用户、请求、地域、实例或功能暴露的机制；能观察用户体验、业务结果与系统健康并有可信基线；继续、暂停、终止和回退条件可在执行前定义；每个远端配置、流量、发布、部署和回退动作都有明确负责人及授权。缺少可观察信号、无法限制暴露范围或没有可执行回退时，先补齐能力或改用更保守的发布安排，不把直接全量发布称为渐进式交付。

交付流程：

1. 固定候选制品、剩余风险假设、目标人群和当前环境，明确本轮最大允许爆炸半径。
2. 选择满足风险控制所需的最小机制。使用开关时明确所有者、默认行为、依赖关系和清理条件。
3. 在执行前定义阶段、群体或比例、观察窗口、基线、成功指标、护栏指标以及扩大、保持、停止和回退阈值。
4. 核对精确环境、当前状态、操作权限和恢复步骤。没有明确授权时，只完成方案和只读核验，不修改正式环境。
5. 对首个受控群体暴露，读取完整观察窗口中的实际信号；证据不足时保持当前阶段，不按预定时间自动扩大。
6. 根据阈值扩大、暂停或回退，并为每次决策记录制品、暴露范围、时间和证据。
7. 达到目标后确认最终暴露状态。临时开关、路由和旧版本清理由独立工作单元处理，继续遵守调用方证明与授权边界。

## 产出证据

- 主干每批次的目标、兼容边界与独立验证结果，分支创建、合入与删除时间，最终主干 CI，失败后的修复或回退结果；
- 持续交付的最终提交或合并结果 CI、制品版本与来源提交、同一制品各环境提升记录、已授权部署后的冒烟与健康结果、交付能力指标变化；
- 渐进发布的精确制品与暴露范围、每阶段基线与观测结果、每次扩大/暂停/回退的阈值判断与负责人、回退或禁用后的恢复结果、最终暴露状态。

## 方法边界

- 本技能决定集成、交付与受控暴露的节奏，不决定功能工作单元的主要开发或证据方法；实现仍按 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 为各工作单元选法。
- 开发任务的分支、提交、推送和 MR/PR 由 [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md) 按普通 Git 交付默认值处理。合并、制品发布、环境变更和部署不在该默认值内；计划、流水线配置或本技能触发都不会把它们纳入范围。
- 功能开关、金丝雀和 A/B 分流是可选机制，不是独立正确性证据，也不应为了人工测试改变产品设计。
- 不可逆数据迁移、公共契约破坏或无法按群体隔离的共享副作用不能仅靠缩小流量解决；先建立兼容迁移、状态边界与恢复方案。
- 完成声明通过 [verification-before-completion](../verification-before-completion/SKILL.md) 核对当前制品、观测、决策与最终状态，不能用开发环境或过时指标代替。
