# Dispatching Parallel Agents：安全并行派发

## 核心原则

并行处理独立且确有并行收益的工作，而不是仅仅因为工作数量多就派发。只有当一个任务的结果不会改变另一个任务的处理方式，而且二者不会通过共享可变状态相互干扰时，它们才真正独立。开发任务中的代理使用同一份计划文档对齐；非开发调查共享同一目标、边界和证据要求，不因使用多个代理就自动转换为开发任务。

## 证明独立性

对每一对候选任务检查：

1. **信息：** 两者能否基于当前已知事实开始，而不需要等待对方的决策或发现？
2. **写入：** 两者是否避开相同文件、生成产物、分支操作、数据库、外部资源、端口和进程状态？
3. **契约：** 两者能否保持共享接口，而不各自发明或修改它们？
4. **完成顺序：** 任一任务先完成是否都不会让另一个任务失效？
5. **集成：** 根代理能否在明确边界上协调并验证两个结果？

任何答案不确定时，就缩小任务、把其中一个改成只读，或改为顺序执行。

## 安全派发

1. 先判断任务类型。开发任务确认已有 [writing-plans](../writing-plans/SKILL.md) 创建的计划文档；非开发调查只需明确共享目标、边界和证据要求。
2. 按独立问题域划分单元，而不是按任意文件数量分组；记录负责人、依赖、独占读写范围、共享状态、预期产物或报告和验证方式。
3. 开发任务给每个代理同一计划文件的精确路径和工作单元标识，跨工作树时传递绝对路径；非开发调查给出同一请求和范围。两者都提供相关证据与约束。
4. 明确告知代理不得继续派生子代理。开发任务中不得并发改写计划文档，只有根代理负责协调和更新；非开发调查由根代理统一汇总共享状态。
5. 只有节约的时间或上下文明显大于派发、协调和集成成本时才并行；即使两个单元独立，也可以顺序执行或由根代理直接完成。
6. 代理返回后，检查实际文件和证据，排查隐藏重叠，并在接受组合结果前运行集成验证。开发任务把新事实与状态写回计划；非开发调查把结论统一汇总到共享请求或对话状态。

当更广泛的委派执行中同时包含顺序任务时，使用 [subagent-driven-development](../subagent-driven-development/SKILL.md)。当看似独立的症状可能共享同一根因时，先使用 [systematic-debugging](../systematic-debugging/SKILL.md)。

## 边界

- 绝不并行编辑同一文件、锁文件、生成产物、迁移序列或共享外部状态。
- 只有数据源稳定且查询不会产生写入时，才能并行执行只读调查。
- 子代理即使发现了额外工作，也不得再派生代理；应把工作报告给根代理。
- 存在计划文档时，不得让多个代理各自维护副本或同时编辑同一计划文件。
- 除非目标就是独立对照，否则不要让多个代理重复同一调查。
- 并行完成不能替代结果集成和验证；若属于开发任务，也不能替代最终独立子代理评审。

## 示例

API 契约审计和日志证据盘点可以作为非开发调查并行，只要结论互不依赖、并行确有收益；它们不因此需要开发计划。两个修复如果都会修改同一个客户端接口和包锁文件，就不独立；应先确定接口，再顺序执行，并对最终开发差异统一评审。

## 常见错误

- 只数任务数量，不检查写入集合或决策依赖。
- 只因存在两个独立单元就并行，不比较协调成本与实际收益。
- 为非开发调查使用多个代理，就错误创建开发计划或正式实现流程。
- 假设不同目录就代表运行时契约独立。
- 授权多个代理修复同一个失败。
- 让子代理在根代理不可见的范围内继续扩散派发。
- 不检查共享仓库状态就直接合并多个摘要。
