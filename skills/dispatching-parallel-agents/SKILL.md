# Dispatching Parallel Agents：安全并行派发

## 核心原则

只有工作单元可安全隔离且并行收益高于协调成本时才并行。收益可以来自缩短等待时间，也可以来自在不互相锚定的情况下形成独立实现或证据。工作数量多不代表适合派发；即使可以并行，也允许顺序协作或由协调者完成。并行不改变开发任务判定，独立性判断也不预先决定使用子代理还是独立工作任务。

## 证明独立性

对每一对候选单元检查：

1. **信息：** 都能基于同一已确认目标和当前事实开始，不等待对方决策或发现；需要独立对照时，在回报前不读取对方结论；
2. **写入：** 不共享文件、生成产物、分支操作、数据库、外部资源、端口或进程状态；
3. **契约：** 共享接口与评价边界已经固定，不会各自发明或修改；
4. **顺序：** 任一先完成都不会使另一项失效；
5. **集成：** 根代理能在明确边界上组合并验证结果。

任一答案不确定时，缩小任务、把一方改成只读，使用隔离工作树，或顺序执行。实现完成后才能取得稳定输入的测试或评估不应伪装成并行单元，但仍可以由不同代理顺序协作。

## 实现与验证双轨

计划已经固定目标行为、真实入口、共享契约和评价边界时，可以把生产实现与独立验证作为常见的并行组合。实现者只拥有约定的生产文件，验证者只拥有约定的测试、夹具或评估产物；验证预期必须来自共同输入，不得从实现者的中间代码或结论反推。

验证工作只有在所需需求、接口、模式、夹具和可观察结果已经稳定时才能并行设计与编写。测试需要实现探索生成接口、模式、快照或其他稳定输入时，改为顺序协作。

两条轨道共享一个工作区时，一方运行测试期间另一方仍在改变被测状态，所得中间结果不稳定，只能用于局部反馈。协调者必须在双方停止写入后的组合状态重跑验证；若测试准备、生成产物、端口、进程或外部资源无法隔离，使用独立工作树与独立运行资源，或者取消并行。

## 派发与集成

先定义负责人、角色产出、读写范围、预期结果、证据和验证。能在当前 Codex 任务内闭环的单元使用 [subagent-driven-development](../subagent-driven-development/SKILL.md)；用户已明确授权跨会话执行，且单元需要独立长上下文、工作区或恢复生命周期时，使用 [orchestrating-multi-session-work](../orchestrating-multi-session-work/SKILL.md)。两种方式都只保留一个协调者，不允许执行者递归创建同层级工作。

有落盘计划时执行者读取同一计划或其不可变单元快照；没有计划的开发任务和非开发调查共享同一目标与证据边界，不因多代理或多会话协作而转换任务类型或自动升级流程。

协调者检查执行者返回的实际文件和证据，排查隐藏重叠，再运行组合验证。适用时同步计划，并按任务级别或具体风险决定最终独立评审；非开发调查统一汇总结论。

## 边界

- 不并行编辑同一文件、锁文件、生成产物、迁移序列或共享外部状态。
- 只读调查只有在数据源稳定且查询无写入时才能并行。
- 症状可能共享根因时先用 [systematic-debugging](../systematic-debugging/SKILL.md)，不要授权多个代理同时试修。
- 多个代理不得各自维护计划副本，也不得无目的重复同一调查；若目标就是独立对照，根代理必须预先固定共同输入、评价边界和回报格式，并在结果返回前保持判断隔离。
