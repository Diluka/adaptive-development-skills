# Finishing a Development Branch：安全交接分支

## 核心原则

明确决定分支集成和清理方式。完成实现不会自动授权拉取、推送、合并、删除分支或移除工作树。

## 确认当前状态

提出操作前先检查：

```bash
git status --short --branch
git branch --show-current
git remote -v
git worktree list --porcelain
```

根据仓库说明、跟踪关系和用户意图确定目标分支，不要从硬编码名称猜测。随后获取完整集成范围：

```bash
git merge-base HEAD <target-branch>
git log --oneline --decorate <merge-base>..HEAD
git diff --stat <merge-base>..HEAD
```

确定目标分支、合并基点、未提交改动、待集成提交、远端跟踪状态，以及当前工作区是否为关联工作树。使用 [verification-before-completion](../verification-before-completion/SKILL.md) 确认最终差异的最近一次相关验证、独立子代理评审，以及评审后是否又产生项目产物变更。

本次范围内的未提交改动不属于 `<merge-base>..HEAD`，也不会进入 PR/MR、推送或合并结果。在用户另行明确授权并完成提交前，不得创建 PR/MR、推送、合并或声称分支已就绪；可以先预览交接内容。无关未提交改动继续保留。

每个开发任务都必须通过 [requesting-code-review](../requesting-code-review/SKILL.md) 完成最终独立子代理评审；风险只决定评审深度和是否增加专项评审者。主代理自查、PR/MR 评审或运行时验证不能替代这一状态。评审尚未完成，或评审后又修改了准备交付的项目产物却未重新验证和复审时，不要把分支描述为已就绪。

只执行已经完成开发的提交、推送、PR/MR、部署或其他交付操作，不会因此创建新的开发任务，也不需要重复独立评审。但交付前一旦再次修改项目产物，就必须重新验证并评审新的最终版本。

区分此分支引入的失败和已确认的基线失败。必需的相关检查仍失败时，不要声称已就绪。

## 提供真实可用的选项

只提供当前适用的选择：

1. 保留分支和工作树，稍后继续。
2. 准备 PR/MR，或在明确授权后创建 PR/MR；内容包含分支、目标、差异范围、验证和风险。
3. 用户明确要求时推送分支。
4. 仓库策略、必需验证和开发任务最终独立评审已满足，且用户明确要求时执行 Git 合并。
5. 集成完成且确认没有未提交工作后，在用户明确授权下移除工作树或分支。

说明每个选项会造成哪些外部变更。用户只要求检查就绪状态，并不授权上述修改。

## 精确执行

- 按当前仓库工作流准备或创建 PR/MR；不要硬编码托管平台专用 CLI、API 或字段。
- 措辞重要时先预览标题、正文与目标分支。
- 交接前不要自动拉取或变基；先展示分叉情况并解释其影响。
- 未经明确范围，不得强制推送、破坏性重置、宽泛删除分支或移除工作树。
- 执行后验证已创建的 PR/MR、Git 状态、推送、合并或清理结果。

存在无关未提交文件时保留它们。绝不要只为制造整洁结束状态而清理或暂存这些改动。

## 示例

功能工作树准备交接时，报告分支、目标、完整提交范围、状态、定向验证和必需审查状态。询问是保留、创建 PR/MR 进入审查，还是在条件满足后执行 Git 集成。只有集成完成且用户明确授权清理后，才移除精确工作树和分支。

## 常见错误

- 测试通过后自动拉取、推送、合并或删除。
- 交接前隐藏未提交改动。
- 从硬编码名称猜测目标分支。
- 要求在本分支内修复无关的失败测试套件。
- 开发任务的最终独立评审尚未完成，或评审后差异又变化，就提供直接合并。
- 因交付操作本身不是开发任务而忽略它所交付版本原有的验证或评审缺口。
- 未验证提交和未提交状态可恢复就移除工作树。
