# Finishing a Development Branch：安全交接分支

## 核心原则

开发任务和准备正式纳入版本控制的项目变更，在通过适用验证与评审后，默认完成普通 Git 交付：创建或使用合适分支、提交、推送，并根据目标仓库实际的 `git remote` 在 GitLab 创建 MR 或在 GitHub 创建 PR。普通 Git 交付完成不等于合并、发布或部署。

用户明确要求仅修改本地、只提供差异、不提交、不推送或不创建 MR/PR 时，按限制逐项取消相应动作及其依赖的后续动作。合并、创建版本发布、发布制品、部署、正式环境写入、权限修改、破坏性 Git 和其他高影响外部操作仍需用户明确要求。

## 确认状态

```bash
git status --short --branch
git branch --show-current
git remote -v
git worktree list --porcelain
```

根据仓库说明、跟踪关系和用户意图确定目标分支，不从硬编码名称猜测。通过 `git remote` 中目标远端的实际 URL、上游关系和仓库配置判断 GitLab 或 GitHub。存在多个远端时，先确定本任务真正交付的目标，不根据任意一个远端猜测平台。

已有有效基点时获取完整集成范围：

```bash
git merge-base HEAD <target-branch>
git log --oneline --decorate <merge-base>..HEAD
git diff --stat <merge-base>..HEAD
```

确认目标、基点、待集成提交、未提交改动、远端跟踪和工作树关系。使用 [verification-before-completion](../verification-before-completion/SKILL.md) 核对当前增量的相关验证、CI 与适用独立评审。后续变化只有影响既有结论或风险面时，才使对应就绪证据失效；重新检查受影响范围，不从头重复完整任务。

范围内未提交改动不会进入提交、PR/MR、推送或合并结果。用户限制使某一步未执行时，准确报告本地与远端分别包含什么，不得声称未执行的内容已经交付。只执行已完成开发的交付操作不会创建新开发任务或重复评审，但原版本仍适用的必要验证和评审缺口会阻止就绪。

## 处理同步与冲突

把同步或冲突解决作为当前增量单独定级，不继承整个分支或 PR/MR 的复杂度。先列出实际冲突文件、双方语义、目标分支新增内容和受影响风险面：

- 机械文档或元数据冲突只需审阅解决差异、确认没有冲突标记，并在推送后查看对应 CI；不重跑原功能的完整回归或重新评审未变化代码。
- 运行代码、公共契约、依赖或生成结果发生重叠时，只让相关证据失效，运行覆盖该交互的定向检查；影响复杂或高风险边界时再升级评审。
- CI 已在最终提交上覆盖相同检查时不重复本地执行；CI 未覆盖、推送前反馈价值明显或失败成本较高时补最小定向检查。

## 确定交付结果

1. 开发任务默认在合适分支上只暂存范围内文件，创建符合仓库约定的提交，推送目标远端，并在 GitLab 创建 MR 或在 GitHub 创建 PR；内容包含目标、差异、验证和风险。
2. 分支前缀、提交约定、目标分支、Draft/Ready、指派、模板和必要检查都以目标仓库现有规则为准，不把一个仓库的习惯泛化到其他项目。
3. 用户要求仅修改本地或只提供差异时停在对应本地状态；要求不提交、不推送或不创建 MR/PR 时，保留仍允许的上游步骤并清楚报告停止位置。
4. 仓库策略、必要验证和适用独立评审满足且用户明确要求时才合并。创建版本发布、发布制品、部署、正式环境写入、权限修改和其他高影响外部操作同样不属于默认 MR/PR 交付。
5. 集成完成、没有会丢失的未提交工作且用户要求清理时，才移除精确工作树或分支。

## 精确执行

- 遵循当前仓库工作流和实际 `git remote`，不硬编码托管平台专用 CLI、API 或字段。
- 措辞重要时先预览 PR/MR 标题、正文和目标分支。
- 不自动拉取或变基；先展示分叉及影响。
- 只暂存和提交当前任务文件；保留用户及其他任务的改动。
- 不使用强制推送，不执行破坏性重置、宽泛删除分支或移除工作树。
- 执行后验证实际 PR/MR、Git 状态、推送、合并或清理结果。
- 保留无关未提交文件，不为制造整洁状态而清理或暂存。
