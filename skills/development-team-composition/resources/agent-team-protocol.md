# 代理团队协议

Use when 用户明确要求代理团队协作，需要从运行时能力核验与组建开始，维护任务状态、同层通信和交接。开团准入、人数与角色边界见 [主技能](../SKILL.md)；仅在当前运行时许可时创建成员。

## 创建成员

- 先核验当前运行时的持久成员、身份寻址、共享任务、同层通信、事件汇报与唤醒、权限和回收能力，以及上下文与模型配置的继承规则；不把工具名称相似当作能力相同，也不假定能逐成员配置模型或结束、移除成员。
- 缺少所选协作方式必需的能力时，说明具体限制与受影响工作，不能把一次性子代理称为团队。可以提出由负责人协调独立子代理或串行执行的替代方式；用户明确要求团队时，由负责人向用户确认是否接受降级，不静默替换。
- 按主技能的 [成员契约](../SKILL.md#成员契约) 创建成员，给出明确产物、授权读写范围和输入定位；人数与角色安排沿用主技能，不因运行时提供更多实例容量而扩大团队。
- 负责人直连同层成员，不另设管理层；助理在已定需求、范围与授权内细化任务、派发跟进、回收验收。能交成员的执行交成员，负责人保留需求、范围、授权、关键取舍与最终责任，只执行不可替代的用户沟通、决策和专属权限动作。
- 角色授权不扩张工具权限。助理准备精确操作对象、变更与依据，交有权限的成员办理；确实仅负责人能执行的动作才交负责人，不为回避这些动作另造转手流程。权限不足时如实报告限制，不绕过。

## 工作区与并行

- 派发前按主技能的 [跨角色事项](../SKILL.md#跨角色事项) 确定串并行与隔离安排，明确写入面、共享生成物与运行资源；接受可控轻微冲突时，指定集成与验证责任。
- 确需独立工作树时，按需隔离的任务状态分配工作树与分支，不按成员永久建树；创建、进入或复用不要求新会话。
- 新建工作树而用户或仓库未指定位置时，默认放在根工作树下的 `<repo>/.worktrees/<name>`。先核对当前分支与未提交改动；改动归属不明时停止自动迁移并报告，不用隐式 stash 或临时提交制造干净状态。创建失败时报告准确错误，不用 `--force`、分支重置或删除其他工作树绕过。
- 每个工作树有独立的工作目录、索引与检出状态，但仍共享分支与远端引用、对象库、仓库配置与钩子、`refs/stash` 和工作树注册信息。端口、进程、数据库与外部服务不会自动隔离，须另行协调；语义、契约及前置产物依赖也不会因建树而消失。

## 任务与就绪

- 团队模式下，先让既有任务承接负责人自动目标中的目标、范围、验收、进度与恢复信息，再按当前运行时能力清除或停用自动目标机制，并核验结果。不并存另一套驱动负责人自动续跑的目标，也不另建平行账本；未完成目标不能标为完成来冒充清除。
- Issue 可选，按实际信息与追踪收益选择，不因已有托管平台或需求模糊自动创建；一个 Issue 可关联多个有真实依赖的任务，不强制与看板任务一一对应。
- 若使用 Issue，由其承载详述，看板保留来源定位、就近执行指引与当前修正，不复抄全文；未使用时，看板完整承接任务内容。Issue 与看板冲突时，以看板当前有效指引为执行权威，但仍服从已定需求与授权；影响这些边界的取舍交负责人确认。
- 看板记录唯一任务所有者、依赖、执行目录及适用的分支与基线、写入范围、状态、产物与证据定位。可领取、已指派或已认领、执行中、自报完成与任务验收是不同事实；写入范围声明和重叠警告不是文件锁。
- 已确定部分足以形成边界与验收时，助理即可细化成可指派任务；真实输入就绪即可开发，不等待全部需求谈完或额外批准词。只把影响当前任务的需求缺口交负责人澄清，不暂停无关任务。
- 派发前区分**产物前置**与**共享写入或运行资源约束**：前者指向所需产物及其唯一所有者，记录可用的交接提交或产物版本，只阻塞实际依赖它的任务；后者标明需互斥的部分，由助理在已定范围内协调，按 [工作区与并行](#工作区与并行) 落实执行约束。公共产物不是共同写入面，也不设所有公共任务完成后全队才开工的总闸门。
- 指派、认领或更新状态前读最新任务与依赖，按运行时支持的原子方式确立唯一执行者，并核对返回的所有权与状态；冲突时重读实际进展与依赖再决定下一步，不用旧状态盲目重试或重复执行。
- 已认领任务可能不再显示可领取，但仍在正常执行，不因此重新认领。后继实际就绪并开工前，核对所需输入及约定版本已在其执行目录可见；上游完成或账本自动解锁不等于输入已经到位，独立工作树之间也不自动传递产物。任务就绪或指派本身不等于成员已被唤醒。

## 通信、等待与交接

- 成员可向需要该信息的同层成员直接发送新事实、已确认契约、阻塞与交接请求；只有共同输入或边界变化才同步所有受影响成员。一般执行协调交助理，需求、范围、授权或关键契约取舍交负责人确认。
- 使用当前运行时已核验的自动事件汇报与唤醒机制接收进展、跟进任务；需要成员继续工作时派发明确指引，事件到达后核对最新看板与实际产物。消息确认投递不代表已处理，持久排队不要求重复发送；成员空闲不代表任务完成或失败。
- 打断当前轮次、取消任务与结束成员分别核验实际效果。故障转移或改变写入面前，确认旧执行者及相关在飞工作已停止写入，对账实际差异、产物、证据、未完事项与外部副作用，再更新唯一所有者和成员契约；无法确认停止时先报告阻塞，超时或缺少回报不授权另一执行者重复执行。

## 回收与集成

- 成员交接可验收批次，或任务完成、失败、取消、无法自行解除阻塞时，向助理或任务指定的交接对象回报实际产物、交接提交或产物版本、证据、未完事项及写入状态；成功摘要不证明任务完成。
- 助理在已定范围内按依赖小批接收已固定版本的成果，核对实际差异和输入版本，组织受影响接缝验证；记录哪些输入已在下游执行目录可见，再派发相应后继，不等所有任务结束才首次集成。
- 收齐必需任务终态回报并确认所有写入停止后，仍须验证最终稳定组合、排查隐藏重叠并完成任务验收；助理可组织执行与验收，负责人保留最终对外责任。
- 授权范围内，成员可在独立工作树的任务分支本地提交，供接收与集成；局部提交不是最终验收，也不自动获得推送或创建 PR/MR 的授权。
- 共享工作树的 Git 写入、集成与对外交付统一协调、串行执行；完成所需验收与独立评审并得到明确交付授权后，可指定成员执行交付，不要求负责人亲自操作。负责人仍保留最终责任，成员不另设交付轨道。
- 实际提交、推送、PR/MR 与 CI 等待范围沿用 [根入口](../../adaptive-development-workflow/SKILL.md#交付动作按可逆性决定)、[交付分支](../../finishing-a-development-branch/SKILL.md) 与用户授权。团队协作不增加任务范围或交付动作，合并、发布、部署、正式环境写入与权限修改不因协作而获得授权。
- 任务验收与独立评审分别记录，独立资格按 [主技能](../SKILL.md#成员) 核对；成员续领、兼任与职责延续沿用 [成员增员与角色再分配](../SKILL.md#成员增员与角色再分配)。涉及任务或写入面移交时，按前述要求停写、对账并更新契约，不因角色标签变化略过交接。
- 目标完成后回收本次成员任务与已获授权的临时运行资源；按当前运行时能力核验成员与资源的实际状态，不把空闲当作已结束，也不为处理空闲扩大任务。需要跨会话继续时保留目标、任务所有权、事实、产物与证据定位；恢复后重新核验成员与项目状态，不假定成员或未完成任务自动恢复。
