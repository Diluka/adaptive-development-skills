# Behavior-Driven Development：行为驱动开发

Use when 真实业务、开发与测试角色对同一可观察行为存在会改变实现或验收的理解差异，需要围绕具体示例形成共享规则并推进一个小行为增量。

行为和验收边界已被共同理解时直接实现；单个代理把已知需求改写成 Given / When / Then 不产生 BDD 收益。

## Discovery

1. 选择一个即将交付的小行为变化，以真实用户、业务角色或调用方能观察的结果界定范围。
2. 让能代表业务、开发和测试视角的参与者，或相应权威材料，共同检查具体真实示例。
3. 从示例中识别规则、边界、反例和仍会改变实现的问题，优先消除理解差异。

Discovery 的结果是共享理解和真正未决的问题。

## Formulation

1. 选择能区分正确与错误行为的代表性示例，用领域语言表述前置情境、事件和可观察结果。
2. 让业务与技术参与者确认结果含义一致，并移除数据库字段、私有方法、界面选择器等非必要实现细节。
3. Given / When / Then 只是一种可选表达格式；自然语言或其他结构更清楚时沿用更简单的形式。

## Automation

1. 一次选择一个已达成共识且有长期回归价值的示例，从保留该业务行为的真实系统边界观察结果。
2. 依据确认后的示例推进实现；自动化断言来自共享规则，代码或测试不能单方面改写约定行为。
3. 运行示例并核对业务结果；出现新信息时回到 Discovery 或 Formulation，使共享理解、场景和实现重新一致。

低层测试可以辅助定位独立规则，但不能替代业务验收行为。自动化范围按 [evidence.md](evidence.md) 的回归风险、失败信号和维护成本收敛。

## 结果与停止

保留共同确认的规则、示例、反例和未决问题，以及有长期收益时连接真实业务边界的自动化结果。Discovery 与 Formulation 证明共享理解已形成；只有实际运行的 Automation 能证明当前实现与示例一致。

关键业务取舍仍未决定，或方法过程中产生新的独立目标时，返回 Workflow 重新编排。共享理解已形成且当前行为增量已验证时结束本方法；后续实现、文档和证据机制继续由 Execution 选择。
