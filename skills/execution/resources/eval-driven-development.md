# Eval-Driven Development

Use when 需要用代表任务、评价标准和重复试验定义、实现并持续改进 AI、Agent 等主观、多解或概率性能力。

把评估作为开发方法，而不是实现完成后的附加检查：先用代表任务和评价标准定义目标能力、建立基线，再实现并通过重复试验持续改进。结果可以有多个合理答案，但评价维度、失败影响和决策条件必须来自用户目标与真实用途，不能从候选实现反向发明。

## 开始前确认

- 已定义目标能力、真实使用方、成功维度和高影响失败。
- 能从真实用途、人工检查、历史问题或代表性风险建立初始任务。
- 能在足够稳定且相互隔离的环境中运行候选，并记录每次执行。
- 至少有一种与实现相对独立的评价依据，并能校准主观评价。
- 可以记录模型、提示、工具、代理框架、数据和环境版本。
- 评估成本、正式环境数据和外部副作用处于授权边界内。

评价机制本身未知时，本方法尚不具备前提，返回 Execution 重选；该未知形成独立调查目标，或目标 / 质量维度存在会改变方案的关键歧义时，返回 [adaptive-development-workflow](../../adaptive-development-workflow/SKILL.md) 重新编排。

| 概念 | 含义 |
|---|---|
| 任务 `task` | 具有明确输入和成功条件的单个评估问题 |
| 试验 `trial` | 候选对一个任务的一次独立尝试 |
| 评价器 `grader` | 对表现的一个维度评分或判断 |
| 轨迹 `transcript / trace / trajectory` | 一次试验中的输出、工具调用、中间结果和交互记录 |
| 结果状态 `outcome` | 试验结束时环境中的真实最终状态 |
| 评估工具链 / 套件 | 执行、记录和比较评估所需的系统与任务集合 |

评估对象是模型与代理框架的组合。真实结果状态能够验证目标时，优先评价结果状态，并用轨迹解释过程与失败。

## 建立任务集

- 从开发期间已有人工检查、真实用户任务、已确认问题和高影响失败中收集任务；同时覆盖行为应当发生和不应当发生的情况，并按重要风险、用户类型和输入结构保持平衡。
- 让任务说明、可用工具、环境和成功条件一致。评价器检查的要求必须对候选可见；可行时提供一个已知可行的参考结果。
- 记录任务来源、适用范围和加入理由，持续吸收新的真实失败，不围绕固定样例单向优化。
- 初始任务集不求大：20-50 个来自真实失败的任务即可起步，随新失败扩充。

任务应足以区分合理质量差异，但不能规定真实目标不要求的实现路径。

## 设计与校准评价器

- 稳定不变量使用确定性评价器；语义或质量判断使用基于模型的评价器（LLM-as-judge）；高风险、强主观或需要校准时使用领域人员评价。
- 使用 LLM-as-judge 时，为不同评价维度分配独立 judge，依据结构化 rubric 评分；证据不足时返回“无法判断”，不硬凑分数。
- 把多维结果拆成清晰量表，分别评价任务完成、质量、安全、交互或其他真实维度；多组件任务按可独立判定的组件给部分分，避免只判全对或全错。
- 优先评价产物和真实结果状态。只有工具选择、交互过程或资源使用本身属于需求时，才把轨迹行为纳入评分。
- 用领域人员判断校准模型评价器，记录一致、分歧、偏差和不可靠区域。一次模型评分或一个独立代理意见都不是已校准评价。

阅读实际轨迹和评分，确认失败来自候选表现，而不是任务歧义、评价缺陷、环境噪声或工具链限制，并防止候选绕过评价器取得虚假高分。

## 建立基线与重复试验

- 正式改动前运行当前候选作为基线。区分能力型 eval（衡量新能力上限，通过率可从低值起步）与回归型 eval（保护已有行为，通过率接近 100%）；新能力尚不存在时低通过率也是有效起点。通过率持续为 0% 时先核对任务、环境和评价器。
- 每次试验从独立、可比较的环境开始，记录任务、候选版本、模型与工具配置、轨迹、结果状态、评分、错误、延迟、令牌和成本。
- 概率性结果运行多次，次数按波动、失败影响和决策成本决定。至少一次成功有价值时关注 `pass@k`；每次都需可靠成功时关注 `pass^k`；同时检查总体分布、重要风险切片、波动和具体失败。

基线只在任务、评价器、环境和候选边界可比较时有效。实质修改评估定义后，明确哪些旧结果失效，并重新建立受影响基线。

## 核心循环

1. 实现前写清目标能力、初始任务、评价维度和决策条件。运行基线，检查任务可解、环境稳定、评价公平，并阅读代表性轨迹。
2. 实现当前能力所需的最小正式变化，不为刷分加入真实用户不需要的行为。
3. 对受影响任务执行重复试验，同时运行仍覆盖相邻退化风险的回归证据。
4. 比较基线与候选的分布、切片、失败案例、成本和延迟，区分候选缺陷与评估系统缺陷。修正对应一方并记录理由；评估定义变化时重新判断历史结果的可比性。
5. 迭代到预定质量条件得到支持，同时报告仍无法稳定判断或仍有显著波动的区域。

任务集接近饱和时，把稳定任务转入持续回归套件，并用更有区分度的新任务继续衡量进步。评估套件是需要明确负责人和持续维护的项目产物；适用时在相关改动或模型升级后运行回归评估。

上线后的只读正式环境监控可发现分布漂移和未预料失败；用户反馈、轨迹抽查和 A/B 测试补充自动评估，定期领域人员复核校准主观评价器。这些证据各有边界，不能互相冒充，也不授权未明确要求的部署、流量实验或数据写入。

## 产出与边界

记录任务来源、覆盖与已知空白，成功条件、评价器、rubric、校准、分歧和限制，基线与候选的试验次数、分布、风险切片和代表失败，以及轨迹 / 结果状态、成本、延迟、错误、决策条件和剩余不确定性。

评估结果不自动成为确定性产品契约；只有经反复验证的稳定不变量才转为长期确定性测试。证据保留、失效和收敛见 [evidence.md](evidence.md)。子代理可以提供独立证据设计或人工评价，但角色隔离按 [agent-and-parallel-dispatch](../../agent-and-parallel-dispatch/SKILL.md) 管理，不能替代评价器校准。
