# 验证方式选择

Use when 已进入验证节点，需要为当前工作单元选择验证手段并形成最小充分组合。

## 从声明和反证开始

先写清待证明声明、权威来源、真实调用方与风险边界，再问：哪个观察能够推翻“它正确、保持行为或可交付”？只选择能拒绝当前合理错误的证据。

默认先沿真实消费或激活路径直接证明用户或需求明确提及的正常场景，再运行仓库对当前增量明确要求的强制检查。主动追加的类型检查、构建、更多测试和完整 CI 各自在覆盖一个已指明且尚未证明的风险时加入组合；证据足以支持当前交付声明后停止追加。

## 三类验证手段

- **动态执行**：运行产生行为证据——自动化测试、脚本化手工测试、可重复冒烟、调试和测量。黑盒从真实调用方或公共边界观察结果，白盒观察内部环节；端到端可自动也可手动，不因名称天然更充分。
- **静态检查**：工具静态验证不运行行为——构建、编译、类型检查、lint、format 和其他静态分析。记录真实工具链版本、配置、命令和范围；在真实使用位置由严格编译证明的稳定约束不再用运行时测试重复，外部输入仍在运行时解析，副作用、算法、传输、持久化、并发、时间、性能和概率质量仍需对应证据。
- **审视核对**：看，不执行——直接对照需求、规格、设计或既有事实审阅文档、文案、配置、差异和其他无需运行的产物。审视可以验证确定内容，也可以参与批准或人工评价；独立代码评审是另一个有独立角色要求的节点，不能用作者自查冒充。

## 组合与强度

- 主手段覆盖不全处用辅助手段补证据；不同手段只有覆盖不同失效面时才并存。
- 复用输入、环境、版本、路径和风险仍相同的既有测试、观测、评审或 CI，只补受当前增量影响的缺口。
- 复杂耦合、外部依赖或人工判断占主导时，脚本化手工回归可能比新增脆弱自动化更直接；记录步骤、环境和结果，使其可重复审阅。
- 行为保持型变更在修改前先确认有效基线；复杂可复现输出与概率性结果分别使用不同方法，不因都需要“比较基线”而混为一种测试法。

## 防止无效验证

- 断言必须独立来自需求、真实调用方、稳定不变量或外部契约；从待写字面量、当前实现或同一配置复制的镜像断言没有独立证据价值。
- 不为测试增加真实调用方不需要的生产开关、包装层、回退、分支或公共接口；替身只隔离时钟、网络、进程、随机性等真实外部边界。
- 构建通过、mock 调用次数、无关测试和格式检查只能证明各自范围，不能冒充业务行为、框架装配、传输或正式运行证据。
- 测试与更高优先级需求、真实调用方或契约冲突时修正测试或实现，不削弱真实不变量只求绿灯。

完成手段选择后，用 [evidence.md](evidence.md) 判断组合是否充分；即将声称完成时再由 [verification-before-completion](../../verification-before-completion/SKILL.md) 在最终增量上核对声明与证据。
