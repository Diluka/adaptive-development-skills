# Type-Driven Design：类型驱动设计

Use when 开发涉及稳定领域状态、公共 API、协议阶段、权限、单位或其他不变量，目标语言的类型系统能够以可维护方式排除合理的非法表示或调用。

在有可靠静态类型的项目中，优先把稳定不变量编码进类型；这是开发单元内的强推荐设计原则，不要求为使用类型建立独立工作单元或方法循环。普通字段、简单标注和指定字面量直接实现。

## 建模与证明边界

1. 从需求、领域规则、真实调用方或已核验契约识别长期稳定的不变量，并列出当前表示会允许的合理错误状态或调用。
2. 区分静态与运行时约束：当前语言、版本、严格配置和真实使用位置能够可靠检查的约束进入类型模型；外部数据、动态授权、数值计算、时间、并发、环境和副作用继续使用运行时解析、检查或观测。
3. 选择团队可维护的最小构造，例如判别联合、封闭层次、不透明或品牌类型、受控构造器、typestate 和穷尽匹配。保留“不变量 → 类型构造 → 被排除错误”的可审查映射。
4. 让公开操作只接受已证明前提的可信领域类型；新增状态应通过穷尽检查暴露必须同步的分支。

类型模型需要大量断言、强制转换、通用逃生类型或晦涩类型体操才能成立时，简化模型并把相应约束留在运行时。

## 解析不可信输入

把 JSON、HTTP、数据库、文件、消息、用户输入和跨语言值视为不可信表示。用解析器或受控构造器把它们转换为可信领域类型，并让失败成为显式结果。类型断言、反序列化目标声明和强制转换不能替代运行时解析。

解析成功后保存已取得的约束，使领域核心无需重复检查；解析失败时保留能定位边界的错误。

## 证据与剩余风险

在项目真实严格配置和实际调用位置运行编译或静态检查，覆盖类型模型、调用方、穷尽分支和边界适配。记录当前工具链、配置、命令、被排除错误和剩余运行时风险。

编译器已经证明的约束不再用运行时测试重复证明；公共或复杂类型 API 只有在兼容风险值得保护时，才保留少量 intended-valid / intended-invalid 编译契约。仍需运行时证据的范围包括：

- 不可信输入的解析成功、失败与错误传播；
- 合法状态上的算法正确性；
- 真实副作用、跨进程协议、并发、时间、性能和概率性质量。

具体证据按 [evidence.md](evidence.md) 与 [verification-selection.md](verification-selection.md) 选择。类型能缩小非法状态空间，但不能外推整个工作单元正确。
