# Spec-Driven Development：规格驱动开发

Use when 项目已经有高标准正式规格，并且用户、仓库或既定项目流程已明确把它选为当前实施依据，需要维护需求、设计、任务、实现和证据之间的可追溯规格链。

规格的存在本身不触发本方法；普通复杂任务、临时计划或准备编写一份新规格时，由 Workflow 与 Execution 按实际目标选择方法。不得为了采用 SDD 制造规格。

## 核心原则

以已选定的正式规格作为实施依据，把 Requirements → Design / Plan → Tasks → Implement → Evolve 连成可追溯推导链。新事实改变认识时，先更新最接近该事实的规格层，再同步受影响的上下游产物。

本资源只维护规格链。Workflow 拆分和编排实施单元；Execution 为调查、实现、验证和生命周期支持选择具体方法。

## 推进规格链

1. **Requirements**：从现有正式规格确认问题、价值、使用方、纳入范围、可观察结果、约束、验收条件和真实未知。把做什么、为什么做与如何实现分开；额外方向先作为候选保留在讨论或专门决策材料中，完成选择后进入规格链。
2. **Design / Plan**：从已确认需求、真实调用方、已核验契约、已观察问题或通过 Execution 门禁的必要技术前置推导系统边界、数据与交互、关键契约和不变量、技术选择及验证策略，使重要决定能追溯到对应来源。计划只承载已完成选择的设计。
3. **Tasks**：按可独立推进、可观察完成和可验证的结果拆分工作单元；每个单元保留需求、设计依据和完成证据映射，不按文件列表机械拆分。
4. **Implement**：按规格实施，并把工作单元与实际结果关联。具体开发方法、验证手段和执行机制由 Execution 选择。
5. **Evolve / Converge**：新事实出现时判断它影响需求、设计、任务还是实现，更新相应规格层并同步失配项；继续实施前确认现行规格链仍描述准备交付的方向。

默认让一条规格链原地演进并保持单一现行版本。领域确需多个规格版本长期并存时，先采用项目已定义的版本模型，并明确各消费方读取哪个版本。

## 验收证据映射

从确认后的需求、设计约束和验收条件派生待证明的可观察结果、真实调用方和具体失败风险，让证据追溯到规格条目。证据不能从当前实现反推，也不沿组件、类或函数列表机械生成。最小充分组合由 [evidence.md](evidence.md) 与 [verification-selection.md](verification-selection.md) 决定。

规格链证明意图、推导和实现方向一致，不能单独证明运行行为正确。实现与验证能够独立时，双方读取同一规格链；并行与角色分离仍由 Execution 选择。

## 结果与演进边界

保留以下可审查关系：

- 已确认需求和关键约束；
- 需求、设计决定、工作单元和验证方式之间的追溯；
- 规格条目、实现结果和验收证据之间的对应；
- 新事实出现后受影响规格层与实现的同步结果。

现有规格出现会改变业务政策的未决项、技术事实缺口或新的独立目标时，返回 Workflow 安排讨论、调查或开发单元。规格文档的位置、生命周期与表达规则由 `documentation` 管理；工具命令、模板、审批与分支规则服从当前项目约定。
