# Test-Driven Development：以真实行为驱动实现

## 核心原则

用失败行为测试证明实现尚未满足已知需求。只有行为、真实调用方和测试接缝都可信时，TDD 才适用。

## 检查前置条件

以下条件全部成立时使用 TDD：

- 将新增代码或改变行为；
- 必需结果或不变量已明确；
- 真实调用方会使用被测试的输入和输出；
- 接缝保留了要改变的行为；
- 失败具有确定性，能够指导实现。

缺少任一前置条件时选择其他方法：

| 情况 | 方法 |
|---|---|
| 删除死代码或依赖 | [caller-driven-cleanup](../caller-driven-cleanup/SKILL.md) |
| 外部契约不确定 | [contract-verification](../contract-verification/SKILL.md) |
| 根因不明确 | [systematic-debugging](../systematic-debugging/SKILL.md) |
| 可行性不明确 | [technical-spike](../technical-spike/SKILL.md) |
| 生成或机械产物 | 验证生成器和生成结果的契约 |

## TDD 循环

1. 写明一个必需的可观察行为及其真实调用方。
2. 在保留该行为的最低测试接缝编写最小测试。
3. 运行测试，确认它因为目标行为缺失而失败，而不是因为准备过程、过时假设或无关错误。
4. 只实现满足需求所需的最小生产行为。
5. 运行定向测试和相关相邻检查。
6. 在保持已验证行为通过的前提下重构。

如果测试在实现前已经通过，它不能证明目标行为缺失。如果它因错误原因失败，先修正测试或环境再继续。

## 保持接缝真实

保留真实业务规则和框架行为。只对时钟、网络、进程、随机性或不可用外部服务等真实外部边界使用测试替身。

禁止：

- 只为测试添加生产代码开关、包装层、回退分支、重载或公共方法；
- 使用任何真实调用方都不会产生的输入结构调用内部实现；
- 当序列化、中间件、持久化或框架绑定正是测试对象时模拟它们；
- 为保留当前实现而改变有效需求；
- 仅因为测试先存在就保留错误测试。

测试与实现不一致时，先使用 [evidence-based-testing](../evidence-based-testing/SKILL.md)，再决定修改哪一边。

## 示例

对于存在公共服务调用方的确定性计算不变量，先通过该服务使用真实生产输入结构添加测试。观察错误结果，做最小计算改动，再运行相邻用例。不要只为测试内部计算暴露私有辅助函数。

## 常见错误

- 未确认依赖契约就开始 TDD。
- 针对实现细节而不是可观察结果编写测试。
- 用模拟对象让无效调用方显得真实。
- 对删除使用 TDD 并重建应删除的接口。
- 受影响运行时边界被跳过时，仍把通过的测试当作充分证据。
