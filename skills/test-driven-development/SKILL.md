# Test-Driven Development：测试驱动开发

## 进入条件

TDD 是开发方法，但适用场景很窄，不是常用方式：只适合定义精确、自包含的零件或组件开发，且需求、调用方与契约已经完全明确。需求模糊或大功能开发无法写出准确描述需求的测试用例，会产生过度测试与冗余逻辑，不进入 TDD；这类目标应直接实现或选用其他开发方法。

本技能自行判断一个开发工作单元是否适合执行标准 TDD 循环，不依赖其他技能预先选择。用户明确要求使用 TDD 时也先核验以下条件，不能把方法偏好当作跳过判据质量和真实接缝的理由：

- 目标是一个可独立推进的确定性行为增量，而不是主观、概率性或纯声明式内容；缺陷修复的第一个错误状态和因果链已经确定；
- 预期行为和验收判据已经明确，并独立来自需求、真实调用方或已核验契约；
- 测试能够经过保留目标行为的真实稳定接缝，而不是复制当前实现或模拟被测行为本身；
- 失败检查能够拒绝至少一种合理错误实现，并对应值得长期保护的具体回归风险；
- 循环足够小且反馈足够快，先取得正确失败相较直接实现能够提供实际设计、反馈或风险控制收益。

条件全部成立才进入循环。任一条件不成立或在执行中失效时，停止并向任务协调者说明缺口；不要为维持 TDD 形式让测试发明需求、复制目标字面量或改变生产设计。

## Red → Green → Refactor

### Red

1. 从当前需求中选择一个最小、可观察的行为增量。
2. 在保留该行为的最低真实接缝编写一个最小测试。
3. 运行测试并确认它失败。
4. 检查失败原因确实是目标行为尚未实现，而不是测试准备、环境、过时假设或无关错误。

测试没有失败，说明它没有证明缺失行为；先修正测试范围或重新确认增量。测试因错误原因失败时，先排除该原因，不能把任意红灯当作 TDD 证据。

### Green

1. 只编写让当前失败测试通过所需的最小生产行为。
2. 运行当前测试和受影响的快速相邻检查。
3. 确认新增行为满足需求，并且没有通过硬编码测试输入、绕过真实路径或削弱既有契约获得绿灯。

Green 追求尽快获得正确反馈，不要求此时完成最终抽象或一次实现所有未来场景。

### Refactor

1. 在全部相关测试保持通过时消除重复、改善命名、结构和职责边界。
2. 同时整理测试，使其表达行为而非临时实现步骤。
3. 每个小改动后重新运行快速测试；出现失败立即判断是重构漂移还是测试耦合。
4. 保持外部行为不变，直到下一项有意行为增量进入新的 Red。

完成一个循环后，选择下一个最小行为并重复 Red → Green → Refactor，直到当前工作单元满足已确认需求。

## 保持测试可信

- 判据来自需求、真实调用方或已核验契约，不从待写入字面量或当前实现反向复制。
- 通过公开行为或真实稳定接缝测试，避免断言私有结构和无业务意义的内部调用次数。
- 类型系统已在真实使用位置排除的非法状态，不再制造重复的运行时红灯；公共或复杂类型 API 需要兼容保护时，只保留能拒绝真实类型回归的少量编译契约用例。
- 只模拟时钟、网络、进程、随机性或不可用外部系统等真实边界，不模拟被测行为本身。
- 不为测试增加真实调用方不需要的生产开关、包装层、回退、分支或公共接口。
- 一个测试只承担足以指导当前实现的行为范围；复杂场景继续拆成循环，不在首个 Red 一次编码全部结果。

精确文本或字面值只有在其本身构成协议、安全、合规或其他外部契约时才成为行为判据。普通声明式内容没有独立行为判据时，直接实现并从真实使用方取得必要证据，而不是在本技能中制造红灯。

## 停止并退出本方法

出现以下情况时停止 TDD 循环，把新事实返回任务协调者并重新判断适合的处理方式：

- 预期行为、真实调用方或验收判据仍有实质歧义；
- 已观察缺陷的根因尚未确定，测试无法区分症状与原因；
- 第三方 SDK、协议或框架的实际契约尚未核验；
- 当前主要目标是把稳定不变量编码为不可表示的非法状态，而不是实现运行时行为；
- 需要验证的是广泛输入属性、服务版本兼容、旧实现行为基线或概率性质量，而不是一个确定性示例增量；
- 只有改变生产接口或加入测试专用路径才能获得红灯；
- 无法在生产实现前取得因目标行为缺失而正确失败的 Red；
- 测试反馈不稳定或慢到无法支撑小循环。

这些情况分别可能形成 BDD、系统化调试、契约核验、属性测试、消费者驱动契约测试、特征测试或评估驱动开发单元；不要在 TDD 正文里混用它们的流程。

先解决根因、契约、判据、接缝或反馈速度缺口，再从进入条件重新判断；不能从中断的半个循环继续并仍声称执行了完整 TDD。

## 产出证据

保留能说明循环有效的最小证据：目标行为与判据来源、Red 的正确失败、Green 的通过结果、Refactor 后同一行为继续通过，以及受影响相邻检查的结果。

完成前把新增及受影响测试映射到稳定需求或不变量、真实调用方、具体回归风险和独特失败信号：

- 保留核心契约、历史缺陷、边界与错误、状态变化、外部副作用以及不同层级的独特保护；
- 合并或删除只重复同层同风险、约束私有实现、使用过时接缝或镜像普通字面量的测试；
- Red 曾成功驱动实现，不自动意味着对应测试必须永久保留，也不能删除仍提供独特契约或故障定位价值的检查；
- 删除或合并后重跑剩余定向测试和受影响相邻检查，确认最终组合仍能拒绝相应合理错误实现。

## 与相邻方法分工

- BDD 的 Discovery → Formulation → Automation 用业务示例形成共享行为；TDD 从已经明确的确定性增量驱动实现。
- [type-driven-design](../type-driven-design/SKILL.md) 用类型构造排除非法表示；TDD 只覆盖类型系统无法证明的运行时行为，二者不为同一约束重复制造证据。
- 属性测试定义独立属性、生成输入空间与收缩反例。它只作为某个 Red 的测试技术时，由 TDD 拥有实现时序，不再为同一行为执行第二套主要流程；广泛输入不变量本身是主要风险时，交给独立属性测试单元，首次失败不另算 TDD。
- 消费者驱动契约测试拥有消费者契约、提供者验证和版本兼容闭环，不是普通 TDD 单元测试。
- 特征测试先在旧实现上建立绿色事实基线，不是 Red。
- 评估驱动开发使用任务集、grader 和重复 trial 处理概率性结果，不把暂定量表伪装成确定性测试。
