# Test-Driven Development：以真实行为驱动实现

## 核心原则

先用失败的行为测试证明实现还不满足已知需求。测试判据必须来自明确需求、真实调用方或依赖契约，不能靠复制目标内容或当前实现制造红灯。下面列的是 TDD 的前提，不是选用 TDD 的充分条件。只有它比直接实现和现有验证多提供了证据，才使用。

## 检查前提

- 将新增代码或改变行为；
- 必需结果或不变量能在实现前从需求、真实调用方或契约独立确定；
- 真实调用方会使用被测试的输入和输出；
- 接缝保留待改变行为；
- 失败具有确定性并能指导实现；
- 测试能识别至少一种合理但错误的实现，而不是只证明旧字面量不等于新字面量；
- 存在具体可信的回归风险，新增测试的长期价值高于维护成本。

缺少前提时改用更合适的方法：删除用 [caller-driven-cleanup](../caller-driven-cleanup/SKILL.md)，外部契约未知用 [contract-verification](../contract-verification/SKILL.md)，根因未知用 [systematic-debugging](../systematic-debugging/SKILL.md)，可行性未知用 [technical-spike](../technical-spike/SKILL.md)。

## TDD 循环

1. 写明一个必需的可观察行为及其真实调用方。
2. 写明判据来源、要排除的合理错误实现和对应回归风险。
3. 在保留该行为的最低测试接缝编写最小测试。
4. 确认测试因目标行为缺失而失败，而不是准备过程、过时假设或无关错误。
5. 只实现满足需求所需的最小生产行为。
6. 运行定向测试和相关相邻检查。
7. 在已验证行为保持通过时重构。

实现前已经通过的测试不能证明目标行为缺失；测试因错误原因失败时，先修正测试或环境。行为保持型重构在旧实现上通过的核心行为基线，以及从真实执行结果生成并确认的快照，都不是 TDD 红灯。它们由 [evidence-based-testing](../evidence-based-testing/SKILL.md) 建立，并在变更后重复验证。

## 排除低价值红灯

- 若预期结果主要是已指定的提示词、文案、模板文本、静态常量或其他声明式内容，测试只能人工复制新字面量、断言包含或同步更新快照，则直接实现并按影响验证，不选择 TDD。
- 若整体或局部真实输出能够稳定复现，但逐项行为难以断言，使用 [evidence-based-testing](../evidence-based-testing/SKILL.md) 建立快照或其他行为基线；有意变更后的快照审阅与更新是回归验证，不自动成为 TDD。
- 若结果具有主观性、概率性或多种合理答案，先定义代表性样例和评价标准，按需使用独立评估或 [technical-spike](../technical-spike/SKILL.md)，不要把当前偏好伪装成确定性单元测试。
- 精确文本本身属于协议、安全、合规或其他外部契约时，可以测试该契约；测试仍应经过真实生成路径并限制在必要范围。

## 保持接缝真实

接缝必须符合真实调用方式并保留待改变行为；只模拟时钟、网络、进程、随机性或不可用外部服务等真实外部边界。若通过测试需要添加真实调用方和契约都不需要的生产开关、分支、包装层、回退或公共方法，立即停止实现并重新审查测试。

测试与实现冲突、序列化或框架边界可能被模拟掉时，使用 [evidence-based-testing](../evidence-based-testing/SKILL.md) 核验后再决定修改哪一边。
