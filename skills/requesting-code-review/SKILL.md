# Requesting Code Review：请求独立评审

## 核心原则

每个开发任务的最终项目差异都必须由未参与实现的独立子代理至少评审一轮。风险和不确定性只决定评审深度与是否增加专项评审者，不决定是否评审。向评审者提供完整实际差异和事实约束，不要引导结论。

复杂非开发调研不强制评审；只有独立检查能实质降低偏离原目标、遗漏反证或结论不准确的风险时才选择评审代理。

## 决定审查深度

| 改动 | 审查方式 |
|---|---|
| 微小文档、拼写或隔离元数据 | 一个范围很窄的独立子代理评审，确认目标差异和明显错误 |
| 有强验证证据的定向低风险行为 | 一个独立子代理评审正确性、回归风险和验证缺口 |
| 跨模块契约、依赖迁移、身份认证、资金、数据、并发 | 扩大独立评审深度，必要时增加对应专项评审者 |
| 破坏性 Git 操作、数据库模式、正式环境或安全边界 | 深度独立评审，并为实际操作另行取得用户明确授权 |

一个开发任务只要求对最终准备交付的完整差异完成评审，不要求每个工作单元或临时调查产物分别评审。PR/MR 可以承载额外协作评审，但不能替代根代理派发的独立子代理评审。

## 准备证据包

先判断仓库是否已有初始提交：

```bash
git rev-parse --verify HEAD
```

已有 `HEAD` 时，寻找实际分支基点，不要只使用前一个提交：

```bash
git merge-base HEAD <target-branch>
git log --oneline <base>..HEAD
git diff --stat <base>..HEAD
git diff --find-renames -U10 <base>..HEAD
git status --short --untracked-files=all
git diff
git diff --cached
```

没有 `HEAD` 的初始仓库跳过合并基点、提交日志和 `<base>..HEAD` 命令，直接使用 `git diff --cached --stat`、`git diff --cached --find-renames -U10`、`git diff` 和完整状态构造相对空树的证据包。初始提交同样需要独立评审。

包含：

- 需求和明确不变量；
- 当前计划文档的精确路径和最终状态；
- 精确差异范围和改动文件；
- 受影响的真实调用方和依赖契约；
- 已运行的验证及结果；
- 与新失败分开的已知基线失败；
- 未解决假设或有意延后的范围。

评审对象必须是正式实现和相关验证完成后的完整实际差异。说明评审者未参与该版本的实现或修复，并提供最新验证证据；不要只传摘要或预期结论。

未提交工作必须同时覆盖工作区、索引区和未跟踪文件。`git diff` 与 `git diff --cached` 都不会包含未跟踪文件；根据 `git status --short --untracked-files=all` 展开的文件路径逐个纳入证据包，并只对精确文件使用 `git diff --no-index -- /dev/null <path>` 生成审查产物。不要把目录路径传给该命令，不要只为了审查自动暂存文件，也不要用 `HEAD~1` 隐藏多次提交或未提交工作。

## 请求无偏审查

要求评审者使用独立上下文，读取原始需求、计划文档、完整实际差异和验证证据，按严重性给出带文件和行号引用的意见，并检查正确性、回归风险、安全或数据边界，以及与本次改动相关的缺失验证。

评审者原则上只读，不直接修改被审查文件，也不得继续派生子代理。不要预先把可疑问题标为无害，不要暗示“预期没有问题”，不要指示评审者忽略疑虑，也不要用叙述代替评审者阅读差异。

只有根代理可以派发独立评审者。子代理如果识别出评审需求，应把证据包和理由交还根代理，不得继续派生代理。

使用 [receiving-code-review](../receiving-code-review/SKILL.md) 核验评审意见。处理意见产生实质项目修改时，重新运行受影响验证，再由未参与该轮实现或修复的独立子代理复审新的最终版本。只有最终实际差异本身已经评审，且已接受意见完成处理或明确记录处理结论，评审才完成。

如果环境无法创建独立评审子代理，只能报告“实现和验证完成，独立评审尚未完成”，不得声称开发任务完成。评审任务本身不递归要求另一个评审者；处理意见也属于原开发任务，不创建新的任务或计划。

## 评审复杂非开发调研

选择评审复杂调研时，向评审者提供原始目标、范围、关键问题、证据、反证、结论、未决项和临时产物清理证明。要求它检查是否偏离最初目标、证据是否支持结论、是否遗漏合理替代解释。此类评审不要求开发计划或 Git 差异，也不把调查转换为开发任务。

## 示例

对于跨模块的高风险契约改动，提供合并基点差异、受影响调用方与契约、成功和失败的运行链路，以及定向 E2E 结果。要求审查者查找遗漏的边界回归；不要只审查测试文件，也不要在没有真实契约时预设结果。

## 常见错误

- 只审查多次提交改动的最后一个提交。
- 因为改动只是拼写、文档或元数据，就省略开发任务的独立评审。
- 漏掉未跟踪文件或已知失败，使审查者看不到完整改动或无法区分回归。
- 用预期结论影响审查者。
- 让参与实现或修复的代理评审自己的版本，或允许评审代理继续派生。
- 评审后实质修改项目产物，却不重新验证和复审最终差异。
- 把复杂调研的可选准确性评审扩张为所有非开发任务的门禁。
- 把审查批准当成运行时验证的替代品。
