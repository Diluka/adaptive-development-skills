# 行文风格

**先回答读者最关心的问题。** 读者要作判断，先给结论，再给足以判断的依据；读者要执行任务，先写在什么条件下做什么，再写怎样知道做成了。篇幅取决于读者需要知道多少。

- **用正面、直接的表达写清实际行为。** 写出具体的主体、动作和结果。例如，把“优化上传反馈”写成“用户取消上传后，进度条消失，页面显示‘已取消’”。改写时保留原意和仍适用的语气；只改一句时，改动限于该句及必要衔接。
- **限制和否定要有可核对的出处，并服务本文读者的判断。** 写入正文的限制、警告、前提和否定（如“不支持”“不会”“不要”），来源要落在可核对的载体上：文件与行号、契约原文、仓库规则原文及位置、变更记录条目、可执行的复现步骤或用户原话，并直接证明行为和触发条件；目标读者还要能指出本文任务中哪一步会因此改变做法。口头经验、团队共识、通用最佳实践、行业惯例、“为防万一”、只证明相关的实现细节和推测都不算来源。缺少来源的先核实，核实不了按风险或待核实写，不写成限制。属于本文读者的真实限制写清触发条件和已知的正确做法，正确做法未知时先核实。
- **技能指令先写已选路径，不回写已否决的方案。** 讨论中否决且不再影响行动的方案直接略去；写进去会让后续代理误当成新约束。未确认的例外写成待核实问题或验证步骤，不写成条件分支或禁令。
- **让读者看得出事实和判断的区别。** 在关键判断旁给出直接依据：行为说明对照实现与真实调用方，决定对照已确认的取舍，进度和评审意见对照当前差异与检查结果。只观察到现象时，把原因写为待核实；还没核实的担心按风险或待核实问题写，只写不确定性和要核实的问题，不写建议、禁令或“不要”——凭空补一句“不要在高并发下使用”，只会让读者以为自己漏掉了约束；计划、承诺和已完成的事分别表述。
- **按读者和去向选材。** 界面提示写用户现在能做什么；代码注释写维护者需要知道的理由；技能正文写代理作选择所需的指令，配套指南承载选中后才用到的细节。长期维护的事实放在一个权威位置，其余地方用摘要和链接。

写 README 或 AGENTS.md 时，按[仓库说明的读者与分工](resources/repository-instructions.md)决定内容放在哪里。

交付前从接收者角度读一遍：结论是否有据，指令能否照做，措辞是否暗示了尚未完成的工作。再核对限制、前提和否定句：来源落在可核对的载体上，直接证明行为和触发条件，并对应目标读者的具体步骤；没核实的按风险或待核实保留，不写建议或禁令；只有来源直接证明该限制、确实属于其他读者、且目标指南已包含该限制并可达时，才移动或给链接，无法确认时保留在本文；安全、权限和数据损失类限制不移动。按目标受众保护凭据和敏感信息；草拟、写入仓库和对外发送或发布分别按授权执行。
