# Evidence-Based Testing：基于证据选择测试

## 核心原则

为具体问题选择最有效且足够的证据：测试、快照、评估、观测，或其中几种的组合。保留关键契约，并验证真实需求。行为保持型重构必须能够比较修改前后的核心业务行为，不追求测试数量或极致覆盖率。绝不能为人工构造的测试调用改变生产设计，也不能因为可测试就默认使用 TDD。

## 确认待证明结论

对每个争议行为，写清必需结果或不变量、真实调用方和输入结构、相关依赖契约，以及什么证据能推翻当前结论。

测试与实现不一致时同时审查。证据优先级为：需求和不变量 > 真实调用方和生产行为 > 依赖和协议契约 > 当前实现和测试。测试基于不存在的调用方、错误契约或内部细节时修正或删除测试；实现违反真实需求时修正实现。

## 按结果性质选择证据

| 结果性质 | 首选证据 |
|---|---|
| 具有独立、稳定判据的确定性行为 | 定向测试；满足额外收益条件时可选择 [test-driven-development](../test-driven-development/SKILL.md) |
| 整体或局部真实输出可稳定复现，逐项断言成本高 | 经审阅的行为基线或快照回归 |
| 已指定的提示词、文案、静态常量或声明式内容，未改变确定性生成逻辑 | 直接修改、差异审阅和现有检查，不复制目标字面量制造测试 |
| 主观、概率性或允许多种合理答案的结果 | 代表性样例、评价量表、重复评估、实验或真实链路冒烟 |
| 可行性或效果仍未知 | [technical-spike](../technical-spike/SKILL.md) |

如果测试判据只能从待修改的字面量或当前实现反向复制，它就不是独立证据。精确内容本身构成协议、安全、合规或其他外部契约时，才按契约风险保留必要断言。

## 使用快照

快照适合难以逐项断言、但整体或局部结果能够稳定复现的真实输出。快照必须由生产执行路径生成，只覆盖有业务意义且噪声可控的最小范围，并让评审者能从差异判断变化是否符合预期。不得在测试里手写一份生产内容冒充快照。

建立快照前先确认输出稳定，排除时间、随机值、无关顺序和环境漂移。行为保持型工作要在旧实现上保存并确认基线。有意改变输出时，先审阅业务差异再更新快照，不能用无条件接受新快照来掩盖问题。旧基线通过、变更后出现预期差异，再确认新基线，这属于行为基线或回归验证，不是 TDD。

页面、组件树、序列化结构或复杂生成内容可以使用整体或局部快照。如果只改一段静态内容，快照除了重复该字面量外不能发现其他漂移，直接修改更合适。快照只能证明生成结果稳定，不能替代对主观质量或概率性下游效果的评估。

## 评估模糊结果

结果无法用唯一的精确断言表达时，从用户目标、真实调用场景和失败影响中整理代表性样例、评价维度、最低接受条件与反例。暂定量表不应直接固化为生产契约；只有反复证明稳定的不变量才转成长期自动化测试。

独立视角能够降低实现者自证偏差时，可通过 [subagent-driven-development](../subagent-driven-development/SKILL.md) 分离实现和证据设计：评估者依据共享目标独立提出样例、量表、测试或反证，根代理比较证据并集成；参与实现、证据设计或相关项目差异修改的代理不能兼任最终独立评审者。

## 重构前核心行为基线

涉及业务逻辑、状态变化、公共契约或框架边界的行为保持型重构，在修改实现前先为受影响的核心行为建立最小证据基线：

1. 根据必需结果、真实调用方和失败影响列出本次重构必须保持的核心行为。
2. 盘点并运行已有相关测试；它们经过受影响路径并断言可观察结果时直接复用，不重复补测。
3. 只对必要证据缺口，在最低且真实的稳定接缝补充最小测试，并在未重构的实现上确认通过。不追求与本次风险无关的覆盖率或全面补测。
4. 若逻辑确实难以自动化测试，或建立测试接缝的成本与当前风险不成比例，定义可重复的冒烟步骤，固定代表性环境和输入，观察输出、状态与副作用。
5. 重构后运行同一测试或冒烟步骤，比较结果；任何无法由已确认需求解释的差异都表示行为保持尚未得到证明。

测试和冒烟可以配合使用。少量测试负责确定性的核心规则，冒烟负责框架装配、真实调用链或难以隔离的场景。各自覆盖擅长的风险面，合起来能识别本次重构的行为漂移即可。

冒烟观测记录至少包含环境或版本、输入与步骤、重构前后的可观察结果、差异及结论。构建、类型检查、无关测试、模拟调用次数和人工代码审查可以补充证据，但不能单独证明核心业务行为没有漂移。若既没有有效测试，也无法取得可重复的前后观测，则缩小工作单元、先建立验证接缝或暂停对应重构。

基线测试用于锁定已确认的现有行为，应在旧实现上通过，不属于要求先失败的 TDD。若重构同时包含有意行为变化，把该变化拆成独立工作单元，再判断是否使用 [test-driven-development](../test-driven-development/SKILL.md)。纯注释、格式化或其他不影响运行行为的机械改动无需建立此基线。

## 选择测试层级

| 问题 | 首选证据 |
|---|---|
| 纯确定性业务规则 | 定向单元测试或属性测试 |
| 框架绑定、序列化、装饰器或中间件 | 真实框架模块或集成测试 |
| SQL、事务或持久化映射 | 可丢弃的本地或测试数据库集成 |
| 可稳定复现但逐项断言成本高的输出 | 最小范围整体或局部快照 |
| 完整且接近生产的链路 | 窄范围端到端测试 |

只有较低层接缝会抹掉待验证行为时才向上移动。HTTP、SDK、CLI 或协议行为先用 [contract-verification](../contract-verification/SKILL.md) 核实；只在正式环境出现且根因未知的症状先用 [systematic-debugging](../systematic-debugging/SKILL.md) 调查。

## 只模拟真实边界

测试替身只用于控制时钟、网络、进程、随机性或不可用的外部系统。业务不变量与待验证的框架、解析、序列化和持久化行为保持真实。

不要模拟被测单元本身，不要为了测试新增生产开关、包装层、回退分支或公共方法，也不要用模拟调用次数替代可观察结果。

## 选择 TDD

选择 [test-driven-development](../test-driven-development/SKILL.md) 前，确认行为明确且确定，判据来自需求、真实调用方或契约，接缝符合真实调用方式，测试能识别合理的错误实现，并且存在具体回归风险。满足这些条件也可以直接实现；说不清 TDD 比现有验证多提供什么证据时，就直接实现。

只删除不改变行为的清理不使用 TDD；改用 [caller-driven-cleanup](../caller-driven-cleanup/SKILL.md) 验证调用方、构建和导出范围。
