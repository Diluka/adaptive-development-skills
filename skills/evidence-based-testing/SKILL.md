# Evidence-Based Testing：基于证据选择测试

## 核心原则

通过最便宜且稳定、同时保留关键契约的接缝测试真实需求。绝不能只为人工构造的测试调用改变生产设计。

## 先确认待证明结论

对每个争议行为，用一句话写清：

- 必需结果或不变量；
- 真实调用方与输入结构；
- 约束它的依赖契约；
- 能推翻该结论的证据。

测试与实现不一致时必须同时审查。证据优先级为：需求和不变量 > 真实调用方和生产行为 > 依赖和协议契约 > 当前实现和测试。

若测试基于不存在的调用方、错误的依赖行为或内部细节，应修正或删除它；若实现违反真实需求，不能为了保持测试通过而弱化测试。

## 选择测试层级

| 问题 | 首选证据 |
|---|---|
| 纯确定性业务规则 | 定向单元测试或属性测试 |
| 框架绑定、序列化、装饰器、中间件 | 真实框架模块或集成测试 |
| SQL 结构、事务、持久化映射 | 可丢弃的本地或测试数据库集成 |
| HTTP、SDK、CLI 或协议行为 | 契约测试或只读沙箱冒烟测试 |
| 完整且接近生产的链路 | 窄范围端到端测试 |
| 只在正式环境出现的症状 | 先看日志、跟踪、只读 DB 状态与调用链，不要先发明复现方式 |

只有较低层接缝会抹掉待验证行为时才向上移动。

## 只模拟真实边界

测试替身只用于控制时钟、网络、进程、随机性或不可用的外部系统。业务不变量与框架行为保持真实。

禁止：

- 模拟被测单元本身；
- 当解析器或序列化器正是契约时替换它；
- 为测试新增生产代码开关、包装层、回退分支或公共方法；
- 需求是可观察结果，却只断言模拟调用次数。

## 判断是否适合 TDD

当行为明确、代码将改变且存在稳定真实接缝时，使用 [test-driven-development](../test-driven-development/SKILL.md)，并先确认测试因预期缺失行为而失败。

只删除不改变行为的清理不使用 TDD；改用 [caller-driven-cleanup](../caller-driven-cleanup/SKILL.md)，验证保留的调用方、构建与导出范围。

## 示例

若单元测试向内部服务传入真实调用方永远不会生成的输入结构，不要增加回退分支。追踪真实入口、输入归一化过程和依赖契约，再通过真实边界重写或删除测试。若真实调用方也会失败，则保留能够复现该链路的回归测试。

## 常见错误

- 因为测试先存在就默认它正确。
- 用测试替身替换有意义的框架边界。
- 纯不变量足够时仍使用昂贵的端到端测试。
- 仅从类型或模拟对象推断外部契约。
- 把覆盖率百分比当成需求证据。
