# Type-Driven Design：类型驱动设计

## 核心原则

先用类型表达已经确认的稳定不变量，再在类型约束下实现。目标不是增加普通类型标注，而是缩小可表示的状态和程序空间，让违反不变量的合理错误在静态检查阶段失败。

只主张目标语言、版本、工具链、严格配置和真实使用位置实际证明的约束。类型可以减少重复运行时检查，但不能证明尚未解析的外部输入、真实副作用、算法正确性、并发时序、性能或概率性质量。

## 标准流程

### 1. 识别稳定不变量

1. 从需求、领域规则、真实调用方或已核验契约中列出必须成立的状态、组合、转换、权限或语义区别。
2. 为每项不变量列出至少一种当前设计可能允许的合理错误表示或错误调用。
3. 区分长期稳定的领域约束与可能频繁变化的业务政策、部署状态或环境事实。只把前者作为类型模型的候选。
4. 说明类型约束能排除什么，以及排除该错误为何值得增加模型复杂度。不能显著排除错误时，停止本方法并返回入口重新选法。

### 2. 区分编译期与运行期约束

为每项不变量标明证明边界：

- 由静态类型系统可靠表达并在当前严格配置下检查的约束，进入类型模型；
- 依赖外部数据、动态授权、数值计算、时间、并发、环境或真实副作用的约束，保留运行时解析、检查、测试或观测；
- 同时包含两类风险时，在不可信边界取得运行时证据，再把成功结果转换为可信领域类型。

不要把期望类型写在外部数据上就视为约束已经成立，也不要把某一种语言的能力外推到其他语言。先核对实际语言版本、构造可见性、穷尽性规则、互操作边界和逃生口，再决定能主张的静态保证。

### 3. 建立类型模型

选择目标语言可靠支持且团队能够维护的最小构造：

- 用积类型与和类型、封闭层次或判别联合表达有效状态组合；
- 用不透明类型、新类型、品牌类型、精化类型或受控构造器区分语义身份并保存已取得的约束；
- 用 typestate 或等价状态索引表达允许的阶段转换和操作能力；
- 用穷尽匹配处理封闭状态，令新增状态暴露所有必须同步的分支；
- 隐藏能绕过不变量的原始构造方式，只暴露保持约束的创建与转换操作。

让“不变量 → 类型构造 → 被排除错误”的映射可审查。若模型必须依赖大量断言、强制转换、弱化类型、通用逃生类型或晦涩类型体操才能工作，先简化模型；仍无法清楚表达时改用运行时约束，不以复杂度冒充证明。

### 4. 在不可信边界解析

把 JSON、HTTP、数据库、文件、消息、用户输入和跨语言值视为不可信表示。通过解析器或受控构造器把较弱结构转换为可信领域类型，并让失败成为显式结果。

解析成功后保留取得的信息，使领域核心不再重复检查同一约束；解析失败时保留足以定位边界问题的错误。禁止用类型断言、反序列化目标声明或强制转换跳过运行时检查。

### 5. 在类型约束下实现

让函数签名、状态转换和公开操作只接受已经证明所需前提的领域类型。根据编译器反馈补齐合法状态、转换和穷尽分支，在每个小增量后运行快速静态检查。

删除仅为弥补旧表示而存在、现已由类型模型排除的防御分支和重复断言前，确认所有真实入口都经过可信构造路径。不要借类型重设计顺手改变尚未授权的业务行为或外部协议。

### 6. 运行静态验证与必要类型契约用例

在项目真实严格配置和实际使用位置运行编译器或静态分析器，记录工具链版本、配置、命令和受检范围。确认类型模型、所有调用方、穷尽匹配和边界适配共同通过，而不是只检查孤立示例。

只有公共或复杂类型 API 存在具体兼容回归风险时，才保留少量类型契约用例：预期合法的调用必须通过，预期非法的调用必须因目标约束失败。检查失败原因，避免把语法错误、缺失依赖或无关诊断误当作反例证据。编译器已经证明的约束不再用运行时测试重复证明。

### 7. 补足剩余运行时证据

测试不可信边界能接受有效输入、拒绝无效输入并产生预期领域类型或错误。再通过 [evidence-based-testing](../evidence-based-testing/SKILL.md) 为类型系统无法证明的算法、真实副作用、跨进程兼容、并发、时间、性能和概率性结果选择证据。

类型减少了可进入核心逻辑的非法状态，不代表合法状态上的所有行为都正确。把剩余风险显式列出，避免用一次成功编译外推整个工作单元正确。

## 产出证据

至少保留以下可审查结果：

- 稳定不变量、类型构造、被排除错误和运行时剩余风险的映射；
- 当前工具链与严格配置下覆盖真实调用位置的编译或静态检查结果；
- 必要时，公共或复杂类型 API 的 intended-valid / intended-invalid 类型契约结果；
- 封闭状态穷尽处理或等价静态证明；
- 不可信边界的解析成功、失败和错误传播证据；
- 对算法、副作用、跨进程行为、并发、性能和概率性质量仍需运行时证明的清单。

## 排除与停止条件

- 简单字段、普通类型标注、类型别名或已指定字面内容直接实现并运行项目既有静态检查；不要为它们建立独立类型驱动单元。
- 外部 JSON、HTTP、数据库、文件或用户输入在解析成功前不属于可信领域类型；目标类型声明不能替代边界验证。
- 数值算法、广泛运行时输入、真实副作用、并发、时间、性能和概率性质量不能因实现使用了类型就改由本方法证明。
- 类型模型只能靠大量断言、强制转换、通用逃生类型或难懂类型体操维持时，停止扩展，简化设计或把约束返回运行时。
- 编译器或静态分析结果只是一类证据，不另包装成宽泛的 `static-verification` 开发方式。模型检查、定理证明或其他形式验证需求不在本技能范围内，也不能由普通类型检查结果冒充。

## 与相邻方法分工

- [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 负责判断类型建模是否形成独立目标和证据边界；本技能不把普通声明升级为重型方法。
- [spec-driven-development](../spec-driven-development/SKILL.md) 负责 Requirements → Design / Plan → Tasks → Implement / Evolve。规格可以派生类型建模单元，但两种方法不共同拥有同一工作单元。
- [property-based-testing](../property-based-testing/SKILL.md) 验证可信运行时值上的算法、解析器和状态机属性，不重复生成只会检查类型形状的值。
- [behavior-driven-development](../behavior-driven-development/SKILL.md) 验证业务角色可观察的结果，不检查内部类型声明。
- [consumer-driven-contract-testing](../consumer-driven-contract-testing/SKILL.md) 验证跨进程、跨版本的真实协议兼容；共享或本地类型不能替代提供方验证。
- [contract-verification](../contract-verification/SKILL.md) 调查外部 SDK、框架或协议实际如何工作；本地声明不能证明第三方行为。
- [verification-before-completion](../verification-before-completion/SKILL.md) 把“类型约束成立”的声明映射到当前严格静态检查和必要契约证据，不重复本技能的建模流程。
