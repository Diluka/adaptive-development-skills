# Source Repo Study：源码仓库研究

## 核心原则

从具体问题出发建立可追溯的系统模型，不按目录罗列文件。先确认研究所针对的仓库、分支或提交和适用配置，再从真实公共入口与装配路径沿控制流和数据流追踪；读到足以回答问题时停止，不把全面扫描当成完整性。

默认只读研究并直接回答。除非用户要求或项目规范要求持久保存，否则不创建 `wiki/`、`index.md`、`log.md`、图表文件或其他调查产物，也不修改实现。需要长期维护的正式文档时配合 [project-documentation](../project-documentation/SKILL.md)。

## 选择研究模式

只选择回答当前问题所需的模式；需要组合时说明各模式的范围，不要求先做完整地图。

| 模式 | 适用问题 | 主要结果 |
|---|---|---|
| 地图 | “这个仓库由什么组成、主要入口和边界在哪里” | 子系统职责、公共入口、装配关系、关键运行流、存储与外部边界 |
| 专题研究 | “某个功能、概念或机制到底如何工作” | 从入口到副作用的纵向切片、必要机制、状态与所有权 |
| 演进 | “现在为何如此、何时改变、旧行为与当前行为有何差异” | 当前基线、关键变更、版本差异及有证据支持的原因 |

地图模式按职责和运行关系组织结果，不生成文件树注释。专题研究优先围绕一个可回答的问题收敛。演进模式先弄清当前实现，再使用历史解释变化，避免用旧代码代替当前事实。

## 建立证据边界

开始追踪前明确问题、研究范围、当前分支或提交，以及会改变可达路径的构建目标、配置、功能开关、部署版本或运行环境。缺少这些信息但不影响主结论时继续研究并标注边界；只有不同选择会实质改变答案时才请求澄清。

按证据强度区分结论：

| 分类 | 使用规则 |
|---|---|
| 已确认事实 | 可由当前源码、装配、版本历史或运行时观测直接定位；给出精确来源 |
| 证据支持的综合 | 由多个事实连接而成；说明推导关系，不伪装成源码原话 |
| 假设 | 尚缺决定性证据；写明缺口和最便宜的验证方式 |
| 门控行为 | 只在特定配置、功能开关、版本、环境或调用路径下成立；明确条件 |
| 缺失实现 | 在已声明的搜索边界内只有接口、调用或文档而没有可达实现；说明排查范围，不能仅凭一次文本搜索下结论 |

源码注释、测试和项目文档都是线索，但可能过时。已部署产物、实际路由或依赖解析、日志、跟踪、指标和只读数据状态等运行时证据可以纠正静态推断；注明观测环境与时间，区分当前部署和当前工作树。未经授权不访问受限环境，且不得写入正式环境数据源。

## 追踪当前系统

1. 从公共导出、HTTP 或消息入口、CLI、启动流程、计划任务和后台消费者中定位真实入口；优先使用仓库已有语义索引或调用图，再用源码搜索补足动态路径。
2. 检查入口如何被装配：模块注册、依赖注入、路由、插件、生成代码、配置与功能开关可能决定哪个实现实际可达。
3. 沿编排进入领域规则，记录关键输入、状态转换、不变量、错误与返回路径，以及职责由哪个模块或进程拥有。
4. 继续追到持久化、事务、缓存、事件发布与消费、后台任务、重试和最终副作用；只展开与问题相关的分支。
5. 标出外部服务、SDK、框架和协议边界及项目实际使用的版本。真实契约仍不确定时转用 [contract-verification](../contract-verification/SKILL.md)。
6. 从可观察副作用、反向调用方、代表性测试或运行时产物交叉核对主路径，主动寻找能推翻当前模型的分支。

动态分派、反射、代码生成、约定式加载和部署配置可能让静态调用图不完整。找不到直接调用者时先检查这些机制，不把静态不可见等同于不可达。

## 解释专题机制

专题需要教学式展开时，按下列逻辑组织，而不是逐文件复述：

1. 提出源码正在回答的问题；
2. 给出能解释主路径的最简单模型；
3. 找出会破坏简单模型的真实约束；
4. 说明代码为这些约束引入的必要机制；
5. 用一次具体运行流串起入口、状态变化和副作用；
6. 总结所有权、取舍和仍未覆盖的边界。

只解释当前问题实际涉及的层次。概念名、符号和流程应对应源码，不为了讲解完整而虚构抽象、意图或设计理由。

## 研究历史演进

以当前可达实现为基线，使用 `git log`、`git log -S` 或 `-G`、`git blame`、`git show`、标签、发布说明和迁移记录定位关键变化；遇到移动或重命名时跟随文件历史。围绕行为、契约、所有权或数据模型的差异选择提交，不输出无关的提交年表。

提交内容可以证明“改了什么”，提交信息、关联决策或问题记录才可能解释“为什么”。原因没有直接证据时标为综合或未知；不要从作者、时间接近或最终代码反推意图。

## 方法边界

- 目标是理解现有系统时使用本技能；症状原因不明并需要因果证明时使用 [systematic-debugging](../systematic-debugging/SKILL.md)。
- 需要用可丢弃试验判断技术可行性、性能或集成形态时使用 [technical-spike](../technical-spike/SKILL.md)。
- SDK、框架、协议或外部服务的真实行为不确定时使用 [contract-verification](../contract-verification/SKILL.md)。
- 需要设计或审查目标架构时使用 [architecture-design-review](../architecture-design-review/SKILL.md)；同时需要现状与目标方案时，先完成源码研究，再把已确认模型作为架构审查输入。
- 需要保留研究结果时使用 [project-documentation](../project-documentation/SKILL.md)，只整理有长期价值的内容，不把过程日志整体转成正式文档。

若请求还包含修复或实现，把研究结论返回当前开发工作单元并遵守其范围与生命周期，不因发现相邻问题擅自扩展修改。

## 交付结论

默认回答包含与问题相称的简短结论、适用范围或版本、关键运行流、证据分类、未知边界和精确源码引用。源码引用至少给出路径与行号或稳定符号；历史结论给出提交标识；运行时证据给出来源、环境和时间。让读者能够从结论回到证据，而不是用大量引用代替解释。
