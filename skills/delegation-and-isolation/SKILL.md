# 委派与隔离

## 什么时候需要隔离

工作树隔离的是 **Git 状态与文件**，用于存在**多个并发写入者**时。创建、进入或复用工作树不要求新会话。改动小、风险低本身不构成创建工作树的理由——是否需要隔离取决于**有没有并发写入者**，以及失败后能否在当前工作区安全回退。

用户或仓库未指定位置且确需隔离时，默认放在根工作树下的 `<repo>/.worktrees/<name>`。根路径已检出当前任务的开发分支时，先确认状态；存在未提交改动且归属不明时停止自动迁移并报告，不用隐式 stash 或临时提交制造干净状态。创建失败时报告准确错误，不用 `--force`、分支重置或删除其他工作树绕过。

## 工作树不隔离什么

每个工作树有独立的工作目录、索引与检出状态，但**共享**分支与远端引用、对象库、仓库配置与钩子、`refs/stash` 与工作树注册信息。端口、进程、数据库、外部服务等运行资源**不会自动隔离**，必须单独协调。

## 判断能否并行

对每一对候选单元核对：信息（不等待对方决策）、写入（不共享文件、生成物、迁移序列、运行资源）、契约（共享接口已固定）、顺序（任一先完成不会使另一失效）、集成（协调者能组合并验证）。任一答案不确定时，缩小范围、把一方改成只读、使用独立工作树，或顺序执行。测试需要实现完成后才有稳定输入时属于顺序协作，不伪装成并行。

## 委派与回报

- 委派说明固定：工作单元与主要方法、共享目标、读写边界、角色产出、停止条件、验证责任，以及是否授予局部编排权。
- 被委派者只回报新事实、**实际差异**与验证结果，不报成功摘要；单元外发现只回报定位与最小说明，不擅自扩大范围。
- 协调者读取实际文件，在所有写入停止后的**组合状态**重跑验证；不把执行者的成功摘要当作验证。
- 实现者与评审者不能是同一执行者。需要独立判断时，各执行者回报前不读取对方结论，由协调者比较。

## 边界

症状可能共享根因时先定位根因，不让多个执行者同时试修。最终 Git 交付由协调者在组合验证后完成；执行者不独立持有提交、推送或 PR/MR 轨道。合并、发布、部署、正式环境写入与权限修改不因委派而获得授权。
