# Dependency Upgrade：依赖升级

## 核心原则

修改项目实际解析的依赖图。在使用通用升级建议前，先尊重项目锁定的包管理器与运行时。

## 确定当前依赖图

读取而不是假设：

- 仓库说明与工作区边界；
- 清单文件中的包管理器、引擎、运行时与工具链锁定；
- 已安装 CLI 和运行时版本；
- 锁文件格式与工作区配置；
- 直接、传递、可选与对等依赖关系；
- 现有覆盖规则和解析规则及其原因；
- 真实导入、二进制、构建插件与运行时调用方；
- 包注册源、完整性元数据、生命周期脚本、原生构建钩子，以及新增的受信维护者或命名空间。

使用项目包管理器提供的依赖图、`why` 或 `explain` 能力证明依赖归属；具体命令以当前项目安装版本的 `--help` 为准。

## 规划最小升级单元

1. 确认改动原因与受影响的运行时边界。
2. 阅读确切起止版本的发布说明与迁移指南。
3. 检查对等依赖范围、引擎要求、锁文件兼容性与已发布包内容。
4. 优先使用正常解析；只有已验证且无法正常解决的传递依赖冲突才添加覆盖规则，并记录移除条件。
5. 只改该单元必需的清单文件、导入、配置与锁文件条目。
6. 用 [contract-verification](../contract-verification/SKILL.md) 验证变化的边界，再运行定向构建、类型检查、测试与运行时冒烟测试。

删除依赖前先用 [caller-driven-cleanup](../caller-driven-cleanup/SKILL.md) 追踪源码、脚本、插件与运行时加载。

## 安全规则

- 不得把宽泛的 `audit fix`、`--force` 或类似修改当作升级策略。
- 不得自动执行 `git stash`、删除分支、重写无关锁文件区段或切换包管理器。
- 不因技能偏好新版本就升级运行时或包管理器。
- 依赖解析与安装脚本只能在项目隔离的开发或 CI 环境中执行，不在正式环境主机执行。
- 执行前审查新增或变化的生命周期脚本与原生脚本；若需要任务未授权的凭据、主机权限、注册源信任或原生工具链，应停止并报告边界。
- 区分既有失败与本次依赖回归。
- 保留正常工具生成的来源和完整性元数据。

## 示例

仓库锁定包管理器主版本时，即使全局环境存在更新版本也使用项目锁定版本。检查对等依赖图，选择最小兼容目标，并验证真实插件和运行时链路；不要按最新默认值机械重写现有包管理器配置。

## 常见错误

- 不运行解析器就手改锁文件。
- 没有兼容证据却升级相邻包。
- 用覆盖规则隐藏直接对等依赖不匹配。
- 只看源码导入就判断包未使用。
- 把安装成功当成运行时兼容。
