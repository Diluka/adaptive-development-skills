# 正式文档维护方法

正式项目文档记录需要长期维护的项目事实。只有用户要求保留，或项目规范要求维护时，才创建。准备纳入版本控制的文档属于开发任务，按主技能正文的
Git 交付边界定级与交付；位置规则见主技能正文（用户指定 > 项目规范 > 正式
`docs/`）。不要把正式文档放进忽略目录，也不要提交临时过程记录。决定长期保留调查草稿时，先按准备保留的实际增量转换并定级，再整理进正式目录。

## 选择内容

| 文档类型        | 按用途与适用性说明的核心内容                                                                                                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 需求文档        | 目标、范围、可观察结果、验收标准、约束和未决问题；需要以可演进规格贯通需求、设计、任务和实现时，规格链由 [spec-driven-development](../../spec-driven-development/SKILL.md) 拥有，本方法不重复维护需求条目 |
| 设计文档        | 当前事实、选定方案、组件或数据流、关键契约、权衡、风险和回退                                                                                                                                                      |
| 接口文档        | 使用方与提供方、输入输出、错误语义、鉴权、版本和兼容性约束                                                                                                                                                        |
| 规格文档        | 需求到实现的规格链（随演进同步维护），内容与归属见 [spec-driven-development](../../spec-driven-development/SKILL.md)                                                                                              |
| 决策记录（ADR） | 背景、决策、替代方案、理由和后果；进入版本控制后经历提出、接受/拒绝、弃用等生命周期，弃用记录仍保留供追溯                                                                                                         |
| 实施或迁移文档  | 工作单元、依赖、验证、发布、回退和剩余风险                                                                                                                                                                        |
| 交付对外文档    | 面向外部读者（用户、客户、发布说明、API 使用者）：目标读者、可观察行为、变更与兼容性影响、升级或使用方式                                                                                                          |

范围优先由目标、影响和约束正向界定；只有在用户明确否决相关方案，或相邻方案可能被合理误解为范围内且会改变实施、验收、授权或契约/兼容性判断时，才记录具体排除边界。

只创建需要的文档。内容跨类型时，根据项目现有形式和维护成本决定合并或拆分，不生成固定套装或占位文件。

## 编写与维护

1. 明确读者、用途和长期保存范围，只澄清会实质改变内容或结构的歧义。
2. 从当前代码、已有文档、真实调用方和依赖契约收集事实；把未确认内容标为假设或未决问题。
3. 优先更新已有事实来源，避免创建相互竞争的副本。
4. 保留 API、命令、路径、字段和符号的精确写法；实现改变需求、设计或接口时同步更新文档。
5. 确认路径未被忽略，验证内容、链接和事实；任务级别或具体风险要求时，再让未参与编写的独立子代理评审最终差异。

## 文档原则

- **正式文档描述项目当前状态，不讲述历史**：需要演进记录时用 ADR
  或规格链的演进机制，不把历史叙事写入正式文档正文。
- 不得写入凭据、个人信息、正式环境敏感数据或安全绕过细节。
- 不得虚构接口、日期、负责人、状态或验收结果，也不要复制可由代码或生成器可靠产生的大段内容。
