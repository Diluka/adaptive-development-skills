# 项目文本

帮助撰写和维护项目中的文本交付物，涵盖产品界面文案、源代码内文字、项目文档及协作记录和评论。按读者、载体和用途选取事实来源；区分文本草拟、仓库写入与对外发布的授权。普通代码任务不自动要求补写文档、注释或说明。

## 表达方式

- 围绕读者目标，直接说明已选路径、应有行为和预期结果。
- 省略无关的防御性说辞，以及讨论中已否决、且不影响当前范围、行为、验收、授权或风险的方案和“不要做 X”式排除条款。重新提及会把这些选项带回文本，使读者或后续代理误以为它们是当前约束，进而围绕无关选项补出没有依据的要求和说明；只有排除项确实改变上述边界时，才按事实简要说明。
- 将正反交叉句改写为说明目标路径、适用条件和动作边界的正向表达。
- 安全边界、真实限制、拒绝项和负向行为按事实清楚记录，措辞明确并提供安全可行的后续路径；保持风险与授权边界准确。

## 文本类型与事实来源

文本用途和载体决定读者目标及优先核对的证据，不要求套用固定模板：

- **产品与界面文案**：产品介绍、功能说明、标签、空状态、错误提示和通知以已确认的产品目标及实际行为为据；写清适用条件，不承诺尚未实现或未获确认的能力。
- **源代码与工具文本**：代码注释、日志、错误信息和工具帮助以当前实现、真实调用方及外部契约为据；注释解释有维护价值的理由或约束，提示文本准确反映实际状态。
- **项目文档与管理记录**：需求、路线图、计划、进度、验收与决策记录围绕已确认的目标、范围和决定；架构、接口、开发与使用指南、部署和排障材料按读者任务核对当前代码、配置、外部契约和目标环境。区分建议、假设、当前状态、目标设计、承诺与未决事项；README 与 AGENTS.md 的具体职责见下文。
- **协作平台文本**：Issue、Pull Request（PR）、Merge Request（MR）的正文、评论与评审讨论，以及提交和发布说明，依据原始请求、当前差异、已观察事实与适用检查。区分事实、建议、决定和未决项，不把猜测或未完成的验证、合并、发布写成既成事实。草拟与平台发布是不同动作；创建、修改或发表评论须有明确授权。
- **团队与外部沟通**：状态更新、项目公告、邮件和支持回复面向具体接收者，依据已确认事实与承诺，标出未决事项。草拟与发送是不同动作；外发文本须有明确授权。

## README 与 AGENTS.md

两者面向不同读者，应互补而不重复；按项目实际需要组织，不要求填满固定模板。

- **README.md 面向项目使用者**：简洁说明项目用途与主要能力，引导读者完成适用的安装、快速开始和后续阅读。只写项目确实支持的内容；若许可证、贡献、变更记录等已有独立文件，不在 README 重复。使用 GitHub Flavored Markdown；仅在能突出重要说明时使用提示块，项目已有且合适的标识图时可用于标题，不为装饰新增图案。
- **AGENTS.md 面向编程代理**：补充 README 不适合承载的仓库专属技术背景和可执行约束。根目录放置全仓通用说明；只有子项目确有独立命令或规则时才增加嵌套文件。根据实际情况写明目录/技术边界、环境设置、开发与测试命令、代码约定、构建、安全或交付要求；不适用的章节省略，避免照抄模板或 README。
- **命令与约束必须有据可查**：从清单、脚本、CI、配置和现存权威文档核对技术栈、前置条件、命令及其范围；仅在确实运行并成功时声称命令已验证。不要臆造覆盖率门槛、部署步骤、平台行为或项目能力。

- 用户指定位置优先，其次项目现有规范。一个稳定事实只在**一个权威位置**完整解释，其他地方只给摘要与链接；优先修订已有权威位置，不新建职责重叠的文件。
- 从当前代码、真实调用方、外部契约与原始来源取证，标注影响结论的版本与适用范围，区分已确认事实、综合判断与仍无法裁决的冲突。
- 忠实记录真实负向行为、安全与权限限制；事实内容以已核实的接口、日期、状态和验收结果为准，并保护凭据与正式环境敏感信息。
- 临时草稿与调查记录按其载体和授权处理；决定长期保留时，核实证据并整理到相应权威位置。

完成时核对文本能否完成读者目标、事实与状态是否准确、载体格式及引用是否适用；对外发布前确认授权和目标位置。格式与链接检查不能代替事实核验。
