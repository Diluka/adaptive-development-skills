# Technical Spike：技术探索

## 核心原则

用可丢弃证据回答一个未知问题。技术探索用于降低不确定性，不是提前编写正式实现。

独立技术探索的交付结果是结论和证据。即使为此编写最小示例、探测脚本、临时原型、复现代码、实验测试或诊断插桩，只要这些临时产物不会被项目保留、集成、提交或交付，它就不是开发任务，不触发开发任务的强制计划和最终独立评审。

如果技术探索是“调查并完成实现”这类既有开发任务中的工作单元，它继续受该任务的共享计划和授权边界约束；临时探索代码本身不单独评审，最终准备交付的项目差异统一接受独立评审。

## 定义试验

编写原型前记录：

- 一个决策问题；
- 最小且具有代表性的输入与环境；
- 代表成功、失败和无法判断的观察结果；
- 时间或范围边界；
- 禁止的副作用，包括正式环境写入与未授权远端变更；
- 原型如何丢弃或隔离。

若预期行为已明确、只剩实现，使用 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 选择常规方法。

## 运行最小探测

优先顺序：

1. 检查确切的已安装依赖或现有运行时证据。
2. 运行最小命令、请求或独立程序。
3. 使用可丢弃测试夹具或隔离分支、工作树。
4. 性能问题使用代表性数据做基准测试。

不要加入生产架构、通用选项、穷尽测试或无关打磨，只增加回答问题所需的观测代码。

把临时产物放在项目指定的实验位置、临时目录、沙箱、实验分支或可丢弃工作树。不得覆盖、清理或混入用户已有改动；不得把临时依赖声明、锁文件、配置、生成产物或诊断插桩留在准备交付的项目差异中。

使用临时凭据与非敏感的代表性数据。不得把正式环境凭据或真实机密数据放进原型、测试夹具、基准测试、日志或生成产物。若探测只能通过修改远端系统执行，必须取得对精确操作与安全环境的授权，否则报告证据缺口。

问题涉及 SDK 或协议时，仅使用 [contract-verification](../contract-verification/SKILL.md) 确认确切版本并运行最小安全探测，然后停在技术探索结论；除非生产实现另行请求，不得继续改代码或设计回归测试。

## 结束技术探索

| 结果 | 必须记录 |
|---|---|
| 可行 | 证据、约束与仍需完成的生产工作 |
| 不可行 | 观察到的阻碍与被否定假设 |
| 无法判断 | 缺失证据与下一个最便宜的试验 |

删除原型，或把它保留在明确的临时位置。结束时检查工作区，证明没有遗留准备交付的临时依赖、配置、锁文件、生成产物或代码差异。调查结论必须由运行结果、真实契约或其他证据支撑；复杂功能调研如果范围广、证据链长或容易偏离初始目标，可以按准确性收益选择独立评审代理检查目标覆盖和反证，简单调查不增加固定门禁。

如果决定把原型、脚本、测试、配置或其他实验内容保留为项目产物，立即停止把它当临时代码扩展，并转换为开发任务：

1. 创建或更新开发计划文档；
2. 明确哪些实验内容保留、重写或删除；
3. 为正式实现选择合适的主要开发方法；
4. 按业务影响、风险和授权边界判断是否需要用户确认；
5. 完成正式实现和验证；
6. 由未参与实现的独立子代理评审最终交付差异。

如果用户要求把调查结论整理成需要版本控制的正式项目文档，该文档本身是项目产物，也从准备正式文档时进入开发任务流程。不得静默把探索代码变成正式实现。

## 示例

确认某项依赖是否保持所需运行时保证时，针对项目锁定版本编写最小隔离探测，只观察这项保证；不要在技术探索中构建完整集成抽象。

## 常见错误

- 没有决策问题就开始编写代码。
- 过度简化的输入移除了真正未知的边界。
- 把时间限制当成预定答案的截止时间。
- 因原型偶然成功一次就直接发布。
- 把写临时代码等同于进入开发任务，或反过来把准备保留的原型继续当作临时调查。
- 调查结束后把临时依赖、锁文件、配置、插桩或生成产物留在项目差异中。
- 复杂调研明显存在偏航风险，却不评估独立检查能否提高结论准确性。
- 把无法判断当作可行性证明。
