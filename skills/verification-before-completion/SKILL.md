# Verification Before Completion：让证据匹配结论

## 核心原则

每项完成声明都需要能直接衡量该声明的最新证据。验证应与风险和范围成比例；通用全量测试命令既不总是必要，也不总是充分。

## 建立声明与证据映射

先写出准备声明的结论，再为每一项选择最小决定性证据：

| 声明 | 直接证据 |
|---|---|
| 行为已修复 | 已记录的修复前失败，或曾因目标行为失败的回归测试；随后通过真实接缝验证预期行为 |
| 测试通过 | 指定测试命令的最新输出 |
| 构建或类型检查通过 | 精确项目命令的最新输出 |
| 外部集成可用 | 已核实安装版本，加契约或集成探测 |
| 清理安全 | 调用方、导出与加载分析，加构建或保留路径的定向检查 |
| 生产事故已解决 | 当前部署状态和改动后的日志、指标或只读状态 |
| 差异干净 | `git diff --check`、状态，以及对相关已提交、已暂存、未暂存和未跟踪内容的审查 |
| 开发任务已完成 | 最终项目差异的相关运行验证，加未参与实现的独立子代理对同一最终版本的评审证据 |
| 调查已完成 | 原始目标、结论、直接证据、未决项，以及临时产物未遗留在项目差异中的证明 |

无法安全重现旧失败时，使用已有失败证据、根因证据和当前真实链路的验证，并收窄声明。绝不要只为证明修复而还原或部署旧代码、破坏工作状态、修改正式环境数据，或重新制造生产事故。

测试只是其中一种证据。通过的单元测试无法证明被跳过的框架、传输、包或部署边界。

## 运行最新且相关的检查

1. 解析仓库的真实命令和锁定工具链。
2. 运行覆盖已改工作单元的定向检查。
3. 当影响范围、共享契约、发布规则或用户要求值得更广范围时，再增加更广泛检查。
4. 阅读退出码和有意义输出；不要从静默或旧日志推断成功。
5. 区分本次改动引入的回归和已验证的既有基线失败。
6. 对开发任务确认独立评审发生在正式实现和相关验证之后；所有已接受的实质修复都已经重新验证并复审，评审后没有新的未验证项目产物差异。

不要为验证声明而修改正式环境数据。使用只读证据或可丢弃环境。

主代理自查、PR/MR 评审和运行时验证都不能替代开发任务的独立子代理评审，独立评审也不能替代运行时验证。如果环境无法创建评审子代理，只能声明“实现和验证完成，独立评审尚未完成”，不得声称整个开发任务完成。

非开发调查没有统一独立评审门禁。复杂功能调研如果已按偏航风险选择评审代理，则报告该证据；未选择时用目标覆盖、运行结果、真实契约和工作区清理证明支撑结论，不要虚构缺失的评审要求。

## 处理不完整证据

必需检查失败、超时、无法运行、只覆盖部分声明，或开发任务的最终独立评审尚未完成时，收窄声明并说明缺口。必需工作尚未完成时，不要描述为完成。

测试本身与需求冲突时，使用 [evidence-based-testing](../evidence-based-testing/SKILL.md) 调查；不要通过削弱真实不变量追求测试通过。

## 报告结果

说明命令或观测、运行时间、结果，以及它证明了什么。只有剩余风险会影响用户决策时才重点说明。

## 示例

删除包后，确认真实源码、脚本、插件或已发布导出都不再依赖它；运行包管理器正常解析和定向构建。通过的单元测试本身不能证明二进制产物或构建插件已消失。如果旧环境已无法安全恢复，就使用删除前调用方证据和当前保留路径检查，不要为了重现而重新安装旧包。

## 常见错误

- 不运行检查就说“应该会通过”。
- 只运行全量测试，却不验证真实外部边界。
- 复用最终编辑之前的输出。
- 开发任务只有主代理自查或运行时验证，却声称已经完成独立评审。
- 评审后修改最终项目差异，仍复用修改前的验证和评审。
- 把开发任务的评审门禁错误套到所有非开发调查。
- 把无关基线失败当成新回归，或以此为由忽略所有失败。
- 用笼统的“完成”隐藏未经验证的声明。
- 仅为证明修复而危险地重现旧失败。
