# Verification Before Completion：让证据匹配结论

## 核心原则

每项完成声明都要有能直接支撑它的最新证据。验证范围与风险相称；全量测试不一定必要，也未必充分。

## 映射声明与证据

| 声明 | 直接证据 |
|---|---|
| 行为已修复 | 修复前失败或根因证据，加真实接缝上的当前预期行为 |
| 重构保持行为 | 按风险选用或组合重构前后的同一核心测试、相同环境与输入下的可重复冒烟观测和结果对照 |
| 可复现输出保持稳定 | 同一真实执行路径生成的最小快照或行为基线，加对业务差异的审阅 |
| 主观或概率性结果改善 | 预先定义的代表性样例与评价标准，加重复或独立评估结果、已知波动和剩余不确定性 |
| 测试通过 | 指定测试命令的最新输出 |
| 构建或类型检查通过 | 精确项目命令的最新输出 |
| 外部集成可用 | 确切版本，加契约或集成探测 |
| 分支或合并结果通过 CI | 最终推送提交或合并结果对应的 CI 状态、必需任务和结论 |
| 清理安全 | 调用方、导出和加载分析，加保留路径检查 |
| 生产事故已解决 | 当前部署和改动后的日志、指标或只读状态 |
| 差异干净 | Git 状态、差异检查和对已暂存、未暂存、未跟踪内容的审查 |
| 功能收尾已对齐 | 本次变更直接影响的既有伴生产物，加对最小同步内容的审阅 |
| 开发任务已完成 | 当前增量的直接验证，以及任务级别或具体风险要求时适用的独立评审 |
| 调查已完成 | 原始目标、结论、直接证据、未决项和临时产物清理证明 |

无法安全重现旧失败时，用已有的失败或根因证据加当前真实链路验证，并收窄声明。不得为了证明修复而还原旧代码、破坏工作状态或修改正式环境数据。

## 运行检查

1. 明确当前完成声明、实际增量和可能失效的既有证据。
2. 复用适用输入、环境、版本、调用路径和风险面仍相同的测试、评审、观测或 CI。
3. 解析仓库真实命令和锁定工具链，只运行覆盖证据缺口的定向检查。
4. 从计划、变更路径及其已知引用中核对本次变更直接影响的既有维护文档、示例或说明，并审阅最小同步；不做全仓库资料清扫，也不修复本次变更未触及的历史问题。
5. 影响范围、共享契约、发布规则或用户要求值得时再扩大检查。
6. 阅读退出码和有效输出，区分本次回归与已确认的基线失败。

测试只是证据之一，证明不了被跳过的框架、传输、包或部署边界。验证完成声明时不要写正式环境数据。

先按 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 判断独立评审是否适用；适用时再按 [requesting-code-review](../requesting-code-review/SKILL.md) 核对受影响最终差异。只有改变既有结论或风险面的实质修改才使对应验证或评审失效，重新检查受影响范围；机械文档、格式或无语义冲突处理不使无关运行证据失效。缺少必要证据时收窄声明。非开发调查没有统一评审门禁，复杂调研只在实际选择了独立检查时报告该证据。

技能、提示规则或代理工作流属于启发式结果时，格式、引用和静态检查只能证明结构有效。代表性场景和子代理观察属于评估；子代理可能同时受已安装技能、系统规则和会话上下文影响，不能把单次模拟描述为隔离行为测试。明确评估限制，把安装后的真实任务表现和后续具体反馈作为实践验证，并据此继续迭代。

测试本身与需求冲突时使用 [evidence-based-testing](../evidence-based-testing/SKILL.md)，不要削弱真实不变量来追求绿灯。

## 报告

说明命令或观测、运行时间、结果及其支撑的结论。检查失败、超时、无法运行或只覆盖部分声明时，明确缺口，不把未完成工作描述为完成。
