# Project Documentation：维护正式项目文档

## 核心原则

正式项目文档记录需要长期维护的项目事实。只有用户要求保留或项目规范要求维护时才创建。准备纳入版本控制的文档属于开发任务，按 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 根据当前文档增量定级：微小文字修正可以直接修改和检查，复杂设计或跨契约文档才需要计划与独立评审。用户没有收窄交付时，正式文档与其他项目变更一样完成分支、提交、推送和 MR/PR 的普通 Git 交付；临时计划、调查记录和草稿即使写入文件，也不自动成为项目产物或触发 Git 交付。

## 确定位置

按以下优先级选择目录：

1. 用户明确指定的位置；
2. 项目现有文档规范和既有结构；
3. 没有约定时，正式文档使用 `docs/`，临时材料使用被 Git 忽略的 `.docs/`，其中计划位于 `.docs/plans/`。

不要把正式文档放进忽略目录，也不要提交临时过程记录。决定长期保留调查草稿时，先按准备保留的实际增量转换并定级；任务需要落盘计划时再使用 [writing-plans](../writing-plans/SKILL.md)，并只整理仍有长期价值的内容。

## 选择内容

| 文档类型 | 至少说明 |
|---|---|
| 需求文档 | 目标、范围、非目标、可观察结果、验收标准、约束和未决问题 |
| 设计文档 | 当前事实、选定方案、组件或数据流、关键契约、权衡、风险和回退 |
| 接口文档 | 使用方与提供方、输入输出、错误语义、鉴权、版本和兼容性约束 |
| 决策记录 | 背景、决策、替代方案、理由和后果 |
| 实施或迁移文档 | 工作单元、依赖、验证、发布、回退和剩余风险 |

只创建需要的文档。内容跨类型时，根据项目现有形式和维护成本决定合并或拆分，不生成固定套装或占位文件。

## 编写与维护

1. 明确读者、用途和长期保存范围，只澄清会实质改变内容或结构的歧义。
2. 从当前代码、已有文档、真实调用方和依赖契约收集事实；把未确认内容标为假设或未决问题。
3. 优先更新已有事实来源，避免创建相互竞争的副本。
4. 保留 API、命令、路径、字段和符号的精确写法；实现改变需求、设计或接口时同步更新文档。
5. 确认路径未被忽略，验证内容、链接和事实；任务级别或具体风险要求时，再让未参与编写的独立子代理评审最终差异。

不得写入凭据、个人信息、正式环境敏感数据或安全绕过细节；不得虚构接口、日期、负责人、状态或验收结果，也不要复制可由代码或生成器可靠产生的大段内容。
