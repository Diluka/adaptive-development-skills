# Project Documentation：维护正式项目文档

## 核心原则

正式项目文档是项目事实和交付产物的一部分。只有用户明确要求长期保留，或项目规范本身要求维护时才落盘；不要把每次澄清、分析或计划都升级成正式文档。创建、修改或删除准备版本控制的正式项目文档属于开发任务，需要计划、验证和最终独立评审。

## 与开发计划的关系

所有开发任务都由 [writing-plans](../writing-plans/SKILL.md) 在正式实现前创建计划文档。临时计划的创建、更新和状态同步是原任务的生命周期活动，不递归产生新的开发任务，也不会自动成为正式项目文档。

临时调查记录、技术探索结论、个人笔记和草稿的交付结果是结论或证据，不是项目产物；它们不因写入文件就成为开发任务。优先遵循项目的临时文档规范；没有约定时，计划缺省位于被 Git 忽略的 `.docs/plans/`，其他临时材料位于 `.docs/`。只有用户或项目要求长期保存时，才把其中仍有长期价值的需求、决策、接口或实施信息整理到正式项目文档目录。整理时去掉临时状态和过程噪声，不直接提交临时副本。

## 确定目录

按以下优先级选择位置：

1. 用户对当前任务明确指定的目录；
2. 项目现有文档规范、`AGENTS.md`、`README.md` 或既有目录结构；
3. 没有特别约定时使用 `docs/`。

`docs/` 只是正式文档的缺省目录，不得覆盖项目自己的规划。`.docs/` 是临时文档的缺省目录，应被 Git 忽略；不要把需要版本控制的正式文档放入其中。

若采用缺省结构，按需求主题组织多个相关文档：

```text
docs/<requirement-slug>/
├── requirements.md
├── design.md
└── interfaces.md
```

只创建实际需要的文件，不生成空目录、占位文档或固定文档套装。

## 选择文档内容

| 文档类型 | 至少说明 |
|---|---|
| 需求文档 | 目标、范围、非目标、可观察结果、验收标准、约束与未决问题 |
| 设计文档 | 当前事实、选定方案、组件与数据流、关键契约、权衡、风险与回退方式 |
| 接口文档 | 使用方与提供方、输入输出、错误语义、鉴权、版本与兼容性约束、必要示例 |
| 决策记录 | 背景、决策、替代方案、理由与后果 |
| 实施或迁移文档 | 工作单元、依赖顺序、验证、发布、回退与剩余风险 |

用户要求的文档类型优先。内容跨越多种类型时，可以拆分，也可以在一个文档内分节；以项目既有形式和后续维护成本决定。

## 编写与维护

1. 确认文档的读者、用途和需要长期保存的范围；只有会实质改变内容或结构的歧义才询问用户。
2. 从当前代码、已有文档、真实调用方和依赖契约收集事实。无法确认的内容标为假设或未决问题，不把猜测写成既定事实。
3. 先查找是否已有对应文档；同一事实优先更新现有来源，不创建相互竞争的副本。
4. 使用稳定标题和相对链接，保留 API、命令、路径、字段与符号的精确写法。
5. 实现改变需求、设计或接口时，同步更新文档；文档与实现冲突时重新核实事实，不默认任一方永远正确。
6. 确认正式文档路径未被忽略，并让文档随对应需求进入版本控制。按文档目标验证内容、链接和事实，再让未参与编写的独立子代理评审最终差异；提交、推送、合并或发布仍需遵守当前任务的授权边界。

临时草稿可以放在项目指定的临时位置；没有约定时使用 `.docs/`，其中开发计划使用 `.docs/plans/`。如果原任务只是调查，而后决定将草稿提升为正式文档，此时转换为开发任务：先创建或更新计划，明确正式文档范围，再删除过程记录、过时假设和敏感信息，按正式结构写入项目目录并完成验证与独立评审。如果正式文档本来就是既有开发任务的交付物，则只作为原计划中的工作单元处理。

## 安全与质量边界

- 不写入凭据、令牌、个人信息、正式环境敏感数据或可用于绕过安全控制的内容。
- 不复制可以从代码或生成器可靠产生的大段内容；记录稳定契约、来源和维护方式。
- 不为显得完整而虚构接口、日期、负责人、状态或验收结果。
- 不让文档提交夹带与当前需求无关的代码或资料。

## 常见错误

- 用户没有要求长期保留，却自动创建正式文档和提交门禁。
- 把每个开发任务都必须写的临时计划误认为必须版本控制的正式项目文档。
- 把临时调查记录当成正式项目产物，或在决定长期保留后仍不转换为开发任务。
- 因为改动只有文档，就省略最终独立评审。
- 项目已有文档规范，仍强制使用缺省的 `docs/` 或 `.docs/`。
- 把正式文档放进被忽略的临时目录，导致交接时丢失。
- 只新增文档，不在实现变化后更新它。
- 把讨论过程、个人笔记或未经验证的推测直接纳入版本控制。
