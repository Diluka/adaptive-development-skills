# 受控探索未知

## 核心原则

用可丢弃的试验与会话回答未知，让正式实现建立在已收敛的证据上。探索产物保持临时、隔离且可丢弃。

技术探索（technical spike）回答明确的可行性、性能或集成未知；探索性测试（exploratory testing）考察可运行系统的行为和风险。两者先形成结论与证据；用户同时要求实现时，证据收敛后按已确认目标、授权和目标仓库规则继续。

只在盘点当前上下文（包括同一会话）已有结论、证据、支持的推导和适用条件后仍有真实未知时开始探索。用户本人未知或使用“调查、求证”等动作词不等于代理仍未知；已有事实直接回答问题，或通过已确认不变量足以可靠推出答案时直接报告。用户明确要求新的实验、探索会话或记录时，把该过程或产物作为目标，并保持约定的范围与停止条件。

## 选择探索形式

| 问题 | 选择 |
|---|---|
| 技术可行性、依赖行为、性能或集成形态未知 | 技术探索，见下文“定义与运行试验” |
| 可运行产品的行为、交互、状态组合或用户风险未知 | 探索性测试，见下文“探索会话” |

已有症状的根因、外部契约核验、长期回归证据等不是探索形式，按目标条件路由，见下文“边界与转交”。

## 定义与运行试验（Technical Spike）

开始前写清：

- 一个决策问题。
- 最小且有代表性的输入和环境。
- 成功、失败和无法判断时各会观察到什么。
- 时间或范围边界，以及禁止的副作用和原型的丢弃方式。

预期行为已经明确且需要形成正式实现时，结束探索并用取得的证据直接进入实现。

运行最小探测：

1. 先检查确切的已安装依赖或现有运行时证据；适用条件未变且已有证据能回答决策问题时，记录结论并结束，不进入后续步骤。
2. 仍有真实未知时，再运行最小命令、请求或独立程序。
3. 必要时使用可丢弃测试夹具、沙箱、实验分支或工作树；性能问题使用代表性数据。
4. 每次探测只改变一个变量，用对照或基线隔离非目标因素；性能探索先记录现状基线，再与候选方案对照，避免把无关因素归因到被验证的未知。

只增加回答问题所需的观测，不加入生产架构、通用选项、穷尽测试或无关打磨。追加探测前说明哪种结果仍可能改变结论或决策；不存在这种结果时立即结束。

临时产物不得覆盖、清理或混入用户已有改动，也不得把临时依赖、锁文件、配置、生成产物或插桩留在最终差异中。使用非敏感代表性数据；正式环境写入、远端修改或额外权限必须取得精确授权，否则报告证据缺口。

试验结束后，按可行、不可行或无法判断记录证据、阻碍和缺失证据；只有决策问题仍无法回答时才记录下一个最便宜的试验。临时产物的清理与隔离见下文“交付与边界”。

决定保留实验内容或把结论整理为版本控制的正式文档时，立即停止把它当临时产物扩展，按“边界与转交”转交。

## 探索会话（Exploratory Testing）

开始前记录：

- 可观察的产品、版本、环境、入口和代表性数据。
- Charter：本次使命、关注风险、待回答问题和明确排除范围。
- 判断可接受与可疑行为的依据，以及已有脚本化检查覆盖的范围。
- 与问题规模相称的时间盒、记录方式和停止条件。
- 禁止的副作用、数据安全边界和所需授权。

执行探索：

1. 用现有说明、运行状态和已有检查建立足以开始的产品模型，选择第一个高价值探测。
2. 在会话中同步学习、设计测试、执行和解释结果；根据新信息调整输入、状态、顺序、交互和观测面。
3. 把已有脚本、自动化检查和工具当作探测手段，不把它们当成限制探索范围的唯一清单。
4. 追踪与 Charter 相关的新线索。范围外发现只记录必要证据，不静默扩大调查。
5. 区分直接观察、证据支持的推断和待确认问题。异常出现时，记录环境、前置状态、操作、输出和副作用，争取获得最小可复现条件。
6. 到达时间盒或停止条件时结束会话，即使仍有未知。获得稳定症状或最小可复现条件即结束探索：保留复现证据，使用 [systematic-debugging](../systematic-debugging/SKILL.md) 追踪根因。不要为了制造“完成”结论而补写未经观察的结果。

探索不是随意点击。测试者必须能解释当前选择与 Charter、产品模型或新证据的关系；发现数量、执行步数和通过率都不能代替学习价值。

会话记录至少包含 Charter、环境与版本、实际覆盖的风险区域、重要操作、观察结果、可复现问题、未确认线索和剩余未知。

会话后复盘实际执行了什么、发生了什么、学到了什么，以及哪些风险得到支持或削弱。记录妨碍有效探索的环境、数据或知识缺口，还需探索、澄清、诊断或实现的内容，以及对证据质量、覆盖边界和结论可信度的判断。复盘只确认调查结果，不授权实现、部署或外部状态修改。

## 交付与边界

交付问题或 Charter、适用环境、覆盖说明、关键观察或试验证据、复现证据、剩余未知、结论限制和建议的下一步。

### 边界与转交

| 结束条件 | 下一步 | 需要带回的事实 |
|---|---|---|
| 已出现明确症状、目标转为证明根因；或探索中获得稳定症状 / 最小可复现条件 | [systematic-debugging](../systematic-debugging/SKILL.md) | 症状边界、环境、复现步骤、最小条件与尚未解释的因果缺口 |
| SDK / 协议等外部契约或第三方边界仍不确定 | [contract-verification](../contract-verification/SKILL.md) | 真实调用位置、确切版本缺口、待核实边界与最小安全探测问题 |
| 已确认复杂、可重放的现有行为，需要长期回归基线 | [characterization-and-approval-testing](../characterization-and-approval-testing/SKILL.md) | 代表性发现、真实入口、可复现性和待保护行为 |
| 主观、多解或概率性质量需要持续改进 | [eval-driven-development](../eval-driven-development/SKILL.md) | 真实用途、代表任务、质量维度、风险边界和试验条件 |
| 需要正式修改产品，或把探索结论固化为正式内容 | 结束探索并进入对应实现或文档工作 | 准备保留的实际增量、授权边界、试验证据、依赖与剩余未知 |

探索结论、临时产物和正式实现保持可区分。建议、猜测或一次观察只作为相应强度的证据；用户要求实现时，在证据收敛后实施并独立验证正式变化。探索结束时清理或隔离临时产物，确认没有把探索代码混入项目差异。
