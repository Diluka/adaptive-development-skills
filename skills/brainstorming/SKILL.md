# Brainstorming：澄清关键设计选择

## 核心原则

只解决会改变方案的不确定性。如果需求、当前系统和适用契约已经共同确定一条安全路径，就直接推进，不要额外举行设计仪式。

## 澄清决策

1. 先检查相关仓库状态、真实调用方、不变量和依赖契约，再提出本地证据无法回答的问题。
2. 区分关键选择与实现细节。只有当不同答案会改变公开行为、数据模型、架构、不可逆操作或实质范围时，才把它视为关键选择。
3. 明确要做的决策、已经掌握的证据和剩余不确定性。
4. 只有确实存在不同可行路径时才提供选项。说明权衡并给出推荐；不要凑出三个只在命名上不同的方案。
5. 只询问最小的缺失决策。紧密相关的问题一起提出更清楚时，不必强行每次只问一个。
6. 记录选定的约束或成功标准，然后继续使用 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md)。若预期交付包含需要项目保留的产物，在正式实现前使用 [writing-plans](../writing-plans/SKILL.md) 把结论写入计划文档。

## 边界

- 对已经明确的编辑、可从仓库发现的事实、常规依赖操作或微小文档改动，不要触发本技能。
- 当实质选择已经确定时，不要要求额外批准实现方案。
- 不要强制创建设计文档或提交。开发任务必须写的计划文档不等同于设计文档；其他临时记录和正式项目文档仍遵循用户指定与项目现有规范，没有约定时分别使用被 Git 忽略的 `.docs/` 和版本控制的 `docs/`。
- 当缺失选择会改变用户意图、授予新权限或决定不可逆权衡时，必须询问用户，不要替用户猜测。
- 修改现有代码时，不要把无关的重新设计带入当前范围。

## 示例

对于“支持外部回调重复投递”，先检查提供方契约和当前幂等链路。如果尚未确定重复请求应返回原结果还是冲突，而且这个选择会影响调用方，就解释两者影响并询问该决策。如果契约已明确规定响应，则写入计划并按风险判断是否还需确认，不再要求额外设计批准。

## 常见错误

- 把每次代码修改都当成重新设计系统的机会。
- 向用户询问源码、配置或已安装依赖中已经存在的事实。
- 提供只有命名差异的伪选项。
- 在关键选择尚未确定前编写并提交推测性设计。
- 当答案已经不会改变方案时仍继续提问。
