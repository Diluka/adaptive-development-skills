# Brainstorming：澄清会改变方案的选择

## 核心原则

只处理会实质改变实施方向的不确定性。需求、当前系统和适用契约已经给出安全路径时，直接推进，不增加设计仪式。

## 判断与澄清

1. 先核对仓库状态、真实调用方、不变量和依赖契约，确认哪些问题不能由现有证据回答。
2. 只有不同答案会改变公开行为、数据模型、架构、不可逆操作或实质范围时，才把它当作关键选择。
3. 清楚列出待决事项、已知证据和剩余不确定性。存在多个真实可行路径时，说明取舍并给出推荐，不凑伪选项。
4. 只向用户询问最小的缺失决策；紧密相关的问题可以合并提出。
5. 记录选定的约束或成功标准，再通过 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 推进。有计划时把结论写入计划，否则保留在共享目标和约束中。

## 边界

- 能从仓库或依赖中查到的事实，先自行核实；已经明确的实现要求不需要额外批准。
- 缺失的选择会改变用户意图、授权或不可逆取舍时，必须询问用户。
- 不强制创建设计文档或提交。需要长期保存的内容使用 [project-documentation](../project-documentation/SKILL.md)。
- 不把无关的重新设计带入当前范围。
