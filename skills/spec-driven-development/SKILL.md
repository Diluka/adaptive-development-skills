# Spec-Driven Development：规格驱动开发

## 核心原则

把规格作为实现的主要依据，而不是完成编码后失去作用的说明。让需求、设计、任务和代码形成可追溯的推导链，并在实现发现、用户反馈或运行事实改变认识时共同演进。规格不必一次写到“完整”；达到足以安全推进下一阶段的清晰度后即可进入实现，再通过反馈持续收敛。

本技能定义开发方法，不替代调查方法、实现方法或生命周期支持。每个实施工作单元仍由 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 选择适合的主要方法。

## 检查前提

- 功能包含多个相关行为、技术边界或实施工作单元；
- 需求或设计需要迭代，多人、多代理或长上下文实施存在明显理解漂移风险；
- 可以识别目标、权威需求来源、主要约束和可观察结果；
- 维护规格推导链带来的收益高于创建和同步成本。

目标明确、局部可逆且能直接验证的改动直接实现。不要为了采用 SDD 给小改动补造完整规格。

## 推进规格链

1. **Specify / Requirements**：说明要解决的问题、为什么值得做、使用方、范围与非目标、可观察结果、约束、验收条件和未知项。保持“做什么、为什么做”与“如何实现”分离，不用看似合理的实现猜测填补需求空白。
2. **Design / Plan**：从已确认需求推导系统边界、数据与交互、关键契约、不变量、技术选择和验证策略。记录重要选择的依据，并让每个选择能追溯到需求或约束；架构职责不清时使用 [architecture-design-review](../architecture-design-review/SKILL.md)。
3. **Tasks**：把规格和设计分解为可独立推进、可观察完成且能够验证的工作单元。为每个单元保留需求、设计依据和完成证据的映射，不按文件列表机械拆分。
4. **Implement**：依据规格实施各工作单元，并保持任务与实现结果可追溯。根据行为、证据和风险分别选择直接实现、Type-Driven Design、属性测试、契约测试或其他方法；执行顺序、协作状态与交付安排仍由适用的生命周期支持负责。
5. **Evolve / Converge**：新事实出现时，判断它改变的是预期行为、设计策略、任务分解还是仅代码实现；更新最接近该事实的规格层，再传播到所有失配的下游或上游产物。继续实现前确认当前规格链描述的是准备交付的方向。

默认从需求进入设计；已有权威架构或不可变技术约束时可以先建立设计事实，但在任务分解前仍要补全并核对可观察需求，不能让既有设计自行定义业务目标。

## 从规格派生验收证据

把验收证据视为需求和设计的下游产物，不把它当作当前实现的附属说明：

1. 从已确认需求、设计约束和验收条件中选出待证明的可观察结果、真实调用方和具体失败风险，再通过 [evidence-based-testing](../evidence-based-testing/SKILL.md) 选择最小充分证据。
2. 让每份验收证据能够追溯到对应规格条目，并从保留目标风险的真实入口观察结果；不沿生产组件、类或函数列表逐层生成测试。
3. 只有低层规则具有独立稳定判据、不同失效面或必要定位价值时，才为它建立单独证据。需求级证据已经能拒绝同一错误时，不再为覆盖率或流程形式重复测试。
4. 实现与验收证据拥有独立产物、共享契约已经固定且能够安全隔离时，可以通过 [subagent-driven-development](../subagent-driven-development/SKILL.md) 和 [dispatching-parallel-agents](../dispatching-parallel-agents/SKILL.md) 拆成同步推进的工作单元。双方都读取同一规格链，验证者不从未完成实现反推预期；具体并行与组合验证由生命周期支持负责。

## 形成证据

至少保留以下可审查结果：

- 标明已确认内容、假设、未知项和非目标的需求规格；
- 从需求到设计决策、工作单元和验证方式的可追溯关系；
- 需求与设计条目到验收证据、实现结果及未覆盖风险的对应关系；
- 规格、设计、任务与当前实现的一致性检查及未收敛项；
- 需求或实现认识变化后，对受影响规格层的同步结果。

规格链证明意图、推导和当前实现方向一致，不能单独证明运行行为正确。运行证据仍由各实现工作单元选定的测试、评估、观测或真实链路验证提供。

## 排除与衔接

- 当前系统事实、依赖行为或技术可行性未知时，先使用适合的调查方法；不要在规格中把未知写成结论。
- 规格识别出可由类型表达的稳定不变量时，把它派生为独立类型建模工作单元并返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 路由到 [type-driven-design](../type-driven-design/SKILL.md)；不要以“类型也是规格”为由让两个方法共同拥有同一单元。
- 需要用真实业务示例形成共享行为理解时，为该行为切片建立独立 [behavior-driven-development](../behavior-driven-development/SKILL.md) 单元；把确认场景和自动化结果链接回规格链，SDD 不重复拥有同一行为实现。
- 只有关键选择会改变方案时使用 [brainstorming](../brainstorming/SKILL.md)；它不替代规格链。
- 需要协调顺序、负责人、共享状态或恢复上下文时使用 [writing-plans](../writing-plans/SKILL.md) 与 [executing-plans](../executing-plans/SKILL.md)；它们不定义需求和设计。
- 需要把规格、设计或决策长期纳入版本控制时使用 [project-documentation](../project-documentation/SKILL.md)；文档存放方式不决定是否采用 SDD。
- 不把工具专用命令、固定文件名、模板、审批门或分支规则写成 SDD 的通用必要条件。
