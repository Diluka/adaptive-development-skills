# Spec-Driven Development：规格驱动开发

## 核心原则

规格是实施的主要依据，应把需求、设计、任务和代码连成可追溯的推导链。实现发现、用户反馈或运行事实改变认识时，同步演进这条链。规格不必一开始穷尽细节；清晰到足以安全进入下一阶段后即可实施，再通过反馈收敛。

本技能只定义规格链。调查、实现和生命周期支持仍由 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 为各实施工作单元选择适合的主要方法。

## 检查前提

- 已有或将要产生规格文档（规格是高标准的正式技术文档，能承载完整规格链，不随便出现）——这是进入 SDD 的明确触发信号；
- 功能包含多个相关行为、技术边界或实施工作单元；
- 需求或设计需要迭代，且多人、多代理或长上下文实施存在明显的理解漂移风险；
- 能识别目标、权威需求来源、主要约束和可观察结果；
- 维护规格链的收益高于创建和同步成本。

目标明确、局部可逆且能直接验证的改动直接实现。不要为了采用 SDD 给小改动补造完整规格；规格是高标准正式文档，SDD 在自主决策时不常见。

## 推进规格链

1. **Specify / Requirements**：说明问题、价值、使用方、范围与非目标、可观察结果、约束、验收条件和未知项。把“做什么、为什么做”与“如何实现”分开，不用看似合理的实现猜测填补需求空白。
2. **Design / Plan**：从已确认需求推导系统边界、数据与交互、关键契约和不变量、技术选择及验证策略。记录重要选择的依据，并使其能追溯到需求或约束；架构职责不清时使用 [system-understanding](../system-understanding/SKILL.md)。
3. **Tasks**：把规格和设计拆成可独立推进、可观察完成且能够验证的工作单元。每个单元保留需求、设计依据和完成证据的映射，不按文件列表机械拆分。
4. **Implement**：按规格实施各工作单元，并保持任务与实现结果可追溯。根据行为、证据和风险选择直接实现、Type-Driven Design、属性测试、契约测试或其他方法；执行顺序、协作状态和交付安排仍由适用的生命周期支持负责。
5. **Evolve / Converge**：出现新事实时，先判断它影响预期行为、设计策略、任务分解还是仅代码实现。更新最接近该事实的规格层，再同步所有失配的下游或上游产物；继续实现前确认规格链仍描述准备交付的方向。

**演进模型边界**：本技能默认「原地替换（Replace-In-Place）」——一条规格链随认识演进，始终只有一个现行版本。对需要版本长期并存的领域（如多版本语言规格书），演进模型是「流式前进（Flow-Forward）」——多份规格并存、新版渐进取代旧版；「归档并扩展（Archive-and-Extend）」归档旧版、另起新版，介于两者之间。多规格并存是否适用取决于消费方是否同时读取多个版本；超出单规格链演进时，先确认规格文档的版本管理方式再开始。

**可执行 / 可测试规格**：规格条目须可执行——每项验收标准都应能直接转为测试或验证步骤，不写无法观察的承诺；规格链上的验收证据由此获得可运行判据。

默认从需求进入设计；已有权威架构或不可变技术约束时可以先建立设计事实，但在任务分解前仍要补全并核对可观察需求，不能让既有设计自行定义业务目标。

## 从规格派生验收证据

验收证据是需求和设计的下游产物，不是当前实现的附属说明。SDD 在这里只负责**证据映射**：从已确认需求、设计约束和验收条件中确定待证明的可观察结果、真实调用方和具体失败风险，让每份验收证据追溯到对应规格条目，并从保留目标风险的真实入口观察结果；不要沿生产组件、类或函数列表逐层生成测试。最小充分证据、证据独立性、真实接缝与是否追加低层证据等充分性细节由 [evidence-management](../evidence-management/SKILL.md) 负责，不在此重述。

实现与验收证据有独立产物、共享契约已固定且能安全隔离时，可通过 [agent-and-parallel-dispatch](../agent-and-parallel-dispatch/SKILL.md) 拆成同步推进的工作单元。双方读取同一规格链，验证者不从未完成实现反推预期；具体并行与组合验证仍由生命周期支持负责。

## 形成证据

至少保留以下可审查结果：

- 标明已确认内容、假设、未知项和非目标的需求规格；
- 需求、设计决策、工作单元和验证方式之间的可追溯关系；
- 需求与设计条目、验收证据、实现结果和未覆盖风险之间的对应关系；
- 规格、设计、任务与当前实现的一致性检查，以及未收敛项；
- 需求或实现认识变化后，受影响规格层的同步结果。

规格链证明意图、推导和当前实现方向一致，不能单独证明运行行为正确。运行证据仍由各实现工作单元选定的测试、评估、观测或真实链路验证提供。

## 排除与衔接

- 当前系统事实、依赖行为或技术可行性未知时，先使用适合的调查方法，不在规格中把未知写成结论。
- 规格识别出可由类型表达的稳定不变量时，派生独立类型建模工作单元，返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 路由到 [type-driven-design](../type-driven-design/SKILL.md)。类型也是规格，不意味着两个方法共同拥有同一单元。
- 需要用真实业务示例形成共享行为理解时，为该行为切片建立独立 [behavior-driven-development](../behavior-driven-development/SKILL.md) 单元。把确认场景和自动化结果链接回规格链，SDD 不重复拥有同一行为实现。
- 只有关键选择会改变方案时使用 [brainstorming](../brainstorming/SKILL.md)；它不替代规格链。
- 需要协调顺序、负责人、共享状态或恢复上下文时使用 [documentation](../documentation/SKILL.md) 与 [execution](../execution/SKILL.md)；它们不定义需求和设计。
- 需要把规格、设计或决策长期纳入版本控制时使用 [documentation](../documentation/SKILL.md)；文档存放方式不决定是否采用 SDD。
- 工具专用命令、固定文件名、模板、审批门和分支规则不是 SDD 的通用必要条件。
