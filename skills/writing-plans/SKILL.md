# Writing Plans：编写可修正的实施计划

## 核心原则

只在计划能降低协调、恢复上下文或风险控制成本时落盘。计划长短按任务复杂度决定，用来记录当前工作假设并让多代理保持一致。需求、不变量、真实调用方式、依赖契约和新证据始终优先。写计划不等于等待用户审批。

先按 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 判断任务类型、当前增量和级别。用户或项目明确要求正式计划时遵循；任务升级后首次满足落盘条件时再创建，不追补已经完成的微小流程仪式。只交付结论和证据的调查不需要开发计划。

决定保留调查产物时，停止扩展临时代码。准备保留的增量需要计划时，用本技能明确哪些内容保留、重写或删除。一开始就要求调查并实现时，调查只是适用计划中的一个工作单元。

计划的创建、更新、状态同步和处理评审意见都属于原任务，不递归产生新任务或新计划。

## 确定位置

按以下优先级选择目录：

1. 用户明确指定的位置；
2. 项目现有文档规范；
3. 没有约定时使用 `.docs/plans/YYYY-MM-DD-<task-slug>.md`，并确认 `.docs/` 被 Git 忽略。

需要计划的开发任务使用一份计划覆盖全部工作单元。需要长期保存时，通过 [project-documentation](../project-documentation/SKILL.md) 整理到项目正式文档目录；不要直接提交临时过程记录。

## 写出足够内容

计划至少包含：

- 目标与预期结果；
- 任务范围；
- 工作单元及各自的主要开发方法；
- 验证方式；
- 独立评审是否适用、依据及适用时的安排。

每个工作单元都必须能追溯到原始目标、明确需求、完成当前任务不可缺少的前置条件，或 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 定义的既有伴生产物最小同步。保留调用方、环境、版本和行为范围等限定词。

计划把已知且会因本次变更失真的伴生产物列入收尾对齐，不扩大到新建资料、无关章节或历史问题。不要把特定路径泛化为所有相似路径。判断为任务外的问题在取得新授权前不能成为工作单元，也不能通过写入计划获得授权。

计划只记录足以解释主要方法的证据，不扩写流程。为定向行为测试记录独立判据来源和具体回归风险；选择快照时，记录真实生成路径、稳定范围和差异审阅方式；评估模糊结果时，记录共享目标、样例或评价边界。直接实现不需要为了形式完整制造测试。

采用多代理协作时，再补充各角色的产出与独立读写范围。把实现与验证拆成并行单元时，还要记录双方共同读取的需求或规格条目、已确认行为与契约、验证所经真实入口及可观察结果、各自文件与运行资源、独立性依据和组合验证。验证工作不从生产组件或预计实现步骤反推测试清单。

复杂或高风险任务再补充依赖顺序、关键事实与假设、决策点、风险、回退、新增副作用、分工、评审深度、交付安排和仍需取得的授权。常规任务没有独立评审收益时，记录直接验证依据即可，不为填满模板派发评审。可以标注待探索范围，但不得编造文件、接口、行号或依赖行为。

## 决定是否等待确认

以下条件全部成立时，告知用户计划位置后直接执行，不把计划变成第二次批准：

- 原始请求已经明确授权目标行为、范围和交付结果；
- 没有尚未解决的关键取舍或歧义；
- 风险已有可执行控制，且未命中下列任一确认条件；
- 所有操作都在现有授权范围内。

除下节可以默认纳入的阻塞前置条件外，出现任一情况时，在实施前说明计划、取舍和风险并等待确认：

- 拟议方案偏离原始请求已授权的业务语义、公开行为、范围或交付结果；
- 存在尚未解决且会改变方案的需求取舍或关键歧义；
- 涉及高风险、破坏性操作或难以回退的变更；
- 涉及正式环境、非普通 Git 交付的外部写入、权限扩大或其他新增副作用。

计划不改变 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 的交付默认值：开发任务按实际 `git remote` 完成分支、提交、推送和 MR/PR，用户限制可以逐项收窄，非开发任务不自动产生 Git 交付。计划确认不会把合并、发布、部署、消息发送、正式环境操作、权限修改或其他高影响副作用纳入范围。

## 处理阻塞前置条件

已确认不处理就会阻止当前任务正确实现、验证或交付的问题，是当前任务的必要前置条件。加入计划前先发出非阻塞询问，说明阻塞证据、最小处理边界、风险和“未及时回复时将按默认方案继续”。等待期间继续执行不依赖它的工作。

用户未及时回复时，只有同时满足以下条件，才把最小必要处理加入计划并继续：处理方式由需求、真实调用方或契约约束；保持原目标和交付结果；可逆；仍在当前项目写入授权内；并且不涉及业务取舍、高风险或难以回退的操作、正式环境、非普通 Git 交付的外部写入、权限扩大或新增重大副作用。否则只暂停受影响路径，等待明确确认。

## 对齐与修正

多个执行上下文或工作树协作时，计划记录工作单元负责人、读写范围、依赖、共享状态、进展和待协调者决策事项。单个 Codex 任务内由根代理、多个独立工作任务协作时由协调任务维护唯一版本；子代理和独立工作任务只读取相关部分或不可变单元快照，回报新事实和证据，不并发改写计划。

工作树的建立、复用和所有权边界由 [using-git-worktrees](../using-git-worktrees/SKILL.md) 判断。跨工作树传递计划绝对路径前，先确认执行者所在宿主可以访问。

执行中新事实影响计划时：

- 目标、范围、业务行为、交付结果和授权不变，且没有新增副作用：更新计划，告知用户后继续；
- 新事实表明既有伴生产物会因本次变更失真：把最小同步补入收尾工作；仍满足上文直接执行条件时继续，否则请求确认并只暂停该同步路径，不按任务外发现处理；
- 新事实是阻塞当前任务的必要前置条件：按上节进行非阻塞询问，并在符合默认纳入条件且用户未及时回复时更新计划后继续；
- 改变上述任一边界或需要新授权：记录拟议调整，暂停相关实现并请求确认。

计划外发现先排除本次变更直接影响的既有伴生产物同步。剩余问题只有在不处理就会影响当前任务的正确实现、验证或交付时，才进入阻塞前置条件流程。其他问题保持在计划外，最多作为报告事项记录。
