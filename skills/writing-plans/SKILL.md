# Writing Plans：编写可修正的实施计划

## 核心原则

每个开发任务在正式实现前都必须有一份落盘计划。计划长短按任务复杂度决定，用来记录当前工作假设，并让多代理保持一致。需求、不变量、真实调用方式、依赖契约和新证据仍然优先。写计划不等于等待用户审批。

先按 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 判断任务类型。只交付结论和证据的调查不需要开发计划。决定保留调查产物时，停止扩展临时代码，并用本技能明确哪些内容保留、重写或删除。一开始就要求调查并实现时，调查只是开发计划中的一个工作单元。

计划的创建、更新、状态同步和处理评审意见都属于原任务，不递归产生新任务或新计划。

## 确定位置

按以下优先级选择目录：

1. 用户明确指定的位置；
2. 项目现有文档规范；
3. 没有约定时使用 `.docs/plans/YYYY-MM-DD-<task-slug>.md`，并确认 `.docs/` 被 Git 忽略。

一个开发任务使用一份计划覆盖全部工作单元。需要长期保存时，通过 [project-documentation](../project-documentation/SKILL.md) 整理到项目正式文档目录；不要直接提交临时过程记录。

## 写出足够内容

简单计划至少包含：

- 目标与预期结果；
- 任务范围；
- 工作单元及各自的主要开发方法；
- 验证方式；
- 最终独立子代理评审安排。

计划只记录足以解释主要方法的证据，不扩写流程。选择 TDD 时，记录独立判据来源和具体回归风险；选择快照时，记录真实生成路径、稳定范围和差异审阅方式；评估模糊结果时，记录共享目标、样例或评价边界。采用多代理协作时，再补充各角色的产出与独立读写范围。直接实现不需要为了形式完整制造测试。

复杂或高风险任务再补充依赖顺序、关键事实与假设、决策点、风险、回退、新增副作用、分工、评审深度、交付安排和仍需取得的授权。可以标注待探索范围，但不得编造文件、接口、行号或依赖行为。

## 决定是否等待确认

以下条件全部成立时，告知用户计划位置后直接执行：

- 不改变业务行为；
- 需求明确且没有关键取舍；
- 风险低、操作安全且可逆；
- 所有操作都在现有授权范围内。

出现任一情况时，在实施前说明计划、取舍和风险并等待确认：

- 改变业务语义、公开行为或交付结果；
- 存在会改变方案的需求取舍或关键歧义；
- 涉及高风险、破坏性操作或难以回退的变更；
- 涉及正式环境、外部写入、权限扩大或其他新增副作用。

计划确认不自动授权计划之外的提交、推送、合并、部署、消息发送或正式环境操作。

## 对齐与修正

多代理协同时，计划记录工作单元负责人、读写范围、依赖、共享状态、进展和待根代理决策事项。根代理维护唯一版本并提供精确路径；子代理读取相关部分、回报新事实和证据，不并发改写计划。跨工作树时传递协调计划的绝对路径。

执行中新事实影响计划时：

- 目标、范围、业务行为、交付结果和授权不变，且没有新增副作用：更新计划，告知用户后继续；
- 改变上述任一边界或需要新授权：记录拟议调整，暂停相关实现并请求确认。
