# Eval-Driven Development：评估驱动开发

## 核心原则

把评估作为开发方法，而不是实现完成后的附加检查：先用代表性任务和评价标准定义计划能力，建立基线，再实现并通过重复试验持续改进。结果可以有多个合理答案，但评价维度、失败影响和决策条件必须来自用户目标与真实用途，不能从候选实现反向发明。

本技能主导主观或概率性结果的开发工作单元。格式、安全、协议等确定性子不变量仍使用普通测试；[evidence-based-testing](../evidence-based-testing/SKILL.md) 负责判断哪些证据值得组合与长期保留，不在其中复制本技能的完整评估流程。

## 检查前提

开始前确认：

- 已定义计划能力、真实使用方、成功维度和高影响失败；
- 能从真实用途、人工检查、历史问题或代表性风险建立初始任务；
- 能在足够稳定且相互隔离的环境中运行候选，并记录每次执行；
- 至少有一种与实现相对独立的评价依据，并能校准主观评价；
- 可以记录模型、提示、工具、代理框架、数据和环境版本；
- 评估成本、正式环境数据和外部副作用处于授权边界内。

技术可行性或评价机制本身仍未知时，先使用 [technical-spike](../technical-spike/SKILL.md)。目标和质量维度仍存在会改变方案的关键歧义时，返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 选择定义与设计方法，不让评价器替用户决定需求。

## 建立评估模型

统一使用以下概念：

| 概念 | 含义 |
|---|---|
| 任务 `task` | 具有明确输入和成功条件的单个评估问题 |
| 试验 `trial` | 候选对一个任务的一次独立尝试 |
| 评价器 `grader` | 对表现的一个维度评分或判断的逻辑 |
| 轨迹 `transcript` / `trace` / `trajectory` | 一次试验中的输出、工具调用、中间结果和交互记录 |
| 结果状态 `outcome` | 试验结束时环境中的真实最终状态 |
| 评估工具链 `evaluation harness` | 运行任务、隔离环境、记录、评价和汇总结果的基础设施 |
| 评估套件 `evaluation suite` | 衡量一组相关能力或行为的任务集合 |

评估对象是模型与代理框架的组合。不能只根据候选声称完成的文本判断成功；真实结果状态能够验证目标时，优先评价结果状态，并用轨迹解释过程与失败。

## 建立初始任务集

1. 从开发期间已有的人工检查、真实用户任务、已确认问题和高影响失败中收集任务。
2. 同时覆盖行为应当发生和不应当发生的情况，并按重要风险、用户类型和输入结构保持合理平衡。
3. 让任务说明、可用工具、环境和成功条件一致；评价器检查的要求必须对候选可见，不能使用隐藏假设制造失败。
4. 可行时提供一个已知可行的参考结果，证明任务能够完成且评价器配置正确。
5. 记录任务来源、适用范围和加入理由。持续吸收新的真实失败，不围绕一组固定样例单向优化。

任务应足以区分合理质量差异，但不能规定真实目标不要求的具体实现路径。两名合格领域人员无法独立形成相近判断时，先澄清任务或评价维度，不把歧义转换成分数噪声。

## 设计与校准评价器

- 能用稳定不变量判断时使用确定性评价器；需要语义或质量判断时使用基于模型的评价器；高风险、强主观或需要校准时使用领域人员评价。
- 把多维结果拆成清晰、结构化的评价量表，分别评价任务完成、质量、安全、交互或其他真实维度；允许证据不足时返回无法判断。
- 优先评价产物和真实结果状态。只有工具选择、交互过程或资源使用本身属于需求时，才把轨迹行为纳入评分，避免惩罚未预见但有效的方案。
- 用领域人员判断校准基于模型的评价器，记录一致、分歧、偏差和不可靠区域。一次模型评分或一个独立代理意见都不是已校准评价。
- 阅读实际轨迹和评分，确认失败来自候选表现，而不是任务歧义、评价缺陷、环境噪声或工具链限制。
- 防止候选绕过评价器取得虚假高分；通过评价必须真实完成任务，而不是迎合表面检查。

暂定评价量表是开发证据，不自动成为确定性产品契约。只有经过反复验证的稳定不变量才转成长期自动化测试。

## 建立基线与重复试验

在正式改动前运行当前候选作为基线；新能力尚不存在时，低通过率同样是有效起点。每次试验从独立、可比较的环境开始，并记录任务、候选版本、模型与工具配置、轨迹、结果状态、评分、错误、延迟、令牌和成本。

概率性结果必须运行多次试验。次数按波动、失败影响和决策成本决定，不机械规定统一数量：

- 只要多次尝试中至少一次成功就有价值时，关注 `pass@k`；
- 每次都需要可靠成功时，关注 `pass^k`；
- 同时检查总体分布、重要风险切片、波动和具体失败，不用一个平均分掩盖局部退化。

基线只在任务、评价器、环境和候选边界可比较时有效。实质修改评估定义后，明确哪些旧结果失效，并重新建立受影响基线。

## 驱动实现迭代

1. 在实现前写清计划能力、初始任务、评价维度和决策条件。
2. 运行基线，检查任务可解、环境稳定、评价公平，并阅读代表性轨迹。
3. 实现当前能力所需的最小正式变化，不为刷分加入真实用户不需要的行为。
4. 对受影响任务执行重复试验，并同时运行仍覆盖相邻退化风险的回归证据。
5. 比较基线与候选的分布、切片、失败案例、成本和延迟；区分候选缺陷与评估系统缺陷。
6. 修正对应一方并记录理由；评估定义变化时重新判断历史结果的可比性。
7. 迭代到预定质量条件得到支持，同时报告仍无法稳定判断或仍有显著波动的区域。

能力评估可以从较低通过率开始，为改进提供方向；回归评估应覆盖已经可靠做到的行为。能力任务接近饱和后，把稳定任务转入持续回归套件，并用更有区分度的新任务继续衡量进步。

## 持续校准与交付证据

把评估套件作为需要明确负责人和持续维护的项目产物。适用时在每次相关改动或模型升级后运行回归评估；上线后的正式环境监控用于发现分布漂移和未预料失败，用户反馈、轨迹抽查和 A/B 测试补充自动评估，定期领域人员复核用于校准主观评价器。这些证据各自有边界，不能互相冒充。

正式环境观测不授权部署、流量实验或数据写入。只有原任务明确授权且安全边界成立时才执行外部操作；否则说明缺口并使用已有只读证据。

最终交付至少说明：

- 任务集来源、覆盖范围、成功条件和已知空白；
- 评价器、评价量表、校准方式、分歧和限制；
- 基线与候选的试验次数、结果分布、风险切片和代表性失败；
- 轨迹与结果状态如何支持结论，以及成本、延迟和错误变化；
- 达成或未达成的决策条件、剩余不确定性和后续维护安排。

开放式未知风险发现使用 [exploratory-testing](../exploratory-testing/SKILL.md)，已出现症状的根因调查使用 [systematic-debugging](../systematic-debugging/SKILL.md)，具有唯一稳定判据的确定性行为变更返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 重新选择开发方式。子代理可以提供独立证据设计或人工评价，但其角色隔离按 [subagent-driven-development](../subagent-driven-development/SKILL.md) 管理，不能替代评价器校准。
