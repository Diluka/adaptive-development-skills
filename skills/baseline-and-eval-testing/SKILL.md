# 基线比较与评估驱动

## 核心原则

对无法用唯一确定性断言验证的目标，用可审阅基线和代表任务评估取证。

基线方法（特征测试与批准测试）从真实执行中记录系统实际行为，再用差异审阅发现漂移。评估方法以代表性任务和评价标准持续驱动主观、概率性能力的实现与改进。基线与评估是本技能的两个紧密职责：前者保护行为漂移，后者驱动能力与回归，共享执行、记录与比较机制，故合并保留于同一技能。两者的证据都必须独立来自真实用途与需求；观察到的现状或候选实现不自动成为正确目标。

与验证节点的泛化框架（动态执行 / 静态检查 / 审视核对）对接：批准流程 = 动态执行捕获 + 审视核对批准；评估的评价器同样覆盖三类——确定性评价器对应动态执行，静态分析类评价器对应静态检查，人工与基于模型的判断对应审视核对。

## 基线与批准（Characterization / Golden Master / Approval）

从真实执行中记录系统实际产生的行为，再用可审阅基线发现后续差异。Characterization 描述当前行为，Golden Master 保存代表性结果，Approval Testing 负责比较、审阅和显式批准。三者都不能把观察到的现状自动宣称为正确需求。

建立基线前，确认：

- 能从真实入口执行代表性场景，并观察输出、状态或副作用。
- 结果能够稳定复现，或能在不改变业务语义的前提下清除无关噪声。
- 基线范围和差异足够清晰，评审者能够判断变化是否可接受。
- 敏感数据可使用非敏感代表值或安全脱敏，批准产物可以进入长期维护。

标准流程：

1. **选择特征范围**：根据真实调用方、失败影响和准备修改的路径选择少量代表性场景，记录入口、环境、输入和要观察的结果。行为保持型工作必须在修改实现前执行当前版本；未知行为标记为“已观察”。
2. **捕获真实结果**：通过生产执行路径运行场景，把实际输出、状态或副作用渲染为可比较的 received 结果。Golden Master 必须从执行生成，不能手写目标内容或从待实现设计复制预期结果冒充基线。
3. **稳定基线**：重复运行确认结果稳定。只清洗时间、随机标识、临时路径、无关顺序和敏感值等非业务差异，并保留清洗规则；若清洗会掩盖待保护行为，改用更窄的观察面或明确断言。
4. **审阅并批准**：比较 received 结果与现有 approved 结果。首次建立旧行为基线时，评审实际结果并显式批准；为新复杂输出使用 Approval Testing 时，先生成结果，再依据需求评估完整性后批准。第一次缺少 approved 结果只说明基线尚未建立，不能证明业务行为存在缺陷。
5. **修改后比较**：在相同环境、输入和入口重跑场景。非预期差异返回实现定位；预期差异先依据需求、真实调用方或已确认决策解释，再显式更新 approved 结果。不得批量接受新基线来消除失败。
6. **收敛长期保护**：随着行为被理解，把宽泛或难审阅的基线收窄为有业务意义的区域，必要时转换为更明确的语义断言。保留仍能发现合理漂移的最小基线，删除只记录噪声或已被更清晰证据完整替代的批准产物。

以下情况不适合基线与批准：

- 结果无法稳定复现，也没有安全的噪声隔离方式。
- 差异过大、不可读，或没有具备上下文的评审者。
- 目标是主观质量、概率性效果或多种合理答案，改用评估方法。
- 简单确定性规则已有独立判据，改用明确断言或 [property-based-testing](../property-based-testing/SKILL.md)。
- 目标是实现尚不存在的新行为。

## 评估驱动（Eval-Driven Development）

把评估作为开发方法，而不是实现完成后的附加检查。先用代表性任务和评价标准定义目标能力、建立基线，再实现并通过重复试验持续改进。结果可以有多个合理答案，但评价维度、失败影响和决策条件必须来自用户目标与真实用途，不能从候选实现反向发明。

开始前确认：

- 已定义目标能力、真实使用方、成功维度和高影响失败。
- 能从真实用途、人工检查、历史问题或代表性风险建立初始任务。
- 能在足够稳定且相互隔离的环境中运行候选，并记录每次执行。
- 至少有一种与实现相对独立的评价依据，并能校准主观评价。
- 可以记录模型、提示、工具、代理框架、数据和环境版本。
- 评估成本、正式环境数据和外部副作用处于授权边界内。

评价机制本身仍未知时，先使用 [unknown-exploration](../unknown-exploration/SKILL.md)。目标和质量维度仍有会改变方案的关键歧义时，返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 选择定义与设计方法。

| 概念 | 含义 |
|---|---|
| 任务 `task` | 具有明确输入和成功条件的单个评估问题 |
| 试验 `trial` | 候选对一个任务的一次独立尝试 |
| 评价器 `grader` | 对表现的一个维度评分或判断 |
| 轨迹 `transcript / trace / trajectory` | 一次试验中的输出、工具调用、中间结果和交互记录 |
| 结果状态 `outcome` | 试验结束时环境中的真实最终状态 |
| 评估工具链、评估套件 | 执行、记录和比较评估所需的系统与任务集合 |

评估对象是模型与代理框架的组合。真实结果状态能够验证目标时，优先评价结果状态，并用轨迹解释过程与失败。

建立初始任务集时：

- 从开发期间已有的人工检查、真实用户任务、已确认问题和高影响失败中收集任务；同时覆盖行为应当发生和不应当发生的情况，并按重要风险、用户类型和输入结构保持合理平衡。
- 让任务说明、可用工具、环境和成功条件一致。评价器检查的要求必须对候选可见；可行时提供一个已知可行的参考结果。
- 记录任务来源、适用范围和加入理由，持续吸收新的真实失败，不围绕固定样例单向优化。
- 初始任务集不求大：20-50 个来自真实失败的任务即可起步，随新失败持续吸收扩充。

任务应足以区分合理质量差异，但不能规定真实目标不要求的具体实现路径。

设计与校准评价器时：

- 能用稳定不变量判断时，使用确定性评价器；需要语义或质量判断时，使用基于模型的评价器（LLM-as-judge）；高风险、强主观或需要校准时，使用领域人员评价。
- 使用 LLM-as-judge 时，为每个评价维度分配独立 judge，依据结构化 rubric 评分；证据不足时返回「无法判断」，不硬凑分数。
- 把多维结果拆成清晰、结构化的评价量表，分别评价任务完成、质量、安全、交互或其他真实维度；多组件任务按可独立判定的组件分别评分、累计部分分，避免只判全对或全错。
- 优先评价产物和真实结果状态。只有工具选择、交互过程或资源使用本身属于需求时，才把轨迹行为纳入评分。
- 用领域人员判断校准基于模型的评价器，记录一致、分歧、偏差和不可靠区域。一次模型评分或一个独立代理意见都不是已校准评价。

阅读实际轨迹和评分，确认失败来自候选表现而不是任务歧义、评价缺陷、环境噪声或工具链限制，并防止候选绕过评价器取得虚假高分。

建立基线与重复试验：

- 在正式改动前运行当前候选作为基线。区分能力型 eval（衡量新能力上限，通过率从低值起步、随迭代提高）与回归型 eval（保护已有行为，通过率接近 100%，任何回退都须解释）；新能力尚不存在时，低通过率同样是有效起点。通过率持续为 0% 时，大概率是任务或评价器本身有问题，先修正任务与评价再谈能力。
- 每次试验从独立、可比较的环境开始，记录任务、候选版本、模型与工具配置、轨迹、结果状态、评分、错误、延迟、令牌和成本。
- 概率性结果必须运行多次试验，次数按波动、失败影响和决策成本决定。只要多次尝试中至少一次成功就有价值时关注 `pass@k`；每次都需要可靠成功时关注 `pass^k`。同时检查总体分布、重要风险切片、波动和具体失败。

基线只在任务、评价器、环境和候选边界可比较时有效。实质修改评估定义后，明确哪些旧结果失效，并重新建立受影响基线。

驱动实现迭代时：

1. 在实现前写清目标能力、初始任务、评价维度和决策条件。运行基线，检查任务可解、环境稳定、评价公平，并阅读代表性轨迹。
2. 实现当前能力所需的最小正式变化，不为刷分加入真实用户不需要的行为。
3. 对受影响任务执行重复试验，同时运行仍覆盖相邻退化风险的回归证据。
4. 比较基线与候选的分布、切片、失败案例、成本和延迟，区分候选缺陷与评估系统缺陷。修正对应一方并记录理由；评估定义变化时，重新判断历史结果的可比性。
5. 迭代到预定质量条件得到支持，同时报告仍无法稳定判断或仍有显著波动的区域。

当目标能力的任务集接近饱和时，把稳定任务转入持续回归套件，并用更有区分度的新任务继续衡量进步。把评估套件作为需要明确负责人和持续维护的项目产物；适用时，在每次相关改动或模型升级后运行回归评估。

上线后的正式环境监控用于发现分布漂移和未预料失败。用户反馈、轨迹抽查和 A/B 测试补充自动评估，定期领域人员复核用于校准主观评价器。这些证据各自有边界，不能互相冒充。

## 产出证据

- **基线**：场景、环境和输入，机器生成的 received 与 approved 结果或等价基线，稳定化规则、批准人可审阅的差异、修改后的比较结论，以及每次基线更新的依据。
- **评估**：任务集来源、覆盖范围、成功条件和已知空白；评价器、评价量表、校准方式、分歧和限制；基线与候选的试验次数、结果分布、风险切片和代表性失败；轨迹与结果状态如何支持结论，以及成本、延迟和错误变化；达成或未达成的决策条件、剩余不确定性和后续维护安排。

## 边界

- 基线与评估都是证据，不自动成为确定性产品契约；只有经过反复验证的稳定不变量才转成长期自动化测试。
- 正式环境观测不授权部署、流量实验或数据写入；只有原任务明确授权且安全边界成立时，才执行外部操作。
- 暂定评价量表、一次性探索记录和本地随机缓存不自动成为长期确定性契约。
- 证据保留与否由 [evidence-management](../evidence-management/SKILL.md) 按风险收敛。
- 开放式未知风险发现使用 [unknown-exploration](../unknown-exploration/SKILL.md)，已出现症状的根因调查使用 [systematic-debugging](../systematic-debugging/SKILL.md)，具有唯一稳定判据的确定性行为变更返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 重新选择开发方式。
- 子代理可以提供独立证据设计或人工评价，但其角色隔离按 [agent-and-parallel-dispatch](../agent-and-parallel-dispatch/SKILL.md) 管理，不能替代评价器校准。
- 行为保持型变更（如 [maintenance-operations](../maintenance-operations/SKILL.md) 涉及的维护操作）在修改实现前应先用本技能建立基线再对照；若该技能未显式引用本技能，此路由以本技能为入口。
