# Systematic Debugging：基于证据定位根因

## 核心原则

从真实失败边界获取证据，逐步降低不确定性。在某个原因假设能比其他候选更好地解释症状、调用链、环境和反证前，不提出确定性根因；到达第一个错误状态并建立因果链后结束本调查单元，不实施正式修复。

必要时可做最小、可逆且可丢弃的诊断插桩，但不得借此改变业务不变量或暴露敏感数据；部署、外部状态和正式环境操作仍需明确授权。决定保留插桩时立即停止调查，把它作为正式增量返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md) 重新选择开发方式。

## 确认症状

记录实际与预期行为、时间范围、环境、受影响标识符、部署提交或镜像、配置与依赖版本、证据的新旧和可复现性，以及已知未受影响范围。区分应用失败、错误测试假设、监控假象、网络限制和过时部署。

## 追踪真实路径

从真实入口沿数据流和控制流追踪到失败；优先使用仓库语义索引或调用图，再用源码搜索和运行时证据补充。

| 症状 | 有效证据 |
|---|---|
| 只在正式环境出现 | 日志、APM 跟踪、当前部署、只读 DB 状态和下游响应 |
| 失败测试 | 需求、真实调用方、夹具假设、依赖契约和改动代码 |
| 间歇性任务 | 任务载荷、重试、进程异常、幂等状态和时序 |
| 近期回归 | 部署或提交边界、`git log`、`git blame`、依赖和配置改动 |
| 性能回归 | 跟踪片段、剖析、查询计划、指标和代表性负载 |

调查期间不得写正式环境数据源，只查询必要数据并避免暴露敏感值。

## 检验原因假设

1. 列出由证据支持的候选原因，按解释能力排序。
2. 选择能区分首要候选的最小安全观测，必要时使用可逆插桩。
3. 根据结果更新候选，直到因果链到达第一个错误状态或契约违例。

本地复现只有在保留真实失败边界时才有价值，不是使用现有生产证据推理的前置条件。

## 交付根因证据与转换

- 报告症状边界、因果链、第一个错误状态或契约违例、决定性证据、影响范围、反证、剩余不确定性和建议修正边界，不修改实现或测试。
- 请求还包含修复时，建立足以支撑决定的根因证据后停止调查，把被违反的需求或契约、建议修改层和可复用的区分性观测返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md)，重新选择开发方式。

外部边界事实不确定时，把该问题返回 [adaptive-development-workflow](../adaptive-development-workflow/SKILL.md)，拆成独立的 [contract-verification](../contract-verification/SKILL.md) 调查单元。调查中重新运行区分原因的观测并检查受影响链路；证据只覆盖一种失败模式时，收窄结论。后续开发单元可以复用这些观测，但正式回归覆盖和变更后验证由开发方式及其生命周期支持负责。
