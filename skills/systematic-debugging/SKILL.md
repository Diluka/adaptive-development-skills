# Systematic Debugging：基于证据定位根因

## 核心原则

从真实失败边界获取证据，逐步降低不确定性。在某个原因假设能比其他候选更好地解释症状、调用链、环境和反证之前，不要实施推测性的生产修复。

如果区分原因假设的最安全低成本方式是增加诊断插桩，可以在范围和风险允许时进行最小、可逆的观测改动。涉及部署、外部状态或正式环境时仍需明确授权；不得借插桩修改业务不变量或暴露敏感数据。

## 确认症状

记录：

- 精确的实际行为、时间范围、环境和受影响标识符；
- 预期行为及其需求或不变量；
- 相关的已部署提交、镜像、包、配置和依赖版本；
- 证据是当前、历史、可复现还是间歇性的；
- 已知未受影响的范围。

区分应用失败、错误测试假设、监控假象、网络限制和过时部署。

## 追踪真实路径

从真实入口开始，沿数据流和控制流追踪到失败。优先使用仓库已提供的语义索引或调用图能力，再用源码搜索和运行时证据补充。

根据症状选择证据：

| 症状 | 有效证据 |
|---|---|
| 只在正式环境出现的失败 | 日志、APM 跟踪、当前部署、只读 DB 状态、下游响应 |
| 失败测试 | 需求、真实调用方、测试夹具假设、依赖契约、改动代码 |
| 间歇性任务 | 任务载荷、重试历史、工作进程异常、幂等状态、时序 |
| 近期回归 | 部署或提交边界、`git log`、`git blame`、依赖或配置改动 |
| 性能回归 | 跟踪片段、剖析结果、查询计划、指标、代表性负载 |

调查期间绝不写入正式环境数据源。只查询必要数据，并避免暴露敏感值。

## 检验原因假设，而不是试修

1. 列出由证据支持的可能原因。
2. 按解释能力排序，而不是按修改便利性排序。
3. 选择能区分首要候选的最小安全观测；必要时使用可逆诊断插桩。
4. 根据结果更新候选假设。
5. 继续追踪，直到因果链到达第一个错误状态或契约违例。

本地复现在保留真实失败边界时很有价值，但不是使用强生产证据推理的前置条件。删除关键边界的简化复现可能产生误导。

## 在正确层处理结果

先检查用户是否授权实施修复：

- 若请求仅要求诊断，报告根因、决定性证据、影响范围和建议修复，不修改生产实现或测试。
- 若请求包含修复授权，修改第一个违反已确认需求或契约的层。如果测试基于不存在的调用方或无效依赖行为，修正或删除测试；如果生产行为违反需求，在可行时通过稳定真实接缝保留回归测试。

对外部边界使用 [contract-verification](../contract-verification/SKILL.md)，使用 [evidence-based-testing](../evidence-based-testing/SKILL.md) 选择回归覆盖。不要仅为了复现人工测试而添加生产回退分支或选项。

## 验证解释或修复

重新运行用于区分原因假设的观测，并检查受影响链路和相关相邻检查。只要求诊断的任务应说明证据为何支持该根因以及剩余不确定性；已经实施修复时，还要说明改动为什么修复根因。证据只覆盖一种失败模式时，不要声称所有类似事件都已解决。

## 示例

如果多条执行记录报告同一堆栈跟踪，先判断它们是否是同一个失败的重复重试，而不是多个独立原因。检查代表性输入、首个错误状态、当前运行版本和下游契约。用户只要求诊断时报告结论；用户授权修复后，再修改最早违反假设的层，并验证失败输入与正常输入。

## 常见错误

- 不追踪错误状态来源，直接修改执行 `throw` 的位置。
- 在读取现有生产证据前强制先造失败单元测试。
- 把测试夹具当作真实调用方的证明。
- 为了测试理论而大范围查询或修改正式环境数据。
- 只验证偏好的原因假设，忽略相反证据。
- 把诊断请求自动扩展成生产修复。
