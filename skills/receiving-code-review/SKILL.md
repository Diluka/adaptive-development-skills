# Receiving Code Review：基于证据处理反馈

## 核心原则

把反馈当作需要验证的技术主张，而不是根据语气接受或拒绝的命令。只有建议符合真实需求和当前系统，而且当前请求已授权实施时才修改项目产物。

## 核验意见

对每条意见提取声称的缺陷或风险、引用位置和执行链路、受影响的需求或契约、建议改动、严重性和触发条件。多条意见依赖同一假设时先统一验证该假设。

1. 阅读引用内容和足够上下文，追踪真实链路。
2. 确认意见基于当前差异、分支和依赖版本。
3. 检查真实调用方、运行时注册、配置和契约。
4. 把测试作为证据审查，不默认测试或评审解释正确。
5. 用最小相关检查复现或静态证明问题。

外部行为未知时使用 [contract-verification](../contract-verification/SKILL.md)；意见依赖测试假设时使用 [evidence-based-testing](../evidence-based-testing/SKILL.md)。

## 决策与行动

| 结论 | 处理 |
|---|---|
| 已确认缺陷 | 报告证据；已授权时实施最小完整修复并验证 |
| 目标正确但建议方案错误 | 说明约束；已授权时采用符合契约的方案 |
| 不明确 | 只有仓库证据无法解决时才询问缺失需求 |
| 不适用 | 用调用方、契约或运行时证据回应，不修改 |
| 有效但超出范围 | 单独记录，取得新授权后另行处理 |

不要只为测试或审查建议增加生产开关、包装层、回退分支或公共接缝，也不要把“评估反馈”自动解释为“修改文件”。

## 完成闭环

处理意见属于原任务。开发任务由根代理把结论和状态写回原计划；非开发任务记录到调查结论或评审报告。实质修改项目产物后重新运行受影响验证，再通过 [requesting-code-review](../requesting-code-review/SKILL.md) 复审最终差异。修改会改变业务行为、范围、交付结果、授权或新增副作用时先暂停确认。

没有项目修改时记录接受、拒绝、延期或待澄清的证据。评审任务本身不递归评审；复杂非开发调研只改变结论而不产生项目产物时，也不触发开发任务或强制复审。

报告时先说明处理结论，再给决定性证据、验证和适用的复审状态；不要表演式赞同，也不要无证据驳回。
