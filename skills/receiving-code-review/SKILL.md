# 处理代码评审反馈

## 范围

把反馈视为待核验的技术主张。先问：保持意见所述内容不变，能否正确实现、验证和交付当前任务？能则记录为任务外发现；不能或尚不确定时，继续核验。

评审措辞、严重性和修复成本不改变任务范围。只有已确认的问题符合当前需求且已获修改授权时，才修改项目产物。

## 核验

对范围内的每条意见提取：声称的问题、引用位置、触发条件、受影响的需求或契约，以及建议改动。多条意见依赖同一假设时先核验该假设。

1. 阅读引用内容与实际差异，确认分支和版本。
2. 追踪真实调用方、运行时注册、配置和依赖契约。
3. 用最小相关检查复现或静态证明问题。
4. 对照原始需求判断建议方案是否必要且正确。

## 处理

| 结论 | 动作 |
|---|---|
| 当前任务内的已确认缺陷 | 实施最小完整修复并验证 |
| 问题真实，但建议方案不符合契约 | 说明约束并采用符合契约的修复 |
| 仓库证据无法解决的需求歧义 | 询问缺失决定 |
| 不适用 | 用调用方、契约或运行时证据回应 |
| 有效但超出范围 | 单独报告，取得授权后再处理 |

修改后只重新运行受影响验证；修改改变既有评审结论或风险面时，才需要新的独立评审。没有项目修改时，记录接受、拒绝、待澄清或超出范围的结论和决定性证据。
