# Receiving Code Review：基于证据处理反馈

## 核心原则

把反馈当作需要验证的技术主张，而不是根据语气接受或拒绝的命令。只有建议符合真实需求和当前系统，而且当前请求已授权实施时，才修改代码。

## 归一化每条审查意见

提取：

- 声称存在的缺陷或风险；
- 引用的文件、行号和执行链路；
- 受影响的需求、不变量、调用方或依赖契约；
- 建议改动；
- 严重性，以及触发缺陷所需的条件。

如果多条审查意见依赖同一个假设，先统一验证该假设，不要逐个位置重复修改。

## 对照当前证据验证

1. 阅读引用代码和足够的上下文，追踪真实链路。
2. 确认审查基于当前差异、分支和依赖版本。
3. 检查真实调用方、运行时注册、配置和契约。
4. 把测试作为证据审查，不要默认测试或审查者解释一定正确。
5. 用最小相关检查复现或静态证明问题。

外部行为不确定时使用 [contract-verification](../contract-verification/SKILL.md)；审查意见依赖测试假设时使用 [evidence-based-testing](../evidence-based-testing/SKILL.md)。

## 决策并按授权行动

| 结论 | 仅评估时 | 已授权实施时 |
|---|---|---|
| 已确认缺陷 | 报告证据、影响和建议修复 | 实施最小完整修复，并验证受影响链路 |
| 目标正确但建议修复错误 | 解释约束和符合契约的替代方案 | 实施符合契约的替代方案并验证 |
| 不明确 | 只有仓库证据无法解决时才询问缺失需求 | 在需求明确后再实施 |
| 不适用 | 用具体调用方、契约或运行时证据回应 | 不修改代码 |
| 有效但超出范围 | 单独记录，不静默扩大范围 | 取得额外授权后另行处理 |

不要只为人工测试或审查建议的实现增加生产代码选项、包装层、回退分支或公共接缝。

## 完成评审闭环

处理开发任务的独立评审意见属于原开发任务，不创建新的任务或计划。根代理把已确认结论和处理状态写回原计划：

- 没有修改项目产物时，记录接受、拒绝、延期或需要澄清的证据和理由；
- 实质修改准备交付的项目产物时，重新运行所有受影响验证，再通过 [requesting-code-review](../requesting-code-review/SKILL.md) 让未参与该轮实现或修复的独立子代理复审新的最终差异；
- 修改会改变业务行为、扩大范围、改变交付结果、引入新增副作用或需要新授权时，先按原计划的用户确认边界暂停；
- 评审任务本身不递归要求评审，纯粹处理已经完成开发的提交、推送或 PR/MR 也不创建新开发任务；但交付前再次修改项目产物，就重新进入验证和复审。

复杂非开发调研的可选评审只需核验目标覆盖、证据和结论；如果处理意见仍只改变调查结论而不产生准备保留的项目产物，不触发开发任务或强制复审。

## 清晰报告

先说明处理结论：确认但未实施、已接受并修复、接受目标但采用不同修复、需要澄清或不适用。引用决定性证据、重新验证和适用的复审状态。避免表演式赞同，也不要在没有证据时驳回反馈。

## 示例

审查者基于内部单元的合成输入，要求生产代码接受该输入结构。先追踪真实入口与归一化契约。若真实调用方不会产生该输入，评估时应报告测试假设错误；已授权修复时应修正测试，而不是增加回退分支。若真实边界确实可能产生该输入，则保留审查意见并覆盖真实边界。

## 常见错误

- 未阅读当前链路就实施每条建议。
- 因为原作者的意图而为代码辩护。
- 把审查者提供的测试当作需求。
- 只修审查位置的症状，遗漏上游无效状态。
- 把有效但无关的清理混入被审查改动。
- 把“评估反馈”自动解释为“修改文件”。
- 实质修复后复用旧验证或旧评审结论，没有让独立子代理复审最终版本。
- 为处理审查意见递归创建新的开发任务，或反过来借原任务静默扩大范围。
