# Using Git Worktrees：让开发分支默认隔离

## 核心原则

是否创建开发分支仍按任务需要、风险、交付方式和用户要求决定，工作树规则不反过来强迫任务开分支。只要决定为可能产生项目改动的工作创建或检出开发分支，且用户或仓库没有指定其他安排，默认就在独立工作树中进行，让仓库根路径保留默认分支作为稳定基线。明确直接在默认分支完成的工作可以继续使用根路径。

纯只读分支访问是例外。只要不会修改或生成项目状态，并且根路径的默认基线能够安全保持或恢复，执行者可以根据检查成本选择直接比较 refs、在根路径临时检出，或使用工作树；任一条件不确定时使用工作树。

## 判断是否需要

- 任务不需要开发分支，且没有其他隔离风险时，继续使用默认分支所在的根路径。
- 一旦为可能产生项目改动的工作创建或检出开发分支，默认创建或复用对应的独立工作树；改动小、风险低或当前工作区干净都不改变这个默认值。
- 纯只读审查不需要检出时，优先直接比较目标 refs。临时检出更简单时，只有根路径干净、没有并行任务依赖该基线、检查命令不会写入工作区，并且已确认恢复目标时，才可在根路径进行；结束后立即恢复默认分支并确认状态干净。任一条件不满足时使用工作树。
- 当前已经位于该开发分支的关联工作树时直接复用，不创建嵌套或重复工作树。
- 高风险历史操作、大型迁移、冲突解决、并行分支或依赖、目标文件与现有改动重叠，以及验证其他分支或版本时，即使不准备长期保留分支，也按具体风险使用工作树或分离 HEAD 隔离。

任意未提交改动本身不要求创建开发分支，但会限制安全迁移方式；不得为了腾出根路径而擅自暂存、提交、丢弃或移动这些改动。

## 创建前检查

```bash
git rev-parse --show-toplevel
git rev-parse --git-dir
git rev-parse --git-common-dir
git rev-parse --show-superproject-working-tree
git branch --show-current
git status --short
git worktree list --porcelain
```

根据仓库说明和远端元数据确认默认分支、根工作树、目标基点、分支是否已存在以及是否已在其他工作树检出；不要硬编码 `main` 或 `master`。Git 目录与公共目录不同时，当前工作区通常已是关联工作树。它仍可创建同级工作树，但不得把新目标放在当前关联工作树目录内。

除适用的临时纯只读例外外，若根路径已经检出开发分支，先检查状态。干净时把根路径恢复到默认分支，再为该开发分支创建关联工作树；存在未提交改动时停止自动迁移，先确认这些改动的归属和安全搬移方式，不使用隐式 stash、临时提交或丢弃来制造干净状态。工作树位置仍按下节默认规则解析，不仅因用户未指定路径而询问；需要确认的是未提交改动的处理方式。目标分支已经在其他工作树时直接复用该位置。

没有初始提交时先核对当前 Git 的真实契约；支持 `git worktree add --orphan -b <branch> <path>` 时，使用独立的 orphan 分支工作树，不为建立工作树自动生成初始提交。当前 Git 不支持或创建失败时报告限制并请求处理方式，不静默退回根路径继续开发。

## 选择位置并创建

优先遵循用户和仓库指定的位置。没有特别约定时，使用根工作树下的 `<repo>/.worktrees/<name>`；当前位于关联工作树时，先从 `git worktree list --porcelain` 解析根工作树，不把新目标放进当前关联工作树目录。

在承载 `.worktrees/` 的工作树根目录确认忽略规则：

```bash
git check-ignore -q --no-index .worktrees/
```

未被忽略时，只有仓库配置属于当前范围才添加精确规则，不静默提交。优先使用执行环境的原生工作树能力；否则以明确分支和解析后的路径运行 `git worktree add`，不从未检查变量或宽泛路径推导目标。

使用 Git CLI 时，新分支应直接通过 `git worktree add -b <branch> <path> <base>` 在目标工作树创建，不先让根路径切到该分支。已有分支在确认未被其他工作树占用后，通过 `git worktree add <path> <branch>` 检出。

创建命令或创建后验证失败时保留原状态并报告精确错误，不自动改在根路径执行，也不使用 `--force`、隐式 stash、临时提交或分支重置绕过失败。

## 创建后

1. 确认根路径仍在默认分支，目标路径检出预期开发分支或分离 HEAD，且两处状态符合预期。
2. 确认目标基点、上游关系和干净状态，不把陈旧分支误当作最新基线。
3. 阅读新工作区的仓库说明。
4. 开发任务读取协调工作树中的计划绝对路径，不复制计划；非开发调查读取共享目标和证据边界。
5. 只执行任务需要且已授权的准备。不要自动安装依赖、运行全量测试、提交、拉取、推送、合并或删除其他工作树。
6. 条件具备时运行能区分新回归与基线失败的最小检查；缺依赖时报告限制。

报告工作树路径和分支。集成与移除交给 [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md) 或用户明确请求；删除前确认没有会丢失的未提交工作。
