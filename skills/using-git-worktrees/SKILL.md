# Using Git Worktrees：按风险建立隔离

## 核心原则

只有隔离能降低具体 Git 或并发风险时才创建工作树。不要让每次改动都承担工作树准备成本。

## 判断是否需要隔离

以下情况适合使用工作树：

- 历史改写、大型迁移、冲突解决或高风险仓库历史操作；
- 需要不同分支或依赖的并行任务；
- 当前工作区中的无关改动与目标文件重叠；
- 需要在不干扰当前工作的情况下验证另一个分支或版本；
- 仓库或用户明确要求。

对于干净、低风险、隔离的改动，如果没有并发状态需要保留，就继续使用当前工作区。

## 创建前检查

```bash
git rev-parse --show-toplevel
git rev-parse --git-dir
git rev-parse --git-common-dir
git rev-parse --show-superproject-working-tree
git branch --show-current
git status --short
git worktree list --porcelain
```

如果 Git 目录与公共目录不同，并且当前工作区不是子模块，则当前工作区已经是关联工作树。这个事实本身不阻止继续创建工作树：优先使用执行环境提供的原生能力；否则选择当前关联工作树之外的同级位置，并通过 `git worktree list --porcelain` 确认目标分支尚未在其他工作树中检出。

没有初始提交的空仓库无法提供有效工作树基点。报告这一限制并继续使用当前工作区；除非用户明确要求，否则不要为了创建工作树自动生成初始提交。

## 选择安全位置

优先遵循仓库说明。当前工作区是主工作树时，可使用 `<repo>/.worktrees/<name>`。当前工作区是关联工作树时，优先使用仓库指定的同级目录或从主工作树位置解析目标；不要把新目标放在当前关联工作树目录内。

在将承载 `.worktrees/` 的工作树根目录确认该目录已被忽略：

```bash
git check-ignore -q --no-index .worktrees/
```

如果未被忽略，只有在仓库配置属于当前范围时才添加精确忽略规则；不要静默提交这项改动。

优先使用执行环境提供的原生工作树能力。否则使用明确分支名称和解析后的路径执行 `git worktree add`。绝不从未经检查的变量或宽泛路径推导破坏性目标。

## 只准备任务需要的内容

创建后：

1. 确认路径、分支或分离 HEAD 状态，以及干净状态。
2. 阅读新工作区中的仓库说明。
3. 开发任务读取当前计划文档；若计划位于协调工作树的忽略目录，使用根代理提供的绝对路径，不在新工作树复制出独立版本。非开发调查只读取共享目标、边界和证据要求。
4. 识别并报告后续任务需要的依赖或准备工作，但不要把安装当作创建工作树的自动步骤。只有用户明确要求，或已授权执行计划明确包含安装时，才使用项目锁定工具链安装。
5. 环境已经具备条件时，运行能区分新回归与已知失败的最小基线；缺少依赖时报告限制，不要顺手安装。

不要自动安装依赖、运行全量测试、提交文件、拉取、推送、合并或删除其他工作树。

## 明确结束方式

报告工作树路径和分支。把集成和移除留给 [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md) 或用户的明确请求。删除前确认目标工作树没有会丢失的未提交工作。

## 常见错误

- 为了流程仪式创建工作树，并没有实际隔离需求。
- 把当前工作区是关联工作树误判为不能创建同级工作树。
- 在当前关联工作树目录内选择新工作树目标。
- 检查 `.worktrees` 时丢失目录语义，误判忽略规则。
- 创建工作树后自动安装依赖或运行任务不需要的准备命令。
- 实现完成后自动删除工作树或分支。
