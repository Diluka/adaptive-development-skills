# Git 工作树

## 基本规则

工作树规则本身不要求创建分支。任务需要开发分支时才创建分支；为项目改动创建或检出开发分支，且用户和仓库没有指定位置时，默认使用独立工作树，让 Git 根工作树保留默认分支作为稳定基线。用户明确要求直接在默认分支完成时，继续使用根路径。改动小、风险低或当前工作区干净，都不改变这个默认值。

工作树隔离 Git 状态和文件，会话负责上下文、所有权和生命周期。只有粗粒度、持续写入的并行开发单元才要求各自拥有负责会话和独立工作树；创建、进入或复用工作树不要求新会话。

纯只读分支访问可以直接比较 refs、在根路径临时检出，或使用工作树。只有检查不会修改或生成项目状态，且根路径的默认基线能够安全保持或恢复时，才可使用根路径；拿不准就使用工作树。

每个工作树都有独立的工作目录、索引和检出状态，但会通过公共 Git 目录共享分支与远端引用、对象库、仓库配置与钩子、`refs/stash` 和工作树注册信息。端口、进程、数据库和外部服务等运行资源不会自动隔离，必须单独协调。

## 创建前检查

先解析仓库拓扑与状态：`git rev-parse --show-toplevel`、`--git-dir`、`--git-common-dir`、`--show-superproject-working-tree`、`--verify HEAD`、`git rev-list --all --max-count=1`、`git branch --show-current`、`git status --short`、`git worktree list --porcelain`。Git 目录与公共目录不同时，当前工作区通常已经是关联工作树。

根据仓库说明和远端元数据确认默认分支、根工作树、目标基点、分支是否存在，以及它是否已在其他工作树检出。不要硬编码 `main` 或 `master`。结合分支、状态、计划和任务目标判断现有工作树是否属于当前任务；不要迁移或复用其他任务的状态；需要新建时，可以把新工作树放在现有工作树的同级目录，但不得放进当前关联工作树目录。

### 根路径已检出开发分支

除临时纯只读例外外，根路径已经检出当前任务的开发分支时，先检查状态。状态干净时，把根路径恢复到默认分支，再为该开发分支创建关联工作树。存在未提交改动时，停止自动迁移，先确认改动归属和安全搬移方式；不要用隐式 stash、临时提交或丢弃来制造干净状态。

根路径中的开发分支属于其他任务或归属不明时，保持原状并报告占用。条件允许时，仍可从经核实的基点为当前任务创建独立工作树，但不能为了恢复默认基线而切换其他任务的分支。真正需要确认的是未提交改动的处理方式，不是用户没指定路径就询问。

### 没有可用的当前 `HEAD`

`git rev-parse --verify HEAD` 失败，只表示当前工作树的 `HEAD` 无法解析，不代表仓库没有提交。先核实任务目标分支或提交，再用 `git rev-list --all --max-count=1` 检查其他引用；存在可用基点时，从该基点创建工作树。

确认没有可用提交基点后，再通过当前 Git 的帮助核对 `--orphan` 契约。Git 支持该选项且任务不依赖根路径中的未跟踪内容时，使用 `git worktree add --orphan -b <branch> <path>` 创建未出生分支的独立工作树；不支持、创建失败或任务依赖这些未跟踪内容时，报告限制并请求处理方式。不要为了建立工作树而自动生成提交、复制其他任务内容，或静默退回根路径继续开发。

## 选择位置并创建

本节的位置和命令规则，只适用于当前执行上下文通过 Git CLI 创建并自行管理的工作树。目标已由执行环境创建，或已是关联工作树时，直接核对并复用，不执行重复创建命令。

手工 Git CLI 工作树优先遵循用户和仓库指定的位置。没有特别约定时，使用根工作树下的 `<repo>/.worktrees/<name>`。当前位于关联工作树时，先从 `git worktree list --porcelain` 解析根工作树，不把新目标放进当前关联工作树目录。

在承载 `.worktrees/` 的工作树根目录用 `git check-ignore -q --no-index .worktrees/` 确认忽略规则；未被忽略时，只有仓库配置属于当前任务范围，才添加精确的忽略规则，不要静默提交。

环境有适用于当前目标的原生工作树能力时优先使用。没有适用能力，或用户和仓库明确选择手工管理时，以明确的分支和解析后的路径运行 `git worktree add`，不要从未检查的变量或宽泛路径推导目标。通过 `git worktree add -b <branch> <path> <base>` 直接在目标工作树创建新分支，不要先让根路径切换过去；已有分支确认未被其他工作树占用后，再通过 `git worktree add <path> <branch>` 检出。

创建命令或创建后验证失败时，保留原状态并报告准确错误。不要自动改在根路径执行，也不要用 `--force`、隐式 stash、临时提交、分支重置、删除其他工作树或修改其他任务状态来绕过失败。

## 创建后

1. 按用户或仓库安排确认根路径处于预期分支；默认场景下保留默认分支。确认目标路径检出预期开发分支或分离 HEAD，且两处状态符合预期。
2. 确认目标基点、上游关系和干净状态，不把陈旧分支误当作最新基线。
3. 阅读新工作区的仓库说明。
4. 有适用计划时，读取协调工作树中的计划绝对路径，不复制计划；没有计划的开发任务和非开发调查，读取共享目标、约束和证据边界。
5. 只执行建立隔离环境所需的准备。不要在创建工作树阶段提前安装依赖、运行全量测试或执行最终 Git 交付；实现与验证完成后，由 [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md) 按任务默认值或用户限制处理提交、推送和 MR/PR。拉取、合并和删除其他工作树继续遵守各自边界。
6. 条件具备时，运行能区分新回归与基线失败的最小检查；缺依赖时报告限制。

报告任务工作树路径和分支。进入后只在该工作树中实施和检查本任务，不把其他工作树的并发改动纳入本任务差异。普通 Git 交付、集成与移除交给 [finishing-a-development-branch](../finishing-a-development-branch/SKILL.md)；删除前确认用户要求清理，且没有会丢失的未提交工作。

## 并行开发前

准备通过多个工作树并行开发时，先完整阅读 [通过工作树并行开发](resources/parallel-development.md)，随后划分所有权、依赖、共享资源和串行集成边界。
