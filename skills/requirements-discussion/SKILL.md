# 需求讨论与收敛

帮助用户把逐步表达的想法收敛为可执行共识，而不是把每句探讨立即变成任务。优先形成正确理解和必要取舍，不追求尽快派工或补齐文档。

## 判断当前在讨论什么

- 按当前需求缺口进入讨论；简单、已定的需求直接进入现有流程，不额外增加讨论阶段。
- 结合语义、前后文和既有决定，分辨探讨、偏好与已定决定，不靠孤立关键词机械判断。
- 先理解用户想得到的结果，再讨论实现方案；只问会影响范围、验收或授权的关键未知，不重问已有答案。
- 意图不明确且会影响执行时才澄清；不能因为用户提到一种做法，就推断已选定方案或授权实施。

## 推进而不抢跑

- 综合多轮意见修正当前理解，不把每条新意见当作孤立任务，也不只附和最后一句话。
- 围绕当前争点比较相关方案，说明影响选择的事实、收益、代价与不确定性；不为凑数扩展候选。
- 保留建议和偏好的适用条件，不把默认建议升级为必须遵守的红线。
- 遇到意见矛盾或事实缺口，指出对目标的具体影响，提出需要选择的取舍或最小必要核实，不用猜测填空。
- 需要用户反馈时，给出当前理解和关键问题后主动交还对话，不连续调用工具推进尚未收敛的事项。
- 头脑风暴只是可选方法；不强制发散，也不规定方案数量或问答轮数。

## 何时交还现有流程

- 用足够简短的表达保留当前共识与未决点，只整理有助于下一步的信息，不要求每轮填固定栏目。
- 已确定部分足以拆分即可交回后续流程；执行条件与授权已具备的工作可开工，不等待所有需求谈完或固定“批准”口令。
- 未决部分只阻塞真正依赖它的事项，不阻塞无关的已定工作；讨论本身不构成派工或写入授权。
- 新意见改变既有共识时，只重新讨论受影响部分，不无故重开全部需求。

## 职责边界

- 本技能是按需的判断机制，不是第二个总入口；形成共识与未决点后交回现有流程，不包办任务拆分与实施。
- 不默认生成产品需求文档、规格或计划；用户确实需要这些交付物时，再交由相应流程处理。
