# 技能包设计

> 状态：**v3**。本文是技能包目标状态的权威说明；历史重构记录留在 `.docs/plans/`。

## 目的

用户通常只给一句话需求，而不是一份现成规格。这套技能的价值是让代理基于当前事实，稳定选择**下一步最有信息或交付价值的动作**：该直接做、核实契约、追查已观察的错误、澄清用户才能决定的规则，还是先做可丢弃试验。选择后才按所选方法的规矩执行，用与声明相称的证据停止。

成功意味着少绕路、少返工，交付符合真实需求与契约；不是让相同措辞永远映射到相同方法。同一句“加上退款申请”，已有退款规则和接口时可以直接实现，资格、权限或状态规则没有来源时应先澄清关键决定。工作路径由**已知事实与缺口**改变，而不是由“加、修、调查”等动词决定。

## 从请求选择下一步

1. 识别用户要得到事实、决定，还是项目产物；以当前仓库、调用方、既有约束和授权判断已经知道什么。简短请求不自动要求正式规格、计划或新测试。
2. 找出当前最可能使下一步走错的缺口。缺的是用户拥有的业务取舍时，只问会改变行为或验收的关键问题；缺的是可核查的版本、调用方或症状时，用最小只读调查；缺的是可行性事实时做隔离、可丢弃的探索。缺口已由现有证据覆盖时直接回答或实施。
3. 从能拒绝当前合理错误的最短路径开始；风险、不可逆性、依赖关系和外部副作用决定是否增加计划、独立评审或更强证据。路径变化时保留仍适用的事实，只修正受影响的动作与验证。
4. 核对真实消费或激活路径上的结果、适用的仓库强制检查，以及声明所需的授权与独立证据；足以支持当前结论即停。提示文本或一次代理模拟只能说明有限样例，不能代替安装后的真实表现。

**辨别相邻路径**：已观察到稳定错误状态，追到首个错误与因果链；外部行为或版本未知，先核对实际安装或部署契约；连可行性或评价依据都未知，做有限探索。行为保持型删除先排查动态调用方并建立可比较的真实基线；已有稳定判据的功能改动可直接实施。正式规格只有已被明确选为实施依据且维护追溯链确有价值时才成为方法输入；不能为了选“规格驱动开发”先编一份规格。

## 节点与方法的分工

`adaptive-development-workflow` 从请求决定当前要做的事及其边界；讨论、调查、设计、作业、验证、评审都是可选的工作视角，不是一条固定流水线。`execution` 在当前边界内区分具体调查、开发、验证与文档方法；缺口不存在时直接行动也是完整选择。复杂机制（工作树、独立评审、交付、文档等）在实际选择后再加载。

| 当前障碍 | 最小有效动作与停止信号 |
|---|---|
| 会改变需求或验收的用户决策缺失 | 澄清那项决定；已经由用户或权威事实确定时继续，不重问 |
| 真实调用、外部契约、根因或可行性未知 | 针对缺口取证；足以选择实现或回答时停止调查 |
| 目标、约束与实际接缝已知 | 直接实施或检查；从真实使用路径核对预期结果 |
| 产物复杂、跨单元或难以回退 | 为已经选定的路线记录必要计划、依赖与风险，不用计划替用户做产品决策 |
| 完成声明尚缺覆盖 | 补能拒绝该风险的证据；需要独立视角时交未参与实现者评审 |

调查是取证方式，不是绕开已授权实现的终点：同一请求既要求调查又要求修复时，调查结果可以直接支持当前授权范围内的实施；出现新的用户可见行为、公共契约、架构边界、风险、授权或副作用时暂停受影响路径，关键取舍或高风险/难回退新动作先确认。计划只承载已选方向，执行发现新证据时可修正；用户纠正需求时清除旧假设在实现、测试和文档中的残留。

## 内容与加载原则

技能写能改变选择或执行可靠性的判据、不可替代的失败经验、停止条件和安全边界；公开标准方法只需完整名称与**可区分相邻方法的一句话**，不复述训练语料中已有的教程。独立技能承载选择后仍需专门约束的机制；`resources/` 只存实际会按需读取的细节。`description` 以 `Use when` 起头，指向真实用户问题或独有缺口，避免让所有日常任务同时触发多个宽泛入口。

缩写有歧义时，每个文件首次出现独立写出中文名、英文全称和缩写，并说明后续使用缩写；技能和方法名称用全称。通用技术词不需逐一展开。

文档从读者的问题出发，真实负向行为、安全限制和有决策价值的淘汰理由照实表达；不以否定词数量、固定栏目或字数代替准确性。来源、版本和适用范围影响结论时保持可追溯，避免一个事实出现互相竞争的权威解释。

## 不可失的边界

- 需求、已确认不变量、真实调用方和已核验契约优先于实现、测试及预设流程；缺少事实不能用代理推测补成产品规则。
- 动态导入、反射、注册、配置或外部调用可能让静态引用搜索漏报；死代码删除和兼容性判断需要对应证据。锁文件声明与实际安装/部署版本冲突时，以实际运行边界为准并报告差异。
- 独立评审者不能参与所评内容的实现、证据设计或修改。测试期望不从待写实现复制；替身只隔离真实外部边界，已由类型证明的约束不再靠镜像运行时断言补数。
- 用户未收窄的开发成果按目标仓库约定完成分支、提交、推送与 MR/PR，并核对最终提交的 CI；只读调查不自动触发 Git 交付。合并、发布、部署、权限修改、外部消息、流量调整和其他高影响操作不因选择方法而获得授权；开发、调查与验证不得写入正式环境数据源。保留用户和其他任务的改动。
- 验证复用仍适用于当前输入、环境、版本、调用路径和风险面的证据；最终完成声明核对实际增量、适用独立评审和最终提交的 CI 状态。静态结构检查不证明代理行为改进。

## 验收场景

用相同的短请求和固定事实输入核对首个实质动作、待问的关键决定、验证或停止信号；改变事实后，路径必须随之改变：

- “给订单页加按订单号筛选”：用户已确认完全匹配，接口支持 `orderNo` 且页面已有筛选控件时直接实现并验证筛选、清空；同一句话若多商户订单号重复、匹配范围无权威规则，先询问用户是全局、商户内还是模糊匹配；若匹配规则已定但接口行为未知，则先核验接口。三者都不先编规格。
- “让移动端支持退款申请”：资格与权限规则没有权威来源时询问用户拥有的关键决定；现有规则和服务契约都已覆盖时沿真实移动调用链实施，不自行发明退款规则。
- “修复取消上传却提示成功”：已可稳定复现时先观察取消路径并追踪错误状态；修复后验证取消不提示成功且正常上传仍成功，不用延迟或大重构猜根因。
- “升级支付 SDK”：目标版本已由用户选定为 2.x，部署实际用 1.x 而锁文件是 2.x，且要求保持现有支付行为时，先核验运行调用方、版本差异和回调基线，再决定升级步骤；同一句请求若目标版本尚未确定且版本选择会改变兼容方案，先确认目标。不只改声明版本，也不在正式环境执行交易探测。

事实翻转对照、重复运行和真实安装后的反馈才能评估启发式选择。上述样例是验收输入，不宣称单次模拟证明生产使用效果。

## 当前技能分工

- **选路**：`adaptive-development-workflow` 管从请求到工作边界，`execution` 管当前缺口与具体方法。
- **调查**：`system-understanding`、`contract-verification`、`unknown-exploration` 分别处理现有系统事实、真实边界契约和可丢弃试验。
- **机制**：`maintenance-operations`、`using-git-worktrees`、`agent-and-parallel-dispatch`、`documentation`、`requesting-code-review`、`receiving-code-review` 承担选定后的特殊约束。
- **收尾**：`verification-before-completion` 核对完成声明，`finishing-a-development-branch` 处理普通 Git 交付，`delivery` 处理主干集成、可发布性和受控暴露；方法本身不扩大操作授权。

从简短请求能否选出正确路径、避免多余产物与越权行动、并保留以上红线来评估每项技能是否值得独立存在；目录完整不是存在理由。
