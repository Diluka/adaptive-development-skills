# 技能包设计

> 状态：**v2** 本文件是 adaptive-development-skills
> 的设计文档，描述技能包的目标状态与设计规则。
> 历史演进与重构过程记录见 `.docs/plans/` 下的临时计划文件。

## 1. 目的与设计原则

### 1.1 目的

- 让使用这套技能的代理在**办事效率**与**任务准确度**之间找到合适的平衡。
  - 效率 = 少绕路、少做无用功、快速交付。
  - 准确度 = 少出错、少返工、满足真实需求与契约。
- 平衡点不固定，随「实际情况」（增量大小、风险、证据缺口等）动态调整，由代理
  临场决定，技能不预设判断。

### 1.2 结构

技能在设计上分为两类：

| 类别 | 角色 | 内容 |
|---|---|---|
| **入口** | 理解工作节点与执行循环 | `adaptive-development-workflow` 说明节点是什么与各自规矩；`execution` 提供执行循环与方法名录 |
| **方法** | 选定后落地执行的具体方法 | 独立机制技能（git 工作树、评审、交付、文档等）与 `execution` 方法名录中的公开标准方法 |

设计目标：技能包提供「方法目录 + 规矩」，不教代理如何决策——所有工作节点与
方法都是可选的，选中就要按规矩办事；何时进入哪个节点、选择哪个方法，由代理
根据任务实际情况临场发挥。

### 1.3 放权原则

- 技能不预设「什么情况必须/不能进入某个节点」，不预设「什么级别必须做什么」。
- 技能保留：节点与方法的**规矩**（核心循环、停止条件）、**红线**（安全 / 授权 /
  隐私 / 合规）、以及**仓库经验**（踩坑换来的判据，如动态调用方清单、实际安装
  版本优先、评审必须独立）。
- 公开标准方法（TDD、BDD、属性测试、契约测试、主干开发等）AI 预训练已覆盖，
  正文只提完整名字与一句话适用，不复述标准流程。

### 1.4 缩写规则

- 方法名 / 技能名一律全称（目录、`name` 字段、正文首次提及），不写缩写，
  防止缩写歧义（例：TDD 同时是 Test-Driven Development 与 Type-Driven Design
  的缩写）。
- 有歧义的方法缩写（SDD、BDD 等）在每个文件首次出现处写「完整中文名 + 英文
  全称 + 缩写 + 声明后续使用缩写」，**每个文件独立声明，不跨文件继承**。
- 无歧义的通用技术词（API、CLI、SDK、HTTP、SQL、CI 等）不声明全称。
- 全局术语对照表不保留：全局统一声明无法消除跨文件歧义，歧义处置下沉到各文件
  首次声明。

### 1.5 项目产物表达

计划、Issue / 工作项、需求、设计、规格、ADR、README、Wiki 和交付文档以当前路线为主体，用目标、纳入范围、必要约束、决策依据和成功标准闭合内容。讨论和调查可以比较候选路线；进入项目产物时提炼选定方向与真正门控的未决项。

淘汰路线的原因有助于理解或复核当前决策时，在最接近决策依据的位置记录一次路线名称及其与决策标准冲突的原因，说明深度止于该决策依据；决策、实施和后果继续只描述当前路线。安全、授权、隐私、合规和真实负向行为契约继续明确表达。

范围在一个权威位置用穷尽的纳入项和必要约束闭合；该定义已经完整承载用户列出的排除要求时，省略被排除对象的名称。后续章节引用该范围或验证实际集合。适用栏目按实际事实出现；空的风险、未知、评审、发布或回退栏目直接省略。

定稿时逐句检查含“不、无、未、禁止、避免、排除、无需、不得”等否定标记的内容。安全 / 授权 / 隐私 / 合规红线、真实负向行为契约、影响结论的证据缺口，以及一处带具体原因的淘汰路线具有信息价值；其余句子改写为目标状态、纳入范围、选定动作或正向验收标准，改写后仍无新增信息则删除。

## 2. 工作节点（adaptive-development-workflow）

### 2.1 节点是什么

| 节点 | 是什么 | 规矩 |
|---|---|---|
| **讨论** | 与用户一起澄清需求边界、关键歧义与成功标准 | 先发散再收敛，只澄清会实质改变方案的关键歧义；可参考头脑风暴（Brainstorming） |
| **调查** | 取证回答未知：读代码、文档、日志、跑实验 | 只交付可追溯事实、证据与决策输入；证据足以回答原问题即停止 |
| **设计** | 把选定方向展开为落盘方案 | 计划只承载已完成选择的内容 |
| **作业** | 产出交付物：代码、正文、配置、调研 | 以真实调用方、契约和项目约定为边界 |
| **验证** | 核对产物是否符合预期 | 用真实消费或激活路径的直接证据；证据足以支撑声明即停止追加 |
| **评审** | 整体审视交付是否值得 | 必须独立于实现者；只给意见与结论，不改动 |

### 2.2 编排原则

- 所有节点可选，不预设任何节点"必须"或"不能"进入；由代理根据任务实际情况
  临场编排。
- 节点不是固定流水线：返工（验证失败回到作业）、插入子流程（作业中插入调查
  或讨论）、任务分裂（新事实产生独立目标）都是正常形态。
- 每个保留节点都要能说明它能发现哪种合理错误；已有证据覆盖同一风险或节点没有
  实际收益时可跳过。
- 完整例子（串起全部节点的复杂工作流）见 `adaptive-development-workflow/SKILL.md`。

## 3. 任务类型

| 类型 | 含义 | 典型产出 |
|---|---|---|
| **讨论** | 和用户一起把模糊的事情逐渐定义清晰 | 澄清后的定义、规格、决策 |
| **调查** | 研究和学习 | 事实、根因、可行性、证据 |
| **作业** | 完成具体的工作 | 可交付成果（代码、配置、文档等） |
| **验证** | 对一个已有的东西进行论证 | 论证结论（是否正确、是否满足） |

- 类型是模糊的大分类而非互斥标签，可看作任务的**侧重点**：一个任务通常以一类
  为主，可能叠加其他类型；侧重点决定主工作流。

## 4. Execution（微观执行）

### 4.1 执行循环

每个工作单元遵循同一循环，但步骤轻重按任务实际情况调整：

1. **明确边界与缺口**：确认工作单元、当前节点、目标、范围、授权与待拒绝的合理
   错误；盘点当前上下文已有结论与证据，已有事实足以回答就直接执行或回答。
2. **选择做法并执行**：按主要不确定性或风险从方法名录选择一个主要方法；不存在
   待补缺口时直接实现、直接检查或直接操作是一等选择。
3. **核对结果并同步**：用所选证据核对动作结果；有计划时同步状态、关键证据和
   偏差。
4. **反馈、重选或转换**：结果只改变当前动作、方法或证据组合时在原节点内修正
   后继续；改变工作单元、级别、节点、范围、授权、交付结果或副作用时返回工作流
   重新编排。

### 4.2 方法名录

方法都是可选的，按任务实际情况临场选择；选中就要按该方法规矩办事。完整名录
（调查 / 开发 / 验证 / 文档评审交付 / 执行机制）见 `execution/SKILL.md`。公开
标准方法只保留完整名字 + 一句话适用，不复述标准流程。

### 4.3 资源

- `resources/verification-selection.md`：验证手段（动态执行 / 静态检查 / 审视
  核对）与最小充分组合原则。
- `resources/evidence.md`：证据充分性、独立性、复用、失效与收敛。
- `resources/baseline-and-evaluation.md`：行为基线与评估方法分流。

### 5.3 独立技能设计原则

- 每个技能有**明确职责、清晰边界**，不与其它技能重叠或冲突。
- **放权优先**：技能提供判据与规矩，不提供决策预设。
- **宁少勿滥**：不设无实际收益的宽泛技能；公开方法不设独立入口。
- **经验沉淀**：仓库踩坑换来的判据与红线必须保留，这是技能包不可替代的价值。
- **加载策略**：简单方法可直接提及；复杂方法经决策确定适用后再按需读取其说明，
  避免污染上下文。触发描述（`Use when`）只回答"这是什么"，不回答"你现在该不该
  用"——是否使用由代理临场决定。

### 5.4 缩写与全称

- 技能名 / 方法名一律全称（目录、`name` 字段、`agents/openai.yaml` 的
  `display_name`、正文首次提及），不写缩写。
- 有歧义的方法缩写：每个文件首次出现处写「完整中文名 + 英文全称 + 缩写 +
  声明后续使用缩写」，不跨文件继承。
- 无歧义的通用技术词不声明。

## 6. 授权与红线（全局）

- 开发任务默认按仓库约定完成分支、提交、推送与 MR/PR；用户明确收窄时按其限制
  执行。
- 合并、发布、部署、正式环境写入、权限修改、外部消息、流量调整和其他高影响
  外部操作需要明确授权；选择任何方法或交付机制都不扩大授权。
- 调查、开发和验证期间不得写入正式环境数据源；只读证据不授权数据修复。
- 保留用户和其他任务的改动；不通过暂存、提交、重置、清理或移动来占用其状态。
- 评审必须独立于实现者。
- 不为测试增加真实调用方不需要的生产开关、包装、回退、分支或公共接口。
